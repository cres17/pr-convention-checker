작성일: 2026-10-07  
대상: `ver2`, HEAD `d262ec2faff3b98c917e3e99f7b6260cf0514ff3`에 앞선 수정과 이번 수정이 적용된 미커밋 작업 트리

## 1. 결론

앞선 논리 업데이트에는 실제로 재현되는 결함 네 종류가 남아 있었다. 이번에는 테스트 수와 문서 설명을 전제로 삼지 않고, 입력 형식·이름 해석·참조·순서·변경 강도 조건을 바꾸는 반례로 찾았다. 모두 운영 코드와 회귀 테스트를 수정했다.

현재 검증한 범위에서는 같은 입력의 순서와 Python 해시 seed가 판정·검증 상태를 바꾸지 않는다. 확인된 문서 불일치는 다른 계약의 확인 불가 상태와 함께 보존된다. 실제 Git diff의 응답 필드 삭제도 엄격한 계약 검사를 실행한다.

이는 제한된 정적 계약 검사에 대한 회귀 근거다. Python 프로그램 전체의 실행 의미, 실제 PR 정확도, 실제 배포 API, 자연어 문서의 진실성까지 검증한 결과는 아니다. 기존 경계 평가 1/8도 개선됐다고 주장하지 않는다.

## 2. 검토 방법과 범위

- 순수 정책 엔진, 계약 추출·비교, 세 값 집계, 변경 강도 필터, 공통 검사 서비스와 결과 출력 연결을 읽었다.
- 변경 전 결과를 `before-seed1.json`부터 `before-seed8.json`, `threshold-before.json`에 별도로 보존했다. 이전 평가 입력과 결과를 덮어쓰지 않았다.
- 첫 입력 9개는 오류 반례 7개와 정상 통제 2개다. 실제 Git 형식의 필드 삭제 반례를 별도로 추가하여 최종 입력은 10개다.
- `gate.on_unverified: warn`을 사용해 확인 불가와 확인된 위반을 구분했다. 차단 기본값만 보고 잘못된 분석을 성공으로 계산하지 않았다.
- 실제 임시 Git 저장소에서 CLI·MCP·Desktop 서비스의 결과를 비교했다. GitHub Action은 네트워크 수집을 대체한 통제 입력으로 비교했다. 실제 GitHub PR/원격 CI 검증과는 구분한다.
- 테스트의 기대값은 고정 JSON과 진리표로 정의했다. 제품 함수가 반환한 값을 기대값으로 다시 사용하지 않았다.

## 3. 재현한 결함과 수정

| ID | 위험 | 수정 전 관측 | 원인 | 수정 후 |
|---|---|---|---|---|
| R1 | 높음 | `.fastapi`, `.pydantic` 상대 import와 조건부 `int = str`가 `pass/verified`; 해석하지 못한 데코레이터가 `pass/not-applicable` | import의 level을 무시하고 모듈 조건문 안의 이름 변경을 놓침; receiver가 없으면 데코레이터를 건너뜀 | 해당 문법을 명시적 확인 불가로 반환. 모델 필드가 기본 타입 이름을 가리는 경우도 거부 |
| R2 | 높음 | 삭제된 API 문서에 Path Item `$ref` 또는 `get: null`이 남아도 `pass/verified` | 직접 get 속성 부재를 실제 API 부재와 동일하게 취급 | Path Item 참조는 미지원으로 표시. operation의 부재와 잘못된 null을 구분 |
| R3 | 높음 | 동일한 두 API 입력이 seed 1·2·3·7에서는 `fail/verified`, 4·5·6·8에서는 `warn/unverified` | set 순서로 계약을 순회하고 첫 불일치/미지원에서 반환. 중첩 any 집계가 partial을 지움 | 항목을 모두 평가하고 안정적인 순서로 집계. 알려진 불일치와 미지원 항목을 `violated/partial`로 보존 |
| R4 | 높음 | 응답 모델 필드 한 줄을 삭제하고 문서를 갱신하지 않아도 강도 필터에서 `unmatched/pass` | 실제 diff에는 데코레이터·함수 선언이 추가/삭제되지 않아 `impl-only`로 분류 | api-schema 규칙은 완전한 전후 소스로 확인한 응답 계약 변경을 강도 필터에 반영 |

R1의 정상 범위는 직접 절대 import가 실제 프레임워크를 가리킨다는 전제다. 로컬의 동명 모듈·실행 환경의 패키지 해석까지 확인한 것이 아니다. 모듈 수준의 제어문을 보수적으로 미지원 처리하므로 무해한 조건문도 확인 불가가 될 수 있다. 이를 완전한 Python 심볼 분석으로 표현하지 않는다.

R2의 `$ref`를 직접 해결하는 새 기능은 추가하지 않았다. 미지원 참조가 삭제 확인의 근거가 되는 오류를 고쳤다. 기존의 단순 `#/components/schemas/Name` 응답 객체 참조 지원은 유지한다.

R3에서 한 문서가 모든 계약을 충족한다면 any 문서 대안은 확인된 충족으로 판정할 수 있다. 다른 불완전한 대안까지 읽어야만 성공할 수 있게 바꾸지 않았다. 반대로 불완전한 실패 결과를 단일 any 안에 넣는다고 검증 완료로 승격하지 않는다.

R4는 기존 정책의 변경 강도 조건을 제거한 수정이 아니다. 지원 범위의 응답 계약 변경은 그 자체로 `route-contract-change`의 근거가 된다. 완전한 소스를 읽지 못했거나 미지원 문법이고 독립적인 강도 근거도 없으면 조건부 의무 자체를 확인 불가로 남긴다. 모든 트리거가 이 상태일 때 문서가 없다는 사실만으로 확정 위반을 만들지 않는다.

## 4. 수정 후 판정 흐름과 불변 조건

```text
어댑터: 정책·변경 diff·완전한 전후 소스·현재 문서를 수집
  ↓
공통 검사: 정책 실행 전제 검사·문법 신호 보강·입력 기록
  ↓
규칙: 경로·ignore 판정
  ↓
api-schema + 강도 조건: 응답 계약 근거로 변경 강도 보강
  ↓
조건이 확인됐거나 확인 불가인 트리거를 보존
  ↓
계약 전후 비교 → 해당 메서드·경로의 문서 항목별 대조
  ↓
문서 내 all 집계 → 문서 대안 any 또는 의무 all 집계
  ↓
규칙 판정 + 검증 범위 → 알려진 위반 목록 + 확인 한계
  ↓
심각도·gate.on_unverified → pass/warn/fail
```

유지하는 불변 조건:

1. 미지원 입력을 빈 계약·무변경·파일 조건 충족으로 바꾸지 않는다.
2. 조건부 의무의 전제를 확인하지 못하면 확정 위반을 만들어내지 않는다.
3. 확인된 전제와 알려진 문서 불일치가 있으면 다른 계약의 확인 불가가 그 불일치를 숨기지 않는다.
4. 불완전한 검증 범위는 중첩 집계에서 verified로 바뀌지 않는다.
5. 독립 항목·파일의 순서와 해시 seed는 정책 판정과 검증 상태를 바꾸지 않는다.
6. 확인 불가 정책을 warn에서 fail로 강화해도 기초 사실과 규칙 판정은 변하지 않으며 최종 게이트가 약해지지 않는다.
7. 같은 소스·문서·정책은 공통 검사 경로를 쓰는 진입점에서 동일한 판정을 만든다. 수집 방식의 차이를 지우거나 실제 원격 검증으로 주장하지 않는다.
8. 확인된 위반, 확인 불가, 적용 대상 없음, 예외 승인은 서로 다른 상태다. 단순 pass를 전체 정확성 증명으로 사용하지 않는다.

### 세 값 논리

| all: A ∧ B | 충족 | 위반 | 확인 불가 |
|---|---|---|---|
| 충족 | 충족 | 위반 | 확인 불가 |
| 위반 | 위반 | 위반 | 위반·부분 확인 |
| 확인 불가 | 확인 불가 | 위반·부분 확인 | 확인 불가 |

| any: A ∨ B | 충족 | 위반 | 확인 불가 |
|---|---|---|---|
| 충족 | 충족 | 충족 | 충족 |
| 위반 | 충족 | 위반 | 확인 불가 |
| 확인 불가 | 충족 | 확인 불가 | 확인 불가 |

이는 판정 진리표다. verified/partial은 별도로 보존한다. 예를 들어 partial인 위반 하나만 가진 any는 위반·부분 확인이다. 완전한 충족 대안이 있으면 그 근거로 verified 충족이 가능하다.

## 6. 남은 보완 우선순위

### 1. 변경 범위를 먼저 명확히 정한 지원 확대

기존 경계 평가에는 여러 줄 route, OpenAPI YAML, router prefix/조합, 동적·별칭 환경 키 등이 남는다. 이번 엄격한 api-schema의 정적 지원과 기존 auto 정책의 일반적인 탐지 성능은 별개다. 원래 경계 평가를 api-schema 정책으로 바꾸어 점수가 개선됐다고 보고하면 안 된다.

영역 하나씩 지원 문법·전후 원문·이름/경로 조합 규칙·정상 통제를 정하고 추가해야 한다. 추천 시작점은 고정 HTTP route 조합 또는 정적 환경 키 별칭 중 하나다. 실제 사용 사례의 빈도 자료가 없으므로 우선순위는 의견이다.

### 2. 소스 계약의 부분 해석을 더 세밀하게 표현

현재 소스 모듈 하나가 미지원이면 응답 delta 전체가 확인 불가가 될 수 있다. 문서 항목별 부분 검증은 이번에 보완했지만 소스 항목별 부분 검증은 다르다. 단순히 해석한 모듈만 합치면 미지원 모듈의 중복 route·등록 순서·prefix 영향을 놓칠 수 있다.

추후 모듈·앱/라우터 단위의 계약 식별과 미확정 범위를 함께 표현한 후 부분 결과를 합쳐야 한다. 이 기능을 이미 구현했다고 주장하지 않는다.

### 3. 실행 환경·배포 계약과의 독립 검증

현재 정적 검사는 직접 절대 import와 선언 구조를 전제로 한다. 동명 로컬 패키지, 앱 실행 성공, middleware, 런타임 변경, 응답 반환값, 배포 prefix까지 증명하지 않는다. 지원 범위에 대해 통제한 실제 프레임워크의 생성 OpenAPI와 대조하는 별도 oracle을 마련하면 도움 된다. 대상 저장소의 임의 코드를 분석 과정에서 실행하는 기능으로 확장하지 않는다.

### 4. 성능과 결과 크기 측정

이번 강도 필터는 소스 계약을 확인하고 내용 평가에서 다시 비교할 수 있다. 같은 파일을 여러 규칙이 사용하면 파싱을 반복한다. 현재 실패하거나 실제 지연을 재현한 것은 아니므로 성능 결함으로 단정하지 않는다. 입력 해시·분석 모드에 묶인 검사 실행 범위 내 캐시를 도입하기 전에 큰 고정 프로젝트로 기준을 측정하는 편이 낫다. 문서별 상세 사유가 늘어난 결과 크기도 함께 측정한다.

## 7. 미검증 범위와 변경 상태

- 이번 수정의 원격 CI·세 플랫폼 설치본·오프라인 네이티브 실행은 다시 검증하지 않았다.
- 실제 GitHub API의 최신 PR 수집·레이트 제한·권한 실패는 이번 진입점 비교의 대상이 아니다.
- 실제 사용자 PR과 독립 평가자의 blind 평가를 수행하지 않았다. 작성자가 만든 반례와 회귀 수치를 운영 정확도로 일반화하지 않는다.
- 사용자 작업 중 두 문서 삭제는 수정·복구하지 않았고 자체 게이트 후보에서도 제외했다.
- 커밋·푸시는 하지 않았다. 앞선 작업과 이번 수정이 작업 트리에 함께 남아 있다.

최종 근거의 파일 해시는 [verification.json](../assessment/logical-rereview-2026-10-07/verification.json)에 기록한다. 이 문서의 HEAD는 수정본의 커밋 ID가 아니라 작업 트리의 Git 기준점이다.
