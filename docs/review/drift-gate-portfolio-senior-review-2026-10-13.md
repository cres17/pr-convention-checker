## 논리 구조를 단계별로 본 평가

### 1. 문제 정의: 좋은 출발점

문제는 “AI가 코드가 맞다고 한다”가 아니라 “코드 변경이 팀의 문서 갱신 의무를 충족했는가”다.
YAML 정책이 의무를 정하고 LLM은 보조 설명을 맡는다. 비용·가용성·비결정성을 핵심 gate와 분리했다는 점은
설명할 가치가 높다. 파일 동반 수정 확인과 문서 내용의 의미 검사를 구분하는 것도 적절하다.

아쉬운 점은 제품 범위다. 같은 저장소가 정책 엔진·desktop·프로젝트 진행 관리·LLM 구독 연결·조직 저장소·평가
플랫폼을 함께 다룬다. 실사용 근거가 아직 부족한 상태에서 기능 폭이 먼저 커졌다. 기술적으로 만들 수 있다는 것과
그 기능이 핵심 문제에 필요한지는 다른 판단이다. 포트폴리오에서는 핵심 문제와 연결되는 2~3개 흐름을 중심에 둔다.

### 2. 입력 수집: 신뢰성을 구체적으로 설계했다

`adapters/git/immutable.py`는 commit OID, 원본 tree/blob, raw diff, 정책 pin을 사용한다. 작업 트리의
attributes나 replacement ref가 원본 비교를 바꾸지 않도록 별도 bare diff 경로와 Git 환경 통제를 둔다.
`adapters/snapshot.py`와 `inspection.py`에서 캡처와 재평가의 경계를 만든 점도 좋다.

면접에서 중요한 설명은 “SHA-256이 있으니 판정이 참”이 아니라 “같은 입력이었음을 확인하고 다시 평가할 수 있다”다.
출처 무결성, 파서의 해석 정확성, 최종 논리의 일관성은 각각 다른 보장이다.

### 3. 사실 모델: 불확실성을 숨기지 않는 점이 강점

`core/models/facts.py`는 Exact/Bounded/Unknown 사실을 분리하고 `must ⊆ may`를 생성 시 검사한다.
Unknown의 상한을 빈 집합으로 두지 않는다. 증거를 못 찾았다는 사실을 변경 없음으로 바꾸지 않는 모델이다.
scope/profile/evidence를 함께 가진다는 점도 좋다.

다만 이 타입이 파서의 관찰을 자동으로 참으로 만드는 것은 아니다. 사실 생성 단계에서 잘못된 의미를 주면
타입과 이후 증명 검증기는 그 잘못된 전제를 일관되게 전달할 수 있다. 아래 compatibility 반례가 이 위험을 보여 준다.

### 4. 규칙·proof·gate: 분리는 적절하고 운영 연결은 계속 관리해야 한다

`core/evaluation/result_guard.py`는 결과를 믿고 읽는 대신 입력 context, 명제 구조, 참조, truth,
충분한 증인, 범위, 순환을 재검증한다. “검증기가 검증기의 결과를 확인한다”는 문구에 그치지 않고 재계산한다.
`core/gating/enforcement.py`는 정책 결과와 조직의 allow/review/block을 구분한다.

이 경계는 좋은 설계지만, `status`, `decision`, `verification`, `result`, `enforcement`가 공존해 변경 시 불일치 위험이 있다.
호환성을 위한 상태와 실제 논리 상태의 변환은 한곳에서 담당해야 한다. 현재 evaluator의 큰 조정 함수와
여러 projection을 만질 때 같은 뜻이 모든 출력 채널에서 유지되는지 계약 시험이 중요하다.

### 5. schema 포함 관계: 현재 가장 큰 감점 지점

응답은 new ⊆ old, 요청은 old ⊆ new로 비교한다는 방향 자체는 맞다. 이전 791565f의 oneOf/allOf/default/상속
반례는 수정됐고 관련 회귀도 통과했다. 하지만 다음 세 반례는 현재 a76306f에서 다시 재현됐다.

| ID | 입력과 올바른 해석 | 현재 결과 | 중요도 |
|---|---|---|---|
| P1-a | 기존 `oneOf: [{enum:[1]}, {enum:[1.0]}]`, 새 `enum:[1]`. 1은 기존 두 분기에 동시에 맞아 거부되지만 새 schema에는 허용됨 | T / 실제 gate pass | 높음: 잘못된 확정 통과 |
| P1-b | 기존 string 응답, 새 `{type:integer, enum:[1.0]}`. 1.0은 새 계약에 허용되며 기존에는 거부됨 | T / 실제 gate pass | 높음: 잘못된 확정 통과 |
| P2 | 기존 `{enum:[{}]}`, 새 `{type:object, additionalProperties:false}`. 둘 다 빈 객체만 허용 | F / 실제 gate fail | 중간: 동등한 변경을 차단 |

원인:

- `compatibility.py:293`은 enum 동등성을 JSON 문자열로 비교한다. 1과 1.0은 다르게 직렬화된다.
- `compatibility.py:314`는 Python float이면 무조건 number로 분류한다. JSON Schema의 integral number와 다르다.
- 이 오분류 때문에 `subset`의 유한 집합 필터가 실제 가능한 값을 제거하고 빈 집합의 포함 관계를 T로 만든다.
- `compatibility.py:260`은 enum 없는 object/array를 모두 무한 집합으로 간주한다. 빈 객체만 가능한 유한 schema도 있다.

JSON Schema는 1과 1.0을 같은 정수 값으로 다룬다.
[공식 숫자 타입 설명](https://json-schema.org/understanding-json-schema/reference/numeric).
P1은 독립 validator로 old=false/new=true를 확인했고 실제 inspection gate까지 실행했다.
P2는 두 schema의 허용 집합이 `{빈 객체}`로 같다는 구조적 이유와 validator 대조를 함께 확인했다.

수정 기준: Python 표현형과 JSON 값의 의미를 분리하고 수의 동등성·정수 판정을 통일한다. 유한성은 자료형 이름만으로
추론하지 않는다. 지원 범위에서 증명할 수 없으면 U로 두며, F를 확정하려면 유효한 반례가 있어야 한다.

### 6. 검증 전략: 시험 방법은 좋지만 생성 문법의 사각지대가 있다

`test_decision_models.py`의 독립 validator 대조, 기존 실패를 새 테스트로 고정한 방식, 원격 다중 OS 검사는 장점이다.
취소·늦은 응답·ABA·저장 충돌 등 정상 흐름만으로는 드러나지 않는 사례를 시험한 것도 좋다.

그럼에도 `random_schema`의 integer enum은 `[0,1,2]`에서만 만들어진다. 1.0, object enum 같은 이번 반례를 생성하지 않는다.
1,500쌍을 반복해도 생성 문법 밖의 오류는 찾아내지 못한다. 더 큰 반복 횟수보다 숫자 표현 동등성·유한 object/array·
조합별 경계가 독립적으로 포함되는지 확인하는 것이 우선이다.

테스트 수는 회귀 방어의 규모를 보여 주지만 실제 PR 정확도의 분모가 아니다. `scripts/acceptance_matrix.py`가
로컬 시험 통과와 외부 검증 미완료를 구분하는 것은 좋은 방식이다. A17 holdout은 외부 근거 없음으로 남아 있다.

### 7. holdout 지표: 기존 연결 결함은 고쳤지만 분모·정의 보완이 필요하다

제품 inspection 경로 재사용, frozen → packet → labels 연결, source별 분리와 신뢰구간은 장점이다.
다만 두 사례를 추가로 재현했다.

- **P3: 규칙 분모 누락.** policy에는 visible·omitted 두 규칙을 넣고 expected에는 visible만 적었다.
  omitted는 실제 위반이지만 freeze/run은 이를 거부하지 않고 rule 평가 단위를 한 개만 만들었다.
  PR gate는 fail로 남으므로 모든 지표에서 위반이 사라지는 것은 아니다. 하지만 rule별 점수의 분모에는 빠진다.
  `holdout.py:115`가 expected의 key만 순회한다. policy의 모든 규칙을 평가할 계약이면 집합 일치를 강제하고,
  의도적으로 일부만 평가한다면 전체 규칙 수·선택 수·선택 이유·제외 수를 명시해야 한다.
- **P4: false_verified 정의 누락.** 정답은 not-applicable인데 엔진은 violated/verified인 인공 입력을 넣으면
  verified coverage=1/1, false_verified=0/1이었다. precision은 0/1로 오류를 잡지만 false_verified 지표는 잡지 못한다.
  설계는 “틀린 확정 명제”를 세도록 되어 있는데 `evaluation_stats.py:68`은 satisfied↔violated 반대만 센다.
  전체 결정/label 행렬로 지표 정의를 고정해야 한다. undecidable은 곧바로 거짓과 같다고 가정하지 말고 별도 정의한다.

P4의 `source=human` 값은 API 동작 시험을 위한 합성 label이지 실제 사람 검토 자료가 아니다.
이번 반례로 실사용의 오탐률·미탐률을 주장하지 않는다.

### 8. 실행·저장·게시: 실무적인 실패 상황을 고민했다

`core/execution/lifecycle.py`는 append-only 기록을 접어 상태를 얻고 닫힌 실행의 재개와 늦은 성공을 제한한다.
결과 계산 성공과 외부 게시 성공을 구분한다. `adapters/github/publication.py`는 응답을 못 받았을 때
무조건 재전송하지 않고 같은 실행의 게시 여부를 찾는다. GitHub의 원자적 조건부 쓰기를 보장할 수 없다는 한계도 적혀 있다.

로컬 OS 잠금, 저장 버전 비교, 실행 중 초안 보호, Qt/React request ID 및 baseline 검사도 재현 가능한 실패를
바탕으로 설계했다는 근거다. 특정 framework를 사용했다는 사실보다 이런 선택을 설명하는 것이 포트폴리오에 유리하다.

### 9. 신뢰·운영 경계: 개선은 확인되지만 기업 운영 완료와는 다르다

현재 `trusted_validation.py`는 ref를 먼저 OID로 고정하고 subject 불일치를 거부한다.
새 CI trusted-engine job은 후보 Python을 import하지 않고 pin한 엔진을 설치해서 실행한다.
이전 7개 결함을 그대로 미해결이라고 평가하지 않았다.

workflow 자체는 후보가 바꿀 수 있으므로 외부 required workflow/branch rule이 필요하다. 이번에는 GitHub 조직의
그 설정을 검증하지 않았다. 로컬 조직 저장소와 cache를 기업 인증·동시 writer·운영 고가용성으로 설명해서는 안 된다.
README에도 공개 설치본은 화면 경로·파서 문제 수정 전 버전이라고 명시돼 있다. 최신 build 성공과
면접관이 다운로드하는 공개 파일의 품질은 다른 문제다.

### 10. 유지보수·전달력: 추상화보다 책임 정리가 먼저다

구조 표의 core/adapters 구분은 실제 import 방향에서도 유지된다. AST로 core의 adapter/desktop 역방향 import를
찾았을 때 없었다. 런타임의 모든 I/O를 증명한 결과는 아니며 계층 의존 점검이다.
React 이벤트는 Zod 검증을 거치고, project-progress에는 상태 전이·세션·merge/rebase 모듈이 분리돼 있다.

반면 `adapters/cli/runner.py`는 2,330줄로 argument 정의, 검사 수명주기, 조직 기능, holdout, HTML,
초기화와 추천을 함께 다룬다. `_check_body`만 192줄이다. `progress_service.py` 995줄, `App.tsx` 901줄도
서로 다른 책임이 모이는 지점이다. 줄 수 자체가 결함은 아니지만, 실제로 바뀌는 이유가 여러 개다.

권장 분리:

- CLI: parser 등록, inspect 실행 조정, bundle/run/holdout/org 명령 핸들러, 출력 처리를 분리한다.
- schema: 값 동등성·정규화·포함 판정·OpenAPI 상속을 각각 명확한 계약으로 나눈다.
- 결과 모델: truth/verification/gate/enforcement 변환을 한곳으로 모으고 출력은 그 결과를 읽는다.
- UI: App의 repository/session 제어와 검사/LLM/현황 흐름을 나눠 읽을 수 있게 한다.
- Python 타입 검사: CI의 `mypy ... || true`를 한 번에 엄격화하기보다 core의 새 모델부터 검사 대상으로 강제한다.

새 플러그인 프레임워크나 더 많은 추상 기반 클래스를 추가할 근거는 보이지 않는다. 먼저 현재 책임 집중과 의미 중복을 줄인다.

문서는 docs 하위 Markdown만 106개다. 기록 보존은 장점이지만 docs/README의 '최신' 링크는 10월 1일 기록이고,
대표 README의 결과 표 역시 과거 수치를 전면에 둔다. 현재 commit·현재 보장·미지원·대표 재현 링크를 한 장으로
정리하고 실험 이력은 아래로 내리는 편이 첫 검토자의 이해에 도움이 된다. 과거 문서와 수치를 덮어쓰지는 않는다.

## 시니어 면접관에게 남을 인상

“정책 엔진과 실패 복구를 설계하고, AI가 제시한 결과를 반례로 검증해 고친 경험은 흥미롭다.
다만 기능 확장이 정확성·실사용 증거보다 앞서간 흔적이 있다. 어떤 범위를 보장하는지 스스로 제한하고
그 결정을 설명할 수 있는지 확인하고 싶다.”

확인할 질문:

1. `pass`, `verified`, `allow`는 왜 다르며 지원하지 않는 문법은 어디에서 U가 되는가?
2. 해시가 일치해도 왜 판정이 틀릴 수 있는가? 이번 숫자 반례를 직접 설명할 수 있는가?
3. 테스트가 통과하는데 새 반례가 나온 원인은 무엇이고 생성기/평가셋을 어떻게 바꿀 것인가?
4. 고정 엔진이 있어도 workflow 보호가 필요한 이유는 무엇인가?
5. 게시 응답 유실을 단순 retry하지 않는 이유와 재확인의 한계는 무엇인가?
6. AI의 제안 중 무엇을 직접 반박했고, 그 판단 근거·본인 작성 범위는 무엇인가?
7. 조직 저장소·진행 관리 등 부가 기능을 제외해도 핵심 사용자 문제를 해결할 수 있는가?

답변을 직접 코드·증거로 연결할 수 있다면 프로젝트의 깊이가 전달된다. 설명하지 못한 부분을 기능 이름이나
테스트 수로 대신하면 오히려 과도하게 확장된 AI 생성 결과물처럼 보일 수 있다. 코드만으로 작성자의 이해도를 단정하지 않는다.

## 포트폴리오 제출 전 우선순위

1. **P1/P2를 고친다.** 논리 모델을 더 크게 만들기보다 지원한다고 선언한 의미의 잘못된 확정을 먼저 막는다.
2. **P3/P4를 고친 후 작은 외부 PR 파일럿을 한다.** 예를 들어 여러 저장소의 20~30개 실제 PR을 개발 사례와
   분리하고 검토자 판단과 비교한다. 이 규모도 일반 정확도 보장의 근거는 아니며 운영 가능성을 점검하는 시작이다.
3. **현재 검증한 버전으로 다운로드 경험을 맞춘다.** 공개 릴리스 갱신 또는 최신 검증 산출물의 명확한 안내가 필요하다.
4. **핵심 책임을 분리한다.** 특히 CLI 조정과 schema 의미론을 우선한다. 전체를 새 추상화로 다시 쓰지는 않는다.
5. **첫 화면을 축약한다.** 문제 1개, 입력/실패/수정 예시 1개, 핵심 구조, 직접 반박한 AI 주장, 현재 결과와 한계를 보여 준다.

제출 시 중심 문장은 “AI의 코드 검증 주장을 정책·근거·재현 가능한 반례로 확인하는 개발 도구”가 적절하다.
“모든 코드와 문서의 의미를 검증한다”, “엔터프라이즈 수준 정확성을 달성했다”, “테스트 수만큼 품질이 입증됐다”는
표현은 현재 근거로 지지하지 못한다. 실사용 시간 절감이나 독립 정확도 수치를 만들지 않는다.
