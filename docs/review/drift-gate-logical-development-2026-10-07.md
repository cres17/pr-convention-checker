# Drift Gate 제품 로직 발전안

작성일: 2026-10-07  
대상: `ver2`, HEAD `d262ec2`에 다자 검토 후 수정 사항이 적용된 **미커밋 작업 트리**  
목적: 자기소개서가 아닌 Drift Gate 제품의 판정 의미·정책 언어·분석 구조를 발전시키기 위한 제안

## 1. 결론

다음 개발의 중심은 **문서 파일의 변경 여부와 실제 계약 반영 여부를 구분하고, 지원하는 계약 하나를 변경 전후로 정확히 비교하는 것**이다.

우선 정책의 의미가 작성 순서에 따라 달라지는 문제를 수정한다. 이어서 내용 검사의 한계를 명시적으로 표현하고, 한 종류의 계약 의미 분석을 완성한다. 검사 결과와 실행 경로의 공통화는 이 의미가 CLI·MCP·Desktop·Action에서 동일하게 유지되도록 한다.

권고 순서:

1. 정책 의미의 모호성 제거
2. 내용 검사 불가 시 파일 변경 검사로 낮아지는 동작 정리
3. 한 종류의 계약을 변경 전후로 비교하는 분석 구현
4. 정책 판정과 검증 상태 분리
5. 공통 검사 서비스와 진입점 간 일치 검증

이 문서는 설계 제안이다. 아래 두 현상은 앞선 검토에서 직접 재현했으며 나머지는 코드 구조에 근거한 개선안이다. 문서 작성 과정에서 운영 코드를 추가 수정하지 않았다.

## 2. 현재 확인한 두 현상

### 2.1 응답 모델 참조 변경과 무관한 문서 수정이 함께 통과한다

사용한 정책 조건:

- 트리거: `src/**`
- 최소 변경 강도: `impl-only`
- 요구 문서: `docs/api/**`
- 내용 검사: `auto`
- 심각도: `blocker`

입력 변경:

```diff
--- src/api.py
-@app.get('/orders', response_model=FullOrder)
+@app.get('/orders', response_model=BriefOrder)
```

```diff
--- docs/api/other.md
-Old unrelated note
+New unrelated note
```

관측 결과는 `pass`였고 충족한 그룹의 내용 근거 문자열은 비어 있었다.

현재 `content_requirement()`는 지원하는 HTTP 메서드·경로의 추가/삭제를 찾지 못한 `auto` 검사에서 `None`을 반환한다. 평가기는 이를 파일 변경 조건으로 처리한다. 이 사례는 실제 HTTP 서버 실행이 아닌 엔진 수준의 합성 입력이다.

**해석에 주의할 점:** 현재 문서화된 `auto` 계약은 이런 파일 조건 대체를 허용한다. 따라서 현상을 곧바로 기존 명세 위반이라고 단정하지 않는다. 다만 사용자가 내용 검증을 기대하는 제품으로 발전시키려면 의미가 부족하다. 또한 모델 이름이 바뀌었다는 사실만으로 실제 응답 구조가 달라졌거나 호환성이 깨졌다고 단정할 수 없다. 그것을 구별할 분석이 필요하다.

관련 코드:

- [내용 검사와 자동 대체](../../drift_gate/core/evaluation/contracts.py)
- [그룹 내용 검사·파일 검사 선택](../../drift_gate/core/evaluation/evaluator.py)

### 2.2 중복 그룹 이름의 작성 순서에 따라 결과가 달라진다

같은 규칙 안에 다음 두 그룹을 정의하고, 교차 조건이 `docs`를 참조하도록 했다.

```yaml
groups:
  - name: docs
    all_changed: [docs/a.md]
    required: false
  - name: docs
    all_changed: [src/**]
    required: false
cross_file:
  - name: sync
    when_any_changed: [src/**]
    require_groups: [docs]
```

`src/api.py`만 수정한 동일 입력에서 위 순서는 `pass`, 그룹 순서를 뒤집으면 `fail`이었다. 정책 로더는 두 경우를 모두 허용했다.

원인은 `_evaluate_cross_file_relations()`가 그룹 이름을 키로 사전을 만들면서 마지막 그룹으로 앞의 그룹을 덮어쓰는 것이다. 이는 사용자가 정책 순서만 정리해도 판정이 달라지는 문제다.

관련 코드:

- [정책 검증](../../drift_gate/core/policy/validator.py)
- [교차 조건의 그룹 이름 조회](../../drift_gate/core/evaluation/evaluator.py)

## 3. 발전안 A — 정책 언어의 의미를 명확하게 정의

### 변경 방향

- 규칙 내부의 그룹 이름 중복을 오류로 처리한다.
- 교차 조건 이름의 중복과 참조 관계도 검증한다.
- 그룹의 `any_changed`와 `all_changed`를 동시에 지정하는 경우를 명확하게 정의한다. 우선순위에 암묵적으로 의존하기보다 둘 중 하나만 허용하는 설계를 우선 검토한다.
- 의미에 영향을 주지 않아야 하는 배열 순서 변경으로 판정이 달라지지 않게 한다.
- 작성한 정책이 어떤 파일과 요구 조건에 적용되는지 미리 확인할 수 있게 한다.

기존 중복 규칙 ID 검증과 미정의 그룹 참조 검증은 이미 있다. 이를 새 기능으로 다시 계산하지 않는다.

### 완료 기준

| 사례 | 기대 결과 |
|---|---|
| 그룹 이름 중복 | 실행 전 정책 오류 |
| 존재하지 않는 그룹 참조 | 실행 전 정책 오류 유지 |
| 허용하지 않는 any/all 동시 지정 | 명확한 정책 오류와 수정 안내 |
| 독립 그룹·규칙의 순서 변경 | 판정 의미 유지 |
| 의도적으로 의무를 강화한 정책 | 정상 로드 후 강화된 판정 |

기존 정책이 새 검증에서 거부될 수 있으므로 호환성 변경과 이전 방법을 함께 안내해야 한다. 경로 패턴의 일반적인 포함 관계는 복잡하므로 불완전한 추정을 완전한 논리 검증으로 표시하지 않는다.

## 4. 발전안 B — 내용 검사 불가와 파일 조건 충족을 구분

### 변경 방향

현재 `content_requirement()`의 `None` 또는 `(bool, 설명)` 반환만으로는 다음 상태를 충분히 구분하기 어렵다.

1. 사용자가 파일 변경 여부만 요구함
2. 내용 검사에 필요한 입력을 읽지 못함
3. 지원하지 않는 계약 변경임
4. 내용을 검사했고 충족함
5. 내용을 검사했고 위반함

이 상태를 명시적인 결과로 반환하도록 한다. 내용 검사를 요구한 정책에서는 분석이 불가능하다는 이유로 파일 변경 조건만 충족했다고 결론 내리지 않는다.

`paths`는 기존 파일 조건을 유지한다. 현재의 `auto` 동작을 즉시 모두 바꿀지, 엄격한 모드를 추가하고 단계적으로 이전할지는 호환성 결정이 필요하다. 현재 지원 모드인 `api-routes`와 `env-keys`를 활용하되, 지원하지 않는 응답 스키마 검사를 이미 제공한다고 표시하지 않는다.

### 완료 기준

- 무관한 문서 수정이 지원하지 않는 내용 검사에 대한 검증 완료 근거가 되지 않는다.
- 명시적인 파일 조건은 기존 정상 동작을 유지한다.
- 입력 누락, 미지원 문법, 실제 내용 불일치를 구별해서 출력한다.
- 확인 불가를 경고 또는 차단으로 처리하는 정책 선택과 이유가 결과에 남는다.
- 경고를 차단으로 강화해도 이를 탐지 정확도 향상이라고 집계하지 않는다.

## 5. 발전안 C — 파일에서 계약 항목으로 분석 단위 확장

### 목표

변경 전후의 계약을 구조화하여 무엇이 바뀌었는지와 필요한 근거를 연결한다.

```text
고정된 변경 전·후 입력
  → 지원 범위 내 계약 추출
  → 계약 항목 대응
  → 추가·삭제·변경 분류
  → 필요한 문서·검증 근거 결정
  → 근거 충족 여부와 분석 한계 출력
```

예시 계약 항목:

| 영역 | 항목 | 판단할 변경 |
|---|---|---|
| HTTP API | 메서드·경로·요청/응답 필드 | 필수 입력 추가, 응답 필드 삭제, 타입 변경 |
| 환경설정 | 키·기본값·필수 여부 | 기본값 제거, 새 필수 키 추가 |
| 공개 함수 | 이름·인자·기본값·반환 형태 | 기존 호출자가 사용할 수 있는지 |

첫 구현은 **한 프레임워크의 정적 HTTP 계약** 또는 **정적 환경변수 계약**으로 좁힌다. 예를 들어 직접 선언된 FastAPI 경로와 한정된 모델 표현을 지원하고, 동적 라우팅·상속·별칭 등 해석하지 못하는 부분은 명시한다. 여러 언어의 문법 파서를 불러올 수 있다는 사실과 해당 생태계의 계약 의미를 이해한다는 사실을 구분한다.

문서 근거도 계약 항목과 연결한다. 특정 API 변경을 다른 API의 문서 수정으로 충족시키지 않도록 한다. 가능하면 구조화된 OpenAPI 등에서 검증 가능한 필드부터 시작한다. 자연어 문서 전체의 진실성을 자동 보장하는 목표로 넓히지 않는다.

### 완료 기준

- URL이 같아도 지원하는 요청·응답 구조 변경을 식별한다.
- 모델 이름만 바뀌고 실제 계약이 같으면 불필요한 호환성 위반으로 판정하지 않는다.
- 문서 파일이 변경됐어도 해당 계약 항목이 반영되지 않으면 충족으로 인정하지 않는다.
- 이미 계약 내용이 문서에 반영돼 있는 경우와 새로 문서를 갱신해야 하는 경우를 정책에 따라 구분한다.
- 지원하지 않는 구조는 빈 변경으로 오인하지 않는다.

## 6. 발전안 D — 정책 판정과 검증 상태를 분리

제안하는 결과 모델은 두 축을 가진다. 아래 이름은 설계 예시이며 현재 구현된 스키마가 아니다.

| 축 | 예시 값 | 의미 |
|---|---|---|
| 정책 판정 | 충족 / 위반 / 예외 승인 / 미결정 | 요구한 의무에 대한 결론 |
| 검증 상태 | 완료 / 부분 확인 / 확인 불가 / 적용 대상 없음 | 결론을 내릴 수 있었던 범위 |

집계 원칙:

- 확인된 위반이 하나 있고 다른 항목은 확인 불가라면 위반을 숨기지 않는다. 동시에 전체 검증이 완료됐다고 표시하지 않는다.
- 적용 대상이 없다는 사실을 검증 완료로 집계하지 않는다.
- 예외 승인과 일반 충족을 별도 집계한다.
- 파일명·경로 패턴의 구체성은 분석 정확도의 확률로 표시하지 않는다.

현재 `confidence`는 경로 패턴·변경 유형·rename 여부 등을 사용한다. 이 값을 유지한다면 무엇의 신뢰도를 의미하는지 이름과 설명을 명확하게 해야 한다. 분석 방식·입력 완전성·계약 근거와 구분하는 편이 좋다.

현재의 `pass/warn/fail`과 종료 코드는 외부 연동 계약이므로 새 모델을 내부에 먼저 도입하고 호환 매핑을 정의한다. 출력 스키마 변경에는 버전과 이전 안내가 필요하다.

관련 코드: [신뢰도 계산과 규칙 판정](../../drift_gate/core/evaluation/evaluator.py), [게이트 집계](../../drift_gate/core/gating/gate.py).

## 7. 발전안 E — 공통 검사 서비스를 통한 실행 경로 일치

현재 공통화된 빈 정책 검증을 기반으로, 검사 준비·실행·결과 생성의 공통 계약을 확장한다.

```text
CLI / MCP / Desktop / Action
          ↓
각 어댑터가 외부 입력 수집
          ↓
공통 검사 입력 검증·정규화
          ↓
분석 → 순수 정책 엔진 → 근거가 포함된 실행 결과
          ↓
각 어댑터가 화면·JSON·종료 코드로 표현
```

공통 결과에는 정책 식별값, 비교 방식·기준, 입력 식별값, 생략 범위, 분석 상태를 포함한다. core에 파일·네트워크 I/O를 넣지 않는다. GitHub와 로컬 Git의 입력 수집 차이를 무조건 같은 구현으로 합치지도 않는다.

### 완료 기준

- 동등한 변경과 정책을 전달하면 진입점별 판정·검사 범위가 일치한다.
- 입력 오류와 규칙 위반의 의미가 모든 진입점에서 유지된다.
- compact 응답이나 화면 요약에서도 결과를 해석하는 데 필요한 생략 정보가 유지된다.
- CLI 작업 트리 비교와 PR 비교처럼 의도적으로 다른 입력 범위는 차이를 명시한다.
- 진입점 하나만 수정해 다른 경로의 계약이 뒤처지는 경우를 교차 테스트가 탐지한다.

## 8. 구현 단계와 평가 원칙

| 단계 | 작업 | 우선 이유 |
|---|---|---|
| 1 | 중복 그룹과 모호한 정책 구성 거부 | 정책 의미의 결정성을 먼저 확보 |
| 2 | 내용 검사 결과를 명시적 상태로 변경 | 분석 실패가 약한 성공으로 바뀌는 해석 방지 |
| 3 | 한 종류의 계약 추출·비교·근거 연결 | 제품의 실제 탐지 가치를 높임 |
| 4 | 결과 집계·표시·연동 스키마 정리 | 사용자와 자동화가 같은 의미로 결과를 소비 |
| 5 | 공통 검사 서비스·진입점 교차 검증 | 같은 문제가 어댑터별로 재발하는 것을 방지 |

평가에서는 기존 고정 입력을 유지하고 새 반례와 정상 대조군을 별도 추가한다. 정책 오류 거부율, 지원 범위의 오탐·미탐, 확인 불가 비율을 구분한다. 지원 범위를 줄여 얻은 점수나 확인 불가를 모두 차단해서 얻은 수치를 정확도 향상으로 설명하지 않는다.

이번 문서의 두 재현은 개발 우선순위를 정하는 사례다. 실제 PR에서의 발생 빈도·전체 정확도·사용성 개선량은 아직 측정하지 않았다. 위 설계 전체가 구현됐거나 검증됐다는 뜻도 아니다.
