# 보완 계획 재검증

2026-10-06, 운영 코드 `ae0028d5edd95d5dd4819939a5801cb028639a6b` 기준.

**기존 계획의 문제 선정과 우선순위는 대체로 타당하지만, 그대로 구현하면 범위가 커지거나 새 누락을 만들 수 있어 수정했다.** 운영 코드는 수정하지 않았다. 이전 44조건·외부 12주장 결과는 재실행 수치로 승계하지 않고 보존했다. 이번에는 계획의 전제를 겨냥한 추가 13조건을 실행하고 관련 기존 테스트 161개를 확인했다.

## 재검증으로 바꾼 결정

| 항목 | 기존 계획의 부족한 점 | 확인 근거 | 수정된 결정 |
|---|---|---|---|
| 주석·문자열 | 문자열 속 예시를 코드 변경으로 승격하지 않는다는 문구가 문자열 값 변경도 제외할 수 있음 | `message="old" → "new"`는 현재 impl-only; 같은 `# release`가 완전한 원문에서는 COMMENT 또는 STRING | 문자열 내용의 선언 오탐과 값 변경을 분리. 문맥 불명은 제외하지 않음 |
| 주석 구현 의존성 | diff 조각에 렉서를 쓰면 문맥 문제가 해결된다는 전제, C 계열 렉서까지 한꺼번에 구현 | ChangedFile은 patch만 제공; analyzer는 추가/삭제 줄을 각각 잘라 분석 | 먼저 보수적 판별, 이후 제한된 원문·줄 좌표 제공. 전체 AST 의미 분석 확대와 분리 |
| docs/test 생략 | rename만 고치면 범위 문제가 해결되는 것처럼 보임 | 해당 경로를 명시한 정책도 engine은 PASS·skip, evaluator는 위반 1개(각 1조건) | 명시 규칙 우선. 적용 규칙이 없을 때만 docs/test 생략 |
| 경로 집합 공유 | 이전/현재 경로를 모든 판정에 똑같이 쓸 위험 | trigger와 require는 서로 다른 의미. 기존 require는 현재 경로 기반 | trigger/ignore는 양쪽, 문서 충족은 실제 현재 경로. 공유 유틸에도 역할을 명시 |
| 정책 스키마 | 타입 검사만으로 중복·오타를 막지 못함 | 중복 `rules`, `rulse` 오타, 중복 `required:false`는 PASS. 음수/boolean 임계값은 위반 0개인데 FAIL | 중복 키, 알 수 없는 키, bool/int 구분, 양의 임계값, 자원 한도 포함 |
| 저장소 루트 | 모든 모드에서 Git 루트를 먼저 요구하면 원격 PR 모드가 깨짐 | `_collect_inputs`는 원격 API 분기 후에만 GitAdapter를 생성 | 로컬/원격 입력 문맥 분리. 정책 한 번 로드, 같은 snapshot의 자료 사용 |
| 신뢰 실행기 | main 실행기 사용에 초기 도입·후보 import 차단·필수 검사 발행 통제가 빠짐 | 로컬 origin/main에는 실행기/자체 정책 파일 없음. 후보 소스 설치형 CI 확인 | 초기 신뢰 SHA 확정, 분리 실행, 외부 필수 검사 설정을 별도 완료 조건으로 둠 |
| 운영 목록 | 임의 위치의 신규 운영 파일을 탐지한다는 보장 | `new-runtime/worker.py`, UI `.js`는 inventory에 안 들어감. core `.py`는 들어감 | 선언 범위 내 보장으로 제한. 범위 밖 코드 후보는 경고/검토 대상으로 노출 |

이 중 경로 충족의 반대 방향, 실행 중 정책 교체, workflow 삭제 우회는 이번에 공격 실험한 결과가 아니다. 코드를 읽고 계획에 필요한 예방 조건으로 추가했다. 신뢰된 실행기를 분리하는 것만으로 GitHub의 필수 검사 설정까지 완료되지는 않는다.

## 추가 실행 13조건

1. YAML 중복 루트 rules → PASS.
2. 루트 `rulse` 오타 → PASS.
3. 그룹의 중복 required(마지막 false) → PASS.
4. 음수 임계값 → 위반 0개인데 FAIL.
5. boolean false 임계값 → 위반 0개인데 FAIL.
6. 명시적 문서 규칙 → engine 생략, evaluator 위반.
7. 명시적 테스트 규칙 → engine 생략, evaluator 위반.
8. 런타임 문자열 값 변경 → impl-only(정상 대조).
9. 동일 줄의 COMMENT/STRING 문맥 구분 → 전체 원문 토큰은 다름.
10. 새 최상위 Python 경로 → inventory 제외.
11. 기존 core 경로 → inventory 포함(정상 대조).
12. UI JavaScript 경로 → inventory 제외.
13. 원격 PR 입력 분기가 로컬 Git 생성보다 먼저 있음 → 소스 순서 확인.

이것은 현재 동작을 확인하는 재현 assertion이다. 13개가 실행됐다는 사실은 결함을 수정했다거나 13개 결함이 있다는 의미가 아니다. 13번은 실제 GitHub 네트워크 검사가 아닌 코드 순서 검사다. core/loader/tokenize 직접 호출 중심이며 UI·설치본 검사가 아니다.

## 변경된 실행 순서

0. 입력 모드·정책 출처·출력 호환 계약을 먼저 고정하고, 신뢰 기준 초기 도입 조건을 기록한다.
1. 정책 탐색·스키마·오류 산출물을 수정한다. CLI 오타를 PASS로 만드는 경로를 먼저 닫는다.
2. 보수적 주석 판별과 rename/명시 규칙 생략을 수정한 뒤, 원문 문맥 기반 토큰 판별을 추가한다.
3. 선언된 운영 범위 누락을 막고 신뢰 실행기를 분리한다. 외부 보호 설정은 별도 운영 완료 상태로 기록한다.
4. 비교 모드·출처·skip 표시를 정리한다. 최소 run ID는 1단계부터 있어야 한다.
5. self-audit의 주장 수준과 MCP 계약·언어 지원 표시를 개선한다.
6. 전체 파일 AST를 이용한 의미 분석은 독립 실험으로 검증한 뒤 채택한다.

지금 시작할 수 있는 범위는 0~2의 로컬 운영 수정이다. 전체 계획을 한 번에 구현하거나 C 계열 렉서·새 근거 관리 UI까지 확대할 필요는 없다. 보수적인 경고 증가 가능성은 별도로 측정하고, 기준 테스트 기대값을 결과에 맞춰 조용히 변경하지 않는다.
