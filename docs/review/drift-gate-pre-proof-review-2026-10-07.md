## 재현된 문제

### R1. 변경된 소스에 이전 계획을 재사용하면 잘못 통과한다 — 중간

- 위치: `drift_gate/core/evaluation/obligations.py:137–155`, `evaluate_contract_plan`.
- 입력: `src/api.py`의 before/after가 모두 `GET /old`인 상태로 계획을 만든다. 이후 같은 경로의 after만 `GET /new`로 바꾸고, 문서는 여전히 `GET /old`인 상태로 이전 계획을 평가한다.
- 실제: 이전 계획을 재사용하면 `truth=T`, `complete_within_selection=true`다. 새 소스로 계획부터 다시 만들면 `truth=F`다.
- 원인: 평가 함수는 파일 경로 집합을 확인하지만 계획이 분석한 소스 내용과 현재 입력이 같은지 확인하지 않는다. 이전 계획의 적용 대상 아님 판단을 그대로 사용해 새 의무를 건너뛴다.
- 영향 범위: 계획과 평가를 한 번에 생성하는 정상 `inspect_contract_plan` 호출은 대조군에서 F였다. 기존 게이트의 정상 경로가 잘못 통과한다고 재현한 것은 아니다. 분리된 내부 API의 재사용·캐시·향후 증거 생성 경계가 취약하다.
- 수정 방향: 계획에 불변 입력 식별자를 결합하고 평가 때 일치를 검증하거나, 분리 평가 API를 내부로 제한하고 계획과 평가가 동일한 불변 스냅샷만 받게 한다. 경로 일치만으로는 부족하다. 전체 서비스 신뢰 체계를 이번에 모두 구현해야 한다는 뜻은 아니다.
- 필요한 회귀: 같은 경로·다른 바이트의 이전 계획 재사용 거부, 동일 입력 재평가 허용, 정상 신규 계획의 F 유지.

### R2. 삭제된 env 문서의 남아 있는 키 관측치를 인정한다 — 중간

- 위치: `drift_gate/core/evaluation/obligations.py:98–122`, `_environment_document`와 `_document_outcome`.
- 입력: 소스 환경 키를 `OLD`에서 `NEW`로 변경한다. 문서는 `status='deleted'`, `documented_env_keys=['NEW']`, `document_input_state=''`로 전달한다.
- 실제: `truth=T`, `complete_within_selection=true`다. 같은 문서를 명시적인 `missing`으로 전달하면 F다.
- 원인: env 분기가 공통 삭제 상태 검사보다 먼저 반환한다. 따라서 모순된 삭제 상태와 잔존 관측치를 조합해도 남아 있는 키가 문서 근거가 된다.
- 영향 범위: 정상 `attach_env_documents` 어댑터는 삭제 문서를 missing과 빈 키로 정규화하며, 이 대조군도 F였다. 현재 화면의 일반 삭제 경로가 항상 오판한다는 뜻은 아니다. 새 내부 API가 모순된 관측치를 받아들이는 문제다.
- 수정 방향: 계약 종류별 분기 전에 공통 입력 상태 일관성을 검사한다. 삭제됐으나 결손 상태가 명시되지 않은 관측치는 U 또는 입력 거부, 명시적 결손 문서는 실제 의무에 따라 F로 처리한다.
- 필요한 회귀: 삭제+잔존 키, unavailable+잔존 키, 명시적 missing, 정상 존재 문서의 키 충족을 함께 검증한다.

### R3. 서로 다른 검사 범위가 같은 결과 JSON으로 직렬화된다 — 낮음

- 위치: `drift_gate/core/contracts/planner.py:308–327`, `PlanEvaluation.to_dict`.
- 입력: 계약이 없는 `value=1` → `value=2` 소스에서, API_ROUTE만 조사한 계획과 ENV_KEY만 조사한 계획을 각각 만든다. 요청과 문서 연결은 동일하다.
- 실제: discovery 결과는 서로 다르지만 최종 직렬화 결과는 완전히 같다. 둘 다 T/complete이고 활성 의무 목록은 비어 있다.
- 원인: 출력에 요청한 계약 종류와 닫힌 조사 영역이 없다. 비활성 영역은 의무나 open guard에 나타나지 않아 검사 범위가 사라진다.
- 영향 범위: 메모리의 `plan.discovery`에는 구분이 남아 있다. 현재 외부 CLI JSON이 이 내부 직렬화를 이미 사용한다는 주장은 아니다. 저장·감사·증거 검증에 이 출력을 쓰기 전에 보완해야 한다.
- 수정 방향: 요청한 계약 종류, 프로파일 버전과 조사 영역의 닫힘 상태를 결과 스키마에 명시한다. 검사한 범위가 다른 결과는 출력에서도 구별할 수 있어야 한다.
- 필요한 회귀: 비활성 계약 종류만 다른 두 계획의 직렬화 구별, 활성·비활성·열린 영역을 포함한 범위 보존.

## 검사 범위와 한계

수동 검토는 S1-a~c의 사실·발견·계획·평가 구조와 통합 경계에 집중했다. 누적 변경 중 Git/GitHub 수집, 게이트, MCP, Desktop 및 UI 표현의 관련 diff도 검토했다. 변경된 모든 줄을 수동으로 전수 검토했다고 주장하지 않는다. 누적 변경의 넓은 범위는 전체 회귀 테스트로 확인했다.

macOS arm64에서 Python 3.11.15, 오프스크린 Qt와 로컬 Express 대조군을 사용했다. 화면 번들은 임시 폴더에 생성해 기존 패키지 산출물을 덮어쓰지 않았다. 빌드는 성공했으나 500 kB 이상 청크 경고는 남는다.

이번에 확인하지 않은 범위는 원격 CI, 설치 파일 실행, Windows/Linux 실행, 실제 화면 조작, 실사용 PR 및 독립 홀드아웃 정확도다. 과거 `auto` 경계 1/8 평가는 이번에 다시 실행하지 않았다. 테스트가 모두 통과한 사실을 결함 부재나 논리적 완전성으로 해석하지 않는다.
