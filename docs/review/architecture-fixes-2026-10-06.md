## 복구 계약과 코드 구성

- 확정 기능: 최대 120개. 복구 초안: 최대 240개. 이미 초과한 초안을 읽은 뒤 명시적으로 정리할 수 있으며, 이 상한을 확정 저장의 허용량으로 사용하지 않는다.
- 자동 보관: 전체 envelope 2,000,000바이트. 백업·복구: 전체 envelope 16,000,000바이트. 내보내기에도 상한 검사를 먼저 적용하고, 같은 envelope와 고정 길이 시각을 사용해 크기 경계에서 재불러오기가 실패하지 않게 한다. 초안이 보관 상한을 넘으면 사용자에게 내보내기를 안내한다.
- `progress_limits.py`와 UI `limits.ts`에서 각 계층의 제한을 모았다. 양쪽 테스트가 같은 `tests/contracts/progress.json`을 읽어 제한값과 입력 중 소수 줄 번호의 복구 형식을 확인한다. 계약 자료는 판정 정확도 평가 샘플 폴더와 분리했다.
- `progress_context.py`가 기준 내용의 identity와 요청 검사 identity 생성을 맡는다. 표시 경로·타임스탬프는 기준 identity에서 제외한다. 저장 포맷 schema 1과 기존 파일을 유지한다.
- 프로젝트 경로 보완은 `_checkout_draft`, 보관·내보내기 envelope는 `_draft_payload`에서 공통 처리한다. 다른 프로젝트의 명시된 경로를 현재 경로로 덮어써 수락하지 않는다.
- 기능 삭제는 사용자가 확인한 뒤 초안에서만 적용한다. 확정 기준은 저장할 때 바뀐다. 취소는 항목과 근거를 유지한다.

## 보장 범위와 남은 설계

이번 baseline snapshot은 **확정 기준의 내용**을 일관되게 사용한다. 검사 도중 working tree의 모든 바이트를 고정하는 파일 snapshot이나 결과 파일의 영구 보관까지 구현한 것은 아니다. 검사 중 외부에서 코드를 변경할 때의 전체 파일 일관성은 후속 설계 범위다.

설계의 ApplicationService 전체 분리, 엄격한 모든 DTO 전환, fsync를 포함한 전원 장애 내구성, MCP 계약, 시간 의존 판정의 재설계, 정책 경로 옵션, 배포 출처·서명과 독립 정확도 평가는 이번에 완료하지 않았다. Git 출력 자체의 스트리밍 용량 제한도 후속 과제다. UTF-8로 해석할 수 없는 Git 파일명은 조용히 누락하는 대신 입력 오류로 중단한다.

Windows에서 생성할 수 없는 탭·개행·따옴표·끝 공백 이름 테스트는 해당 운영체제에서 명시적으로 skip한다. macOS에서는 전부 실행했다. 현재 빌드에는 큰 chunk 및 일부 의존성 주석 처리 경고가 남아 있으며 빌드는 성공한다. 이번 실행으로 설치본·Windows·Linux·원격 CI·실사용 정확도 향상을 주장하지 않는다.
