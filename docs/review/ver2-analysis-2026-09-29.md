# ver2 데스크톱 앱 분석 — 코드·오류·계획 준수·시각 전달

작성일: 2026-09-29 · 대상: `cres17/pr-convention-checker` `ver2` (`65afb29`) · 범위: 데스크톱 앱(`drift_gate/desktop/`, `desktop-ui/`)과 프로젝트 현황 기능

## 0. 읽는 방법

- **[재현]**: 이 분석 중 코드를 실제로 실행해 확인한 사실
- **[코드 확인]**: 소스를 읽고 확인한 사실. 실행은 하지 않음
- **[가능성]**: 코드상 발생할 수 있으나 재현하지 않은 위험
- **[제안]**: 의견. 사실이 아님

검증 환경: Linux, Python 3.11, Node 22. `pytest`는 Qt 화면 테스트 2개 파일(`test_desktop_ui.py`, `test_desktop_web.py`)을 제외하고 실행했습니다. 이 컨테이너에 `libEGL.so.1`이 없어 PySide6 WebEngine을 불러올 수 없기 때문입니다. 결과: 569개 통과, 1개 실패(`test_sensitive_html_is_escaped`, 같은 `libEGL` 로드 오류). `desktop-ui`의 `tsc --noEmit`, `vitest`(6개)는 통과했습니다. 실제 데스크톱 앱은 실행하지 않았고, 시각 평가는 저장소의 캡처(`docs/assets/cross-agent-desktop.png`, `docs/assets/project-progress.png`)와 소스 기준입니다.

## 2. 오류

### B1. 코드가 바뀐 근거가 목록·상세에서 '재확인 필요'로 표시되지 않음 — [코드 확인]

- `inspect_progress`는 항목마다 `stale_evidence`를 계산해 `report.items`에 담습니다(`progress_service.py:441-451`).
- 화면은 `report.items`를 한 번도 읽지 않습니다. 목록과 상세는 `draft.requirements`를 씁니다(`ProjectProgress.tsx:108-114, 175, 184`). `draft`는 저장된 기준에서 오며, 저장된 기준에는 `stale_evidence`가 없습니다.
- 결과: 근거 코드 파일이 바뀌면 요약 카드는 그 항목을 '확인 필요'로 셉니다. 하지만 목록 배지는 계속 '구현 확인'이고, 상세의 "코드가 바뀌었습니다" 경고(`:184`)도 나오지 않습니다. 사용자는 어느 항목의 근거가 무효가 됐는지 찾을 수 없습니다.
- 수정: `progressReport`를 받으면 `report.items`의 `stale_evidence`를 id 기준으로 목록 표시에 합칩니다. 또는 서버가 항목별 `effective_status`를 내려주고 화면은 그 값만 쓰게 합니다.

### B2. '확인 필요' 필터와 요약 카드의 기준이 다름 — [코드 확인]

- 집계는 문서 변경·근거 변경을 반영한 실효 상태를 셉니다(`progress_service.py:455-460`).
- 필터는 원래 상태 `entry.implementation_status !== "unknown"`만 봅니다(`ProjectProgress.tsx:110`).
- 결과: 카드는 "확인 필요 3개"인데 필터를 누르면 1개만 보일 수 있습니다. 계획.md 7절 3단계 완료 조건 "합계와 필터 결과가 일치"를 충족하지 못합니다.
- 수정: B1의 `effective_status` 하나를 집계·배지·필터가 같이 쓰도록 합니다.

### B3. 코드 블록 안의 체크 항목이 요구사항으로 추출되고, 진짜 제목은 사라짐 — [재현]

- `CHECKBOX`, `HEADING`, 표 파서가 펜스 코드 블록(```` ``` ````)을 건너뛰지 않습니다(`progress_service.py:189-206`).
- 재현 입력: `## 로그인` 제목과, 코드 블록 안의 `- [ ] 코드블록 안 체크`
- 결과: `[('코드블록 안 체크', 7)]`만 추출됩니다. 체크 항목이 하나라도 있으면 제목 대체 추출을 건너뛰기 때문에 실제 기능인 '로그인'은 후보에서 빠집니다.
- 영향: README나 계획 문서의 예시 코드에 체크리스트·표·제목이 들어 있는 경우가 흔합니다.
- 수정: 줄을 순회하면서 ```` ``` ````/`~~~` 펜스 안에서는 세 파서를 모두 건너뜁니다.

### B4. 여러 문서의 같은 이름 항목이 조용히 사라짐 — [재현]

- 제목에서 기호를 뺀 키로 중복을 제거합니다(`seen`, `progress_service.py:198-201`).
- 재현: `a.md`의 `- [x] 로그인`, `b.md`의 `- [ ] 로그인` → 결과 1개, 출처는 `a.md`만 남음
- 계획.md 3절 "분석할 수 없는 문장도 목록에서 조용히 버리지 않는다", 8절 "같은 목표가 README와 계획서에 중복됨 → 병합 후보 제공"과 다릅니다.
- 수정: 제거하지 말고 `duplicates: [{path, line}]`로 묶어 '병합 후보' 배지를 달고, 사용자가 병합 여부를 고르게 합니다.

### B5. 저장 오류가 어느 항목인지 알려주지 않음 — [코드 확인]

- `save_baseline`은 첫 오류에서 멈추고 항목과 무관한 문장만 돌려줍니다. 예: "각 기능의 이름과 완료 조건을 입력해 주세요.", "코드 근거의 줄 번호를 확인해 주세요."(`progress_service.py:302-367`, `394-406`)
- 항목은 최대 120개입니다. 사용자는 어느 항목의 어느 칸이 문제인지 직접 찾아야 합니다.
- 수정: 모든 항목을 검사해 `errors: [{id, field, message}]`로 돌려줍니다. 화면은 해당 행에 빨간 표시를 달고, 첫 오류 항목을 선택한 뒤 입력 칸에 포커스를 옮깁니다(7절 V3 참고).

### B6. 연속 이벤트 중 앞 이벤트가 버려질 수 있음 — [가능성]

- `App.tsx`는 `progress*` 이벤트를 `setProgressEvent(event)` 하나의 상태에 덮어쓰고, `ProjectProgress`는 `useEffect`로 마지막 값만 처리합니다.
- `saveProgress`는 `progressSaved`와 `progressReport`를 연달아 보냅니다(`web_app.py:88-90`). React 18은 React 밖에서 온 업데이트도 묶어서 렌더링할 수 있습니다. 두 메시지가 한 렌더링으로 묶이면 `progressSaved`가 처리되지 않습니다. 그러면 `draft`가 서버에서 정규화한 근거(`excerpt`, `sha256`)를 받지 못합니다.
- 수정: 이벤트를 큐(배열)로 쌓아 순서대로 소비합니다. 또는 `ProjectProgress`가 브리지 이벤트를 직접 구독하게 합니다.

### 참고: 기존 동작 중 의도와 다를 수 있는 점

- 체크 항목의 `[x]` 여부를 버립니다. 계획상 구현 근거로 쓰면 안 되는 것은 맞지만, "문서에는 완료로 표시됨" 정보를 보여주면 문서와 실제의 차이를 드러낼 수 있습니다. [제안]
- `truncated`는 `len >= 120`이면 참입니다. 정확히 120개일 때도 '잘림'으로 표시됩니다(`:242`). 영향은 작습니다.

## 5. MD 점검 기능에 추가할 수 있는 기능 [제안]

현재 구조(규칙 기반 + 사용자 확인)를 유지하면서 추가할 수 있는 순서입니다.

1. **문서 안 체크 표시와 실제 근거의 불일치 경고.** `[x]`인데 코드 근거가 없거나 근거가 오래된 항목을 '문서는 완료 표시, 근거 없음'으로 따로 보여줍니다. 계획.md 8절 첫 사례와 같은 문제입니다.
2. **문서 내부 링크·경로 검사.** 계획/README에 적힌 `` `drift_gate/desktop/service.py` `` 같은 경로와 `[링크](../x.md)`가 실제로 존재하는지 검사합니다. 이미 있는 `docs-check` 명령과 같은 계열이라 구현 비용이 낮습니다.
3. **진행 이력 비교.** 기준을 저장할 때마다 `(버전, HEAD, 상태별 개수)`를 기록하고 "지난 기준 대비 +2 구현, 1 회귀, 기준에서 1개 제외"를 표시합니다. 계획.md 5단계에 해당합니다.
4. **현황 보고서 내보내기(Markdown/JSON).** 이번에 만든 파일명 규칙을 그대로 쓰면 `{project}_{branch}_{version}_progress_{timestamp}.md`로 저장됩니다. 팀 공유나 PR 설명에 붙이기 쉽습니다.
5. **테스트 기록 연결(읽기 전용).** `pytest --junitxml`이나 vitest JSON 결과 파일을 선택하면, 테스트 이름에 요구사항 id를 적은 항목을 '자동 검증 기록'으로 연결합니다. 테스트를 앱이 직접 실행하지 않으므로 계획.md 6절 7번 원칙과 충돌하지 않습니다.
6. **리뷰 화면과 연결.** 규칙 검사에서 바뀐 파일이 현황 항목의 근거 파일과 겹치면, 리뷰 결과에 "이 변경은 '보고서 저장' 기능의 근거를 무효화합니다"라고 표시합니다.
7. **정책 파일이 없을 때 초기 설정 안내.** 지금은 오류 문장만 나옵니다(`service.py:54`). `drift-gate init --preset` 결과 미리보기와 '생성' 버튼을 제공하면 첫 사용 이탈을 줄일 수 있습니다.

## 6. 시각 전달 평가 (캡처 기준)

### 현재 잘 된 점 [사실]

- 판정(수정 필요)을 색상과 **텍스트**로 함께 표시합니다.
- 필요한 문서 조건에 실제 문장이 나옵니다. 예: "API documentation must reflect: add GET /members; remove GET /users"
- 현황 화면의 `0 / 5`처럼 분자·분모를 함께 쓰고, 기준이 없으면 '대상 없음'을 표시합니다. 계획 문서의 원칙과 일치합니다.

### 잘 안 보이는 점과 개선안

| # | 문제 [사실] | 개선안 [제안] |
|---|---|---|
| V1 | 목록 제목이 규칙 ID(`api-doc-sync`)이고, 요약 문장이 엔진의 영어 기본 문구 "required groups are missing"입니다. 무엇이 잘못됐는지가 두 번째 줄에도 없습니다 | 제목을 **"API 문서가 변경을 반영하지 않음"** 같은 문제 문장으로 바꾸고, 규칙 ID는 작은 보조 글씨로 둡니다. 규칙에 `message`가 있으면 그것을 씁니다 |
| V2 | '어떻게 고치는지'가 없습니다. 엔진의 `checklist`, `docs_update_draft`, `missing_docs_explanation`를 표시하지 않습니다 | 상세 패널을 **① 무엇이 바뀌었나(변경 요약) → ② 왜 문제인가 → ③ 고치는 방법(체크리스트) → ④ 문서 초안(복사 버튼)** 순서로 재구성합니다 |
| V3 | 필요한 문서 경로(`docs/api.md`)가 코드 글씨로만 표시되고 누를 수 없습니다 | `docs/api.md 열기` 버튼(OS 기본 편집기)과 '초안 복사'를 붙입니다. 수정 후 '이 규칙만 다시 검사'를 제공합니다 |
| V4 | 페이지마다 영어 eyebrow + 큰 제목 + 설명이 첫 화면 높이의 상당 부분을 차지해 결과가 아래로 밀립니다. 프로젝트 경로도 사이드바·경로 입력칸·상단 경로에 세 번 나옵니다 | 결과가 있으면 헤더를 한 줄로 줄이고, 경로 입력은 '비교 기준 변경' 안으로 접습니다 |
| V5 | 같은 말 '확인 필요'가 리뷰의 `warn`과 현황의 `unknown`에 동시에 쓰입니다 | 리뷰 `warn`은 '주의', 현황 `unknown`은 '근거 없음'처럼 다른 이름을 씁니다 |
| V6 | 현황의 상태 막대가 전부 회색이면 정보가 없습니다(캡처: 확인 필요 5/5). 막대의 `title`이 영어 키(`implemented: 3개`)입니다 | 전부 '근거 없음'이면 막대 대신 **"첫 기능의 코드 근거를 연결해 보세요 →"** 안내와 첫 항목 바로가기를 보여줍니다. 막대 구간에는 한국어 레이블과 개수를 표시합니다 |
| V7 | 요약 카드를 눌러도 아무 일이 없습니다(계획 5절은 필터 연결을 요구) | 카드를 `button`으로 바꾸고 누르면 해당 상태로 필터링합니다. 선택된 카드는 테두리로 표시합니다 |
| V8 | 저장 실패 시 화면 위쪽에 문장 하나만 나옵니다(B5) | 실패 항목 행에 경고 아이콘, 상세의 해당 입력칸에 빨간 테두리와 아래 설명을 붙입니다. 오류 배너에는 "3개 항목을 확인하세요 · 첫 항목으로 이동" 버튼을 둡니다 |

추가 제안:

- 리뷰 목록을 심각도(BLOCKER → MAJOR → …) 순으로 정렬하고 목록 행에 심각도를 표시합니다. `Decision.severity`는 이미 전달됩니다.
- 미추적 파일 개수를 검사 결과에 경고로 표시합니다. 예: "새 파일 2개는 git add 전이라 검사하지 않았습니다." 지금은 입력칸 옆 작은 안내 문구에만 있습니다.
- diff를 `language="text"`로 고정하지 말고 확장자로 언어를 지정합니다.

  - `branch`: 첫 커밋 전에도 구하고, 분리된 HEAD면 생략합니다.
  - 값이 비면 구분자와 함께 생략합니다. 파일명 금지 문자는 `-`로 바꾸고, Windows 예약 이름은 접두사를 붙입니다.
- `.drift-gate.yml`의 `report.filename`으로 형식을 바꿀 수 있습니다. 허용 자리표시자 밖의 값(속성 접근, 형식 지정자 포함)은 무시하고 기본 형식을 씁니다.

- `docs/desktop-app.md`에 '보고서 파일 이름' 절을 추가했습니다.
