## 1. 반영한 네 작업

| 보완점 | 이번 구현 | 완료 기준과 범위 |
|---|---|---|
| 지원 범위 확대 | 같은 파일의 정적 FastAPI/APIRouter prefix·중첩·반복 include와 여러 줄 선언 | 실제 프레임워크가 생성한 메서드·경로 및 응답 schema와 대조 |
| 소스의 부분 해석 | 경로가 확정된 응답 타입 미지원은 해당 계약에만 UnknownResponse로 보존 | 다른 경로의 알려진 위반 유지; scope가 불확실하면 전체 확인 불가 유지 |
| 독립 oracle | 테스트 전용 고정 FastAPI/Pydantic 환경의 OpenAPI 생성 | 정상 32개와 각 문서 변조 통제를 대조; 운영 검사에서 대상 코드 실행 없음 |
| 반복 분석과 결과 크기 | 검사 실행 단위의 최대 128항목 캐시, 동일 입력 전후 측정 | 입력·판정·보고서를 유지하면서 파싱과 실행 시간 감소 확인 |

남아 있던 모든 언어·동적 문법을 지원한다고 주장하지 않는다. 이전 문서의 제안대로 한 영역의 범위를 정해 확장했으며, 기존 경계 평가의 입력과 정책을 바꾸지 않았다. 과거 결과 파일도 보존했다.

## 2. 정적 router 조합

순수 `static_routers.py`가 receiver 종류·선언 위치·prefix·포함 관계를 읽고 최종 경로를 만든다. 임의 Python 코드를 실행하거나 다른 모듈을 import하지 않는다.

지원 예:

```python
app = FastAPI()
router = APIRouter(prefix="/v1")

@router.get("/orders", response_model=Order)
def orders():
    return {"id": 1}

app.include_router(router, prefix="/api")
```

대조할 경로는 `/api/v1/orders`다. router 내부에 parent/child가 있거나 하나의 router를 다른 prefix로 반복 포함하는 경우도 지원한다. 이런 조합의 공식 사용법은 [FastAPI의 다중 파일·router 안내](https://fastapi.tiangolo.com/tutorial/bigger-applications/)를 참고했고, 실제 검증은 아래 고정 버전으로 별도 수행했다.

안전한 해석 범위:

- 모듈에는 앱 하나가 있거나 standalone router 하나만 있다.
- 동일 모듈에 직접 선언된 receiver끼리만 포함한다.
- 모든 route와 receiver를 선언한 다음 include한다. 자식 조합은 부모에 포함되기 전에 끝난다.
- 앱에 연결하지 않은 router의 경로를 해당 앱에 등록된 것처럼 집계하지 않는다.
- prefix는 빈 문자열 또는 `/`로 시작하고 `/`로 끝나지 않는 정적 문자열이다.
- 중복 메서드·경로, 다중 앱, 순환, 조건부/늦은 등록, 외부 router, 동적 prefix, path converter, 추가 설정은 확인 불가다.
- 불투명한 app/router/model 메서드 호출과 외부 함수로 receiver를 넘기는 경우도 확인 불가다. 예: `app.router.routes.clear()`, `configure(app)`.
- 단일 모듈 확장은 깊이 32, 방문 256, 최종 경로 256으로 제한한다. 초과를 빈 계약이나 통과로 바꾸지 않는다.

등록 순서가 다른 임의 프로그램까지 정적 실행한 것은 아니다. 보수적으로 지원 범위를 정해 FastAPI 버전별 포함 시점 동작을 추정하지 않도록 했다.

## 3. 부분 확인의 논리

두 API가 함께 바뀌었다고 가정한다.

- `/orders`: 직접 BaseModel의 primitive 필드 변경이 확인되며 문서는 오래됐다.
- `/opaque`: 경로는 알지만 직접 필드의 `list[int]` 같은 타입을 비교하지 못한다.

이전에는 두 번째 소스 때문에 전체 delta가 확인 불가가 될 수 있었다. 이제 `/opaque`의 타입을 UnknownResponse로 남기고 `/orders`의 알려진 불일치를 유지한다. 결과는 `violated/partial`이다. 파일 순서를 바꿔도 같다. 변경 강도 조건에서도 알려진 계약 변경을 근거로 의무를 성립시킨다.

부분 확인을 허용하는 것은 직접 BaseModel의 단순 필드 선언이다. 메서드·모델 실행 코드·외부 모델·동적 경로처럼 다른 계약에도 영향을 줄 수 있는 문법을 무조건 분리하지 않는다. 소스의 routing scope를 확정하지 못하면 전체 비교를 확인 불가로 유지한다. 모듈 간 동일 메서드·경로도 추측하여 합치지 않는다.

모든 변경이 미지원 응답 형태라면 문서가 없다는 사실만으로 위반을 입증하지 않는다. 반대로 삭제 전 응답 형태가 미지원이어도 경로가 명확하게 제거됐고 문서에서도 없음을 확인하면 삭제 계약은 검증할 수 있다.

## 4. 실제 프레임워크와 대조

테스트 전용 의존성:

- FastAPI `0.115.12`
- Pydantic `2.11.5`
- 이번 실행의 Starlette `0.46.2`

고정 의존성은 `oracle` extra로 두었으며 운영 코어 의존성에는 추가하지 않았다. CI와 Desktop build의 테스트 설치·목록에도 연결했다. 이 변경의 원격 실행 결과를 확인한 것은 아니다.

직접 앱·router·중첩·반복 include 4종에 `int/str/bool/float` 및 각 기본값의 8종을 조합해 32개를 검사했다.

1. 테스트가 작성한 고정 소스로 FastAPI 앱을 만든다.
2. 실제 `app.openapi()` 결과의 메서드·경로와 정적 추출을 비교한다.
3. 생성된 응답 schema를 Drift Gate에 넣어 확인된 통과를 검사한다.
4. 생성된 문서의 필드 타입을 고의로 바꾸고 확인된 위반을 검사한다.

**32개 모두 정상 대조와 변조 통제를 통과했다.** 결과 JSON에는 각 통제 소스·프레임워크 OpenAPI·정적 경로·정상/변조 판정이 있다. 사용자 저장소의 임의 코드를 실행하는 기능을 제품에 넣지 않았다.

이는 통제 앱의 OpenAPI 생성과 비교다. 실제 HTTP 응답, 배포 prefix, middleware, 동명 로컬 패키지, 임의 런타임 변조, 모든 FastAPI 버전을 보장하지 않는다.

## 5. 캐시와 성능 측정

`evaluate`가 AnalysisSession 하나를 만들고 강도 판정·그룹 검사·교차 조건에 전달한다. Python 계약 추출과 OpenAPI JSON 파싱은 분석 모드 및 내용 SHA-256으로 재사용한다. 확인 불가 결과도 보존하며 최대 128항목을 LRU로 유지한다. 전역 상태·디스크 캐시가 없으므로 다음 검사는 새 입력을 다시 읽고 분석한다.

두 번의 검사를 이어 수행하면서 두 번째 소스를 바꾸면 새 결과가 나오는지, 예외가 빈 계약이 되지 않는지, 캐시 상한이 유지되는지를 회귀 검사했다.

### 수정 전후 동일 입력

고정 조건: 모듈 24개, 규칙 8개, 5회 반복. 입력 SHA-256이 수정 전후 같다.

| 측정 | 수정 전 | 최종 수정 후 |
|---|---:|---:|
| 중앙 실행 시간 | 141.21ms | 56.11ms |
| 전체 AST 파싱 | 1,152회 | 432회 |
| 보고서 크기 | 17,876 bytes | 17,876 bytes |
| 판정/검증 | pass/verified | pass/verified |

전체 AST 횟수에는 강도 휴리스틱의 파싱도 포함한다. 새 계약 파싱만 전체 비용인 것처럼 집계하지 않았다. 이 고정 입력에서 중앙 시간은 약 60% 감소했다.

### 더 큰 입력의 캐시 대조

고정 조건: 모듈 32개 × 응답 필드 80개, 규칙 8개, OpenAPI 114,037 bytes, 각각 3회 반복. 같은 최종 코드에서 캐시 항목 수를 0과 128로 바꿔 대조했다.

| 측정 | 캐시 없음 | 캐시 128항목 |
|---|---:|---:|
| 중앙 실행 시간 | 1.268초 | 0.514초 |
| 보고서 크기 | 22,420 bytes | 22,420 bytes |
| 보고서 전체 값 | 동일 | 동일 |

이 결과는 해당 Mac의 합성 입력 측정이다. 매우 큰 입력이 캐시 상한을 넘으면 재파싱이 생길 수 있고, 다른 기기의 처리 시간을 보장하지 않는다. 결과 크기는 감소했다고 주장하지 않는다.

## 6. 최종 검증

- Python 전체: **1,101 통과**, skip/실패 0.
- 이번 새 회귀·oracle 테스트: **61개**. 이 중 oracle 32개는 각각 정상·변조 단언을 포함한다.
- 기존 논리 진리표: 512상태·12,288순서 변형과 seed 8종 재현 통과.
- 기존 고정 평가: 21/21, FP 0·FN 0.
- 기존 일반화 평가: 지원 24/24, 경계 1/8.
- ruff E9,F, README docs-check, diff 공백 검사 통과.
- Python 3.10 문법 파서로 관련 모듈 6개를 확인했다. 3.10 런타임은 이 환경에서 실행하지 않았다.
- 자체 정책 게이트: pass, verification=unverified. 기존 auto 경로 조건은 내용 검증 완료로 바뀌지 않는다.

현재 OpenAPI YAML·외부 router 조합·동적 환경 키·별칭 getter·기존 auto 모드의 불완전 patch 의미 해석은 지원 완료가 아니다. 특히 기존 경계 평가에는 완전한 전후 소스가 없는 patch 입력과 auto 정책이 있으므로, 새 api-schema의 지원 확대를 그 점수의 개선으로 바꾸어 기록하지 않는다.

## 7. 변경 상태와 근거

운영 코드와 테스트·문서·CI 연결을 수정했고 커밋·푸시는 하지 않았다. 원격 CI·새 설치본·실제 서비스 배포는 이번 검증 대상이 아니다. 이전 두 문서에 대한 사용자 삭제 상태도 유지했다.

이전 검증 파일은 당시 작업 트리의 근거로 남겼다. 새 소스 해시와 실행 자료 해시는 [verification.json](../assessment/logical-followup-2026-10-07/verification.json)에 기록한다. Git HEAD 자체는 아직 수정본을 식별하는 커밋이 아니므로 파일 해시와 함께 확인해야 한다.
