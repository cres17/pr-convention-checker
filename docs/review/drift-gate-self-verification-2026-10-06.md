# Drift Gate로 검증한 결과물과 AI 제안 채택·거절 기록

작성일: 2026-10-06, Asia/Seoul. 검증 대상: [`ver2`의 `01e28e1`](https://github.com/cres17/pr-convention-checker/commit/01e28e1620941a539d3e9c14972201b30adafd3b).

## 1. 판단

**현재 수정은 편집 보존과 저장·검사 경계의 안정성을 개선했다. 그러나 Drift Gate의 결과를 전체 코드 품질이나 문서 내용의 정확성 보증으로 받아들여서는 안 된다.** 실제 제품으로 자기 변경을 검사한 뒤, 코드와 별도 반례를 대조했다. 그 결과 새로운 실행 오류 2건, 자기 저장소의 정책 적용 범위 공백, 기존 탐지 정확도의 한계를 확인했다.

이번 작업은 운영 코드 수정이 아닌 **검증·리뷰·재현 자료 작성**이다. 실제 미저장 사용자 초안은 조작하지 않았다. “AI 제안 거절”은 대화에 제공된 과거 제안을 현재 서비스 API로 재현한 판단이며, 사용자가 과거에 직접 수행한 실험이나 실사용 데이터 유실 경험으로 꾸미지 않는다.

주요 결론:

1. 과거 AI의 **“다른 실행이 열려 있지 않은 사본만 정리”** 제안을 자동 삭제 기준으로 채택하지 않는다. 종료된 초안에도 확정되지 않은 편집이 남아 있음을 재현했다.
2. Drift Gate의 `warn`은 타당하다. 다만 현재 정책의 트리거가 이번 운영 코드 28개 파일을 하나도 포함하지 않아 이 결과로 전체 변경을 승인할 수 없다.
3. 잘못된 Git 비교 기준에서 `review`·`self-audit`가 성공 종료한다. `check`에서 이미 고친 실패 처리 원칙을 다른 명령에도 적용해야 한다.
4. MCP의 잘못된 JSON 격리는 동작하지만, 잘못된 UTF-8 바이트는 그 경계 밖에서 서버를 종료시킨다.
5. 테스트 이름 힌트는 행동 검증 여부와 다르다. `baseline_id`의 “테스트 연결 후보”를 테스트 부재로 해석하는 것은 실제 실행 근거와 맞지 않는다.

## 2. 범위와 증거

직전 리뷰 수정 전 기준 `729a3cde70c3457b633798bb50273d815d4d2c12`부터 현재 `01e28e1620941a539d3e9c14972201b30adafd3b`까지 **103개 변경 파일**을 대상으로 했다. GitHub `ver2`도 같은 SHA를 가리키는 것을 이번에 조회했다.

- 정책 검사·제품 코드 리뷰·README 점검은 **현재 커밋을 별도 임시 checkout으로 복제**해 실행했다. 사용자의 기존 문서 삭제 2건과 이번에 생성한 검증 자료는 그 입력에 포함하지 않았다.
- 전체 변경 목록과 운영 코드 변경을 읽고 Git/CLI, MCP, 기준 저장·초안·이력, Qt 브리지, React 상태·병합·문서 보관 연결을 중심으로 검토했다.
- 제품의 `check`, `review`, `docs-check`, 기존 합성 평가 스크립트를 사용했다. 선택형 외부 LLM 호출은 비활성화했다. **Drift Gate의 결정론적 결과를 새 AI 응답이라고 부르지 않는다.**
- 이번 Python 전체 검사는 **834 passed**, React는 **122 passed / 11개 파일**, TypeScript와 Ruff `E9,F`는 통과했다. 별도 추적 실행한 테스트 1건은 이 834개에 포함된 것이며 중복 합산하지 않는다.
- 신규 관찰 실험은 기존 테스트를 약화하거나 운영 코드를 바꾸지 않고 실행했다. “반례 재현 성공”은 제품이 그 반례를 올바르게 처리했다는 뜻이 아니다.
- 설치본·원격 CI는 앞선 작업에서 동일 커밋으로 확인했다. **이번 리뷰에서는 재빌드·원격 CI 재실행·실기기 UI 조작을 하지 않았다.** 현재 기록은 [재현 안내](../assessment/self-verification-2026-10-06/README.md)에 모았다.

## 4. AI 제안을 검증한 뒤 받아들이지 않은 사례

### 사례 A — 종료된 실행의 초안을 자동 정리하자는 제안 거절

**제안 출처:** 이 대화에 사용자가 붙여 넣은 과거 AI 리뷰의 “사본 개수 상한이나 ‘다른 실행이 열려 있지 않은 사본만’ 정리하는 규칙”이라는 제안. 이번에 새로 제안받은 내용으로 바꾸어 쓰지 않는다.

**문제:** 실행 여부는 삭제해도 되는지와 다른 정보다. 실행이 종료됐어도 확정 저장하지 않은 편집이 남을 수 있다.

**실험:** 임시 Git 저장소에서 현재 운영 코드의 `extract_requirements → save_baseline → cache_draft → recovery_copy → DraftSession.close`를 호출했다. 확정 제목은 `로그인 기능`, 초안 제목은 `종료 전에 편집한 미저장 제목`으로 달리했다. 이후 제안의 선택 규칙인 `active=False`를 적용하고, 그 선택을 현재 삭제 API에 전달했다. 모든 삭제는 폐기 가능한 fixture에서만 수행했다.

| 단계 | 실제 관찰 |
|---|---|
| 실행 중 초안 | `active=True`; 삭제 시도 거부 |
| 세션 종료 후 | `active=False`; 미저장 제목 그대로 복구 가능 |
| `active=False` 사본 정리 | 삭제 후보 1개; 삭제 뒤 복구 결과 `{}` |
| 확정 기준 | 여전히 `로그인 기능`; 미저장 제목이 저장돼 있지 않음 |

**판단:** 자동 정리 기준으로는 거절한다. “종료됨”이 “저장됨/불필요함”을 뜻하지 않기 때문이다. 현재 제품의 명시적 선택 삭제와 실행 중 보호를 유지한다. 실행 중 여부는 삭제 금지 조건에 활용하고, 종료 여부만으로 삭제를 허용하지 않는다.

**현재 결함과의 구분:** 현재 제품이 이 자동 정리를 수행한다는 결과가 아니다. 이 실험은 과거 제안의 자동 선택 조건을 외부 harness에서 적용해 위험을 확인한 것이다. 현재 명시적 삭제 API가 사용자가 선택한 종료 사본을 지우는 것은 의도된 동작이다.

### 사례 B — “테스트 연결 후보”를 곧바로 “테스트 없음”으로 해석하지 않음

Drift Gate `review`가 `progress_context.py`의 `baseline_id`를 테스트 연결 후보로 제시했다. 이 결과는 LLM 의견이 아닌 함수명과 테스트명 대응 휴리스틱이다. `heuristics.py:311–370`은 새 함수명에 대응하는 `test_<함수명>` 형식이 diff에 있는지 찾는다.

실제로는 `test_recreated_same_version_baseline_rejects_old_editor_and_preserves_new_edits`가 같은 버전으로 재생성된 다른 기준을 오래된 편집이 덮어쓰지 못하는지 검증한다. 이 테스트를 별도로 실행하면서 Python 호출 이벤트를 추적하니 **`baseline_id`가 5회 호출됐고 테스트도 통과**했다.

따라서 이 한 건을 “테스트가 없는 결함”으로 분류하지 않는다. 테스트 이름을 함수명에 맞추거나 동작을 그대로 복사한 테스트를 추가할 이유도 없다. 다만 이 관찰이 나머지 30건의 오탐 여부나 `baseline_id`의 모든 경계 조건을 증명하지는 않는다.

증거: [관찰 결과](../assessment/self-verification-2026-10-06/probe-run/results.json), [테스트 실행 추적](../assessment/self-verification-2026-10-06/baseline-test-execution.json).

### 사례를 설명할 때 사용할 수 있는 사실 기반 문장

> AI 리뷰에서 종료된 실행의 초안을 정리하자는 제안을 검증 대상으로 삼았다. Drift Gate로 현재 변경을 먼저 검사하고, 임시 저장소에서 실제 초안 보관·복구·삭제 API를 실행했다. 실행을 닫은 뒤에도 미저장 편집이 남아 있었고, 종료 상태만으로 정리하면 복구 사본이 사라졌다. 그래서 자동 삭제 제안을 채택하지 않고 사용자가 선택하는 삭제와 실행 중 보호를 유지하는 방향으로 판단했다.

이는 **이번 대화에서 에이전트가 수행한 재현과 판단의 설명**이다. 사용자의 과거 직접 수행 경험으로 제출하려면 실행 자료를 확인하고 본인의 실제 역할에 맞게 서술해야 한다.

## 5. 새로 재현한 수정 과제

### R1 — P1, 자동화에 연결할 때: 검사 입력 실패가 성공 종료로 바뀜

위치: `drift_gate/adapters/cli/runner.py:1083–1097`, `1194–1224`, `1262–1274`.

존재하지 않는 `missing-review-ref`를 비교 기준으로 전달했다.

| 명령 | 결과 |
|---|---|
| `check` | 종료 2, 오류 출력 — 정상 거부 |
| `review --format json --fail-on low` | 종료 0, `No Python files to review.` |
| `self-audit --json`, 빈 체크리스트 | 종료 0, 항목·경고 모두 빈 배열 |
| 정상 `HEAD`, Python 변경 없음 | 정상 종료 0 — 유지해야 할 통제 사례 |

오류는 stderr에 경고로 남는다. 하지만 종료 코드만 보는 자동화는 성공으로 판단한다. `review --format json`이 일반 문자열을 반환하는 계약 문제도 같은 경로에 있다. 이는 core 게이트가 잘못 계산한 문제가 아니라 CLI의 입력 실패 처리 문제다.

**수정:** 변경 수집 실패는 각 명령에서 정상 빈 결과와 분리해 종료 2로 전달한다. JSON 출력에는 일관된 오류 envelope를 정한다. 보조 `_collect_patch_text`는 별도로 `git diff`를 실행하고 오류를 빈 문자열로 숨기므로, 검증한 `GitAdapter` 결과의 patch를 재사용하거나 같은 수집 경계 안으로 통합한다. 이 보조 경로의 timeout·외부 diff 설정 차이도 함께 제거한다.

**완료 조건:** 없는 ref, Git 저장소 아님, 읽기 실패·timeout은 비정상 종료하고 “지적 없음” 결과를 내지 않는다. 정상 변경 없음은 구조화된 빈 성공 결과다. `--fail-on` 설정과 무관하게 입력 오류는 실패다.

### R2 — P2, 잘못된 로컬 클라이언트 입력: UTF-8 오류가 MCP 세션 전체를 종료

위치: `drift_gate/adapters/mcp/server.py:148–160`.

새 프로세스 stdin에 `0xff + 개행` 다음 정상 `tools/list(id=7)`을 보냈다. 서버는 `line.encode('utf-8')`에서 `UnicodeEncodeError`로 종료 1이 됐고 id 7 응답은 없었다. 정상 요청만 보낸 통제와 잘못된 JSON 뒤 정상 요청을 보낸 통제는 모두 다음 요청을 처리했다.

텍스트 디코딩/재인코딩과 크기 검사가 JSON 프레임 예외 처리보다 앞에 있다. 현재 macOS Python의 surrogate 처리에서 확인했다. 다른 OS의 정확한 예외 종류까지 이번에 재현하지 않았다. 권한 상승이나 원격 노출을 입증한 실험도 아니다.

**수정:** stdin의 바이트 스트림에서 상한을 적용하고 한 줄의 나머지를 배출한 뒤, UTF-8 decode·JSON parse·dispatch를 프레임 단위 오류 경계 안에 둔다. 손상 바이트를 임의로 정상 글자로 치환해 도구 인자를 실행하지 않는다. 응답 크기도 UTF-8 바이트 기준을 유지한다.

**완료 조건:** 정상→잘못된 UTF-8→정상, 상한 전후의 다중 바이트 문자, 너무 긴 줄→정상 요청을 별도 프로세스로 시험한다. 각 잘못된 프레임을 거부한 뒤 다음 정상 요청에 답해야 한다. 기존 JSON/root/args/schema 검사는 유지한다.

### R3 — P2, 제품 자체 검증 범위: 자기 정책이 실제 운영 경로를 다루지 않음

위치: `.drift-gate.yml`, `.github/workflows/ci.yml`.

103개 변경 파일 중 정책 트리거는 workflow 1개에만 맞는다. 운영 코드 28개는 수집·문법 신호 분석 대상이어도 정책의 문서 요구는 적용받지 않는다. `ci.yml`은 테스트·린트·고정 benchmark를 실행하지만 이 실제 변경을 자기 정책으로 검사하는 단계는 없다.

**수정 방향:** 범용 예시 정책과 Drift Gate 자체 저장소 정책을 구분한다. 자체 정책은 최소한 `core/**`, `adapters/{cli,git,mcp}/**`, `desktop/progress_*`, `desktop-ui/src/features/project-progress/**`, 패키징 경로를 실제 계약 문서와 연결한다. 단순 포맷 변경까지 문서를 요구하지 않도록 변경 강도와 예외 기준을 합의한다.

정책을 기존 결과가 통과하도록 사후 조정해서는 안 된다. 문서 누락·무관 문서 수정·정상 문서 수정·테스트 전용 변경의 통제 입력을 먼저 고정하고 후보 정책을 비교한다. CI에는 PR의 실제 base SHA를 확보한 자기 검사와 검사 범위 artifact를 추가한다. baseline을 찾지 못하면 `HEAD`로 조용히 대체하지 않는다.

**완료 조건:** 각 경로의 의도된 계약 변경이 규칙을 활성화하고 관계없는 문서로 충족되지 않는다. 정책 미적용 파일을 보고서에서 확인할 수 있다. 이 범위 지표는 버그 탐지율이 아니다.

## 6. 논리적 기능 보완: 통과의 의미와 정확도

### 파일이 바뀐 것과 계약 내용이 맞는 것을 구분

현재 기본 정책으로 작은 API 변경을 실제 CLI에 넣었다. `create_session(user)`에 필수 `expires_in` 인자를 추가했다.

| 문서 상태 | 실제 gate | 평가 |
|---|---|---|
| 문서 미수정 | `fail`, `api-contract-sync` | 기본 누락 탐지는 동작 |
| 옛 API 설명을 유지하고 spec·CHANGELOG에 무관한 주석만 추가 | `pass` | 기본 경로 규칙만으로는 내용 불일치를 판별하지 않음 |
| spec·CHANGELOG에 필수 인자 변경을 명시 | `pass` | 정상 통제 |

이것은 `any_changed/all_changed`라는 현재 정책의 동작이며 모든 경로 규칙이 의미 비교를 약속한다는 뜻은 아니다. 제품 표시·설명에서 **“관련 파일 변경 확인”과 “지원하는 계약 내용 비교”의 근거 수준을 구분**해야 한다. LLM 설명을 붙이는 것만으로 결정론적 판정이 정확해지는 것도 아니다.

### 기존 고정 합성 평가를 다시 실행한 결과

| 범위 | 일치 | 잘못된 차단 FP | 놓친 위반 FN | 실행 오류 |
|---|---:|---:|---:|---:|
| 지원 사례 | 21/24 | 2 | 1 | 0 |
| 경계 사례 | 1/8 | 1 | 6 | 0 |

양성은 `fail`이어야 하는 변경이다. 이 자료는 이미 공개된 32개 합성 사례의 재실행이며 새로운 holdout이나 실제 PR 정확도가 아니다. 합산 점수로 제품 전체의 정확도를 주장하지 않는다.

지원 범위에서 우선 수정할 항목:

- `A09-stale-route-retained`: 제거한 옛 route를 문서가 계속 남기는 경우 `pass`. route의 추가·제거 집합과 문서의 순변화를 함께 비교해야 한다.
- `E04-existing-token-key`: 같은 환경 키에 대한 주변 처리만 바뀌어도 `fail`. 전후 키 집합 차이를 계산해야 한다.
- `E05-env-access-in-string`: 환경 접근을 설명하는 문자열도 실행 접근으로 취급해 `fail`. AST의 실제 호출과 문자열 리터럴을 구분해야 한다.

관련 구현은 `core/evaluation/contracts.py`와 `adapters/ast/analyzer.py`다. 정규식 예외를 사례별로 추가하기 전에 전후 소스 표현과 지원 문법을 정의한다. 수정 전후 동일 32개 결과를 보존하고, 별도 입력의 이름·공백·주석·별칭·줄 나눔 변형을 검증한다.

경계 사례의 multiline route, router prefix, 동적 환경 키, 별칭, 응답 schema, chained router는 지원 확대 과제다. 한 번에 지원한다고 표시하지 않는다. 해석할 수 없는 경우를 “영향 없음”과 구분해 표시하는 것부터 시작한다.

## 7. 최근 수정에서 유지할 구조와 추가 설계

### 유지할 구현

- `save_baseline`의 저장소 잠금과 버전·내용 식별값 비교, 같은 내용 재시도의 멱등성. 순수 `baseline_id`와 저장 I/O 분리는 적절하다.
- 문서 연결 해제 시 해시·기능·근거를 보관하고 현재 집계만 제외하는 구조. 파일 부재를 원래 편집 삭제로 해결하지 않는다.
- 초안 보관·명시 삭제·실행 수명 잠금의 분리. `revision`과 실행 중 여부를 삭제 함수 안에서 검사한다.
- 저장 성공 뒤 초안 정리·이력 기록 실패를 경고로 분리하는 브리지 동작.
- 검사 시작 시 이력 목록을 고정하고 React에서 baseline/inspection 식별값이 맞는 결과만 수락하는 경계.
- UTF-8 JSON 저장에서 `newline='\n'`을 명시한 수정. 메모리 계산과 실제 파일 바이트 제한이 플랫폼마다 달라지지 않도록 유지한다.

### 다음 구조 개선은 책임의 반복을 줄이는 범위로 한정

1. **검사 입력 수집을 한 번으로 묶는다.** CLI `check/review/self-audit`가 같은 Git 수집 결과를 사용하게 한다. `source_id`, 실제 base OID, 대상 파일·patch hash, 누락 사유, 정책 hash를 묶어 결과 출처를 남긴다. 작업 트리는 검사 도중 바뀔 수 있으므로 Git HEAD만 같다고 같은 입력이라고 주장하지 않는다.
2. **실행 상태와 규칙 판정을 분리한다.** `execution_status`는 완료/입력 오류/부분 입력을, 기존 `gate`는 pass/warn/fail을 표현하도록 설계한다. 호환성을 위해 기존 gate 값을 임의로 늘리지 말고 새 필드·schema와 소비자 이관을 먼저 정의한다. 입력 오류에서는 승인 가능한 gate 결과를 생성하지 않는다.
3. **정책 적용 범위를 독립 정보로 노출한다.** 수집 파일 수, 트리거 일치 파일 수, 미지원 분석, 정책 미적용 경로를 구분한다. 규칙 5개를 순회했다는 숫자를 5개 규칙이 실제 검사했다는 의미로 표시하지 않는다.
4. **MCP transport만 따로 정리한다.** bounded byte reader·decoder·dispatcher·response encoder를 분리하고 테스트한다. 모든 함수를 클래스화하거나 네트워크 서비스로 재작성할 필요는 없다. 실행 시간 제한은 프로세스·도구 취소와 연결하는 별도 단계다.
5. **ProgressApplicationService의 조정 책임을 정의한다.** baseline 읽기, history anchor, report/context 생성, 선택적인 테스트 연결의 순서를 브리지 밖으로 모으되 저장·파일 읽기는 desktop/adapters에 둔다. core에 Qt·파일 I/O를 옮기지 않는다.
6. **Python–TS 계약을 공통 사례로 검증한다.** 현재 `contracts/progress.json`을 유효/무효 schema, 중복 ID, 보관 문서, 불완전 숫자, provenance, 상한 경계 사례로 확장한다. 양쪽이 파싱을 통과한다는 것과 같은 의미로 처리한다는 것도 별도로 확인한다.

### 권장 검증 흐름

```text
검증 대상 commit/작업 트리 고정
  → Git 입력 수집 및 실패 확인
  → 정책·문법 지원 범위 기록
  → Drift Gate 규칙 검사와 코드 리뷰 힌트
  → 지적별 원본 코드·반례·정상 통제 대조
  → 채택 / 거절 / 판단 보류 기록
  → 필요한 수정과 행동 회귀 검사
  → 같은 고정 입력 + 별도 변형 입력 비교
  → 동일 소스의 설치본·CI 검증
  → 근거 파일과 한계를 포함해 완료 보고
```

“문서가 변경됐다”, “테스트를 실행했다”, “설치본이 켜졌다”, “규칙이 통과했다”는 각 단계의 증거다. 서로 다른 단계의 완료를 대신하지 않는다.

## 8. 실행 우선순위와 완료 기준

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 1 | R1 CLI 입력 실패 통일 | 잘못된 기준/비저장소/timeout에서 모든 검사 명령이 비정상 종료; 정상 빈 변경은 JSON 성공 |
| 2 | R2 MCP 바이트 경계 | 손상 UTF-8·상한 초과 프레임 뒤 정상 요청 처리; 기존 JSON 오류 격리 유지 |
| 3 | 자체 정책·운영 문서·CI 자기 검사 | 실제 운영 경로를 의도대로 포괄; 누락·무관 문서·정상 통제를 고정해 오탐 점검 |
| 4 | 지원 사례 3건의 계약 비교 | 기존 FP 2건/FN 1건을 각각 원인별로 수정; 기존 평가·별도 변형 사례 악화 여부 공개 |
| 5 | 검사 입력·결과 출처·부분 입력 표시 | 같은 입력을 추적할 수 있고 미검사/실패가 승인으로 보이지 않음 |
| 6 | 조정 계층·공통 계약·취소 설계 | 기존 저장·복구·전환·충돌 행동을 유지하면서 중복 수집과 오류 처리 제거 |

실제 Windows/macOS 설치 사용자 흐름, keyboard-only 복구·삭제 확인, 장시간 실행, 전원 장애 내구성, 새 독립 데이터의 탐지 정확도는 이번 리뷰에서 확인하지 않았다. 남은 검증을 완료로 간주하지 않는다.
