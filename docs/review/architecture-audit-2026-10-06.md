# Drift Gate 아키텍처·기능 정합성 재검토

검토일: 2026-10-06. 기준: `ver2`, `729a3cde70c3457b633798bb50273d815d4d2c12`.

이 문서는 특정 인물이나 OpenAI·Anthropic의 공식 평가가 아니다. 제품 책임자 관점에서는 결과의 신뢰성과 사용자가 작업을 마칠 수 있는지를, 개발 도구 엔지니어 관점에서는 입력 수집·도메인 규칙·저장·비동기 응답의 계약을 평가했다. 점수나 무결함 인증 대신 재현 조건과 수정 완료 조건을 제시한다.

## 결론

최근 편집 보존 수정의 방향은 타당하다. 재추출 합치기, 버전 충돌 검사, 실행별 초안과 OS 수명 잠금, 복구 사본의 revision 검사, 명시적 복구·저장 구분은 유지해야 한다. 파서 해시 고정과 패키지 오프라인 검사도 유지할 가치가 있다.

그러나 **현재 상태를 충분히 안정적이라고 승인할 수 없다.** 더 넓은 입력 경계에서 잘못된 통과 2건과 편집 막힘 1건을 재현했다. 백업의 프로젝트 정체성, 작업 종료 응답, 저장 후 검사 스냅샷에도 계약 차이가 있다. 파일을 나누는 리팩터링보다 아래 R1–R6을 먼저 고치는 편이 효과적이다.

## 확인 범위와 증거

- 실제 코드 읽기: Git·CLI·GitHub 입력 수집, 정책 진입점과 평가 분기, 문법 분석 상태·번들 검증, Qt 작업 실행, 현황 저장·이력·초안·잠금, React reducer·요청 세션·병합·복구 UI, 구독 CLI 경계, MCP 서버, CI·빌드·릴리스 흐름.
- 이 범위의 주요 연결을 검토했다. 모든 언어별 AST 탐지 규칙과 모든 파일을 줄 단위로 검증한 감사는 아니다.
- 기존 Python 전체 **774 passed**, React 전체 **111 passed**, TypeScript, Ruff `E9,F` 통과. 이 숫자는 새로운 결함이 없다는 증거가 아니다.
- [관찰용 Python 재현 코드](../assessment/architecture-review-2026-10-06/reproduce.py), [결과](../assessment/architecture-review-2026-10-06/results.json).
- [실제 Qt worker 재현](../assessment/architecture-review-2026-10-06/bridge_audit.py), [결과](../assessment/architecture-review-2026-10-06/bridge-results.json).
- [React 관찰용 사례 3개](../assessment/architecture-review-2026-10-06/ui-audit.tsx.fixture), [실행 안내](../assessment/architecture-review-2026-10-06/README.md). jsdom 화면 1건, 수신 스키마 1건, reducer 1건이다. 실제 설치 앱 UI 결과가 아니다.
- 이번에는 운영 코드를 수정하거나 푸시하지 않았다. 재현 코드·검토·설계 문서를 작성했다. 기존 로컬 문서 삭제 2건은 이 작업에 포함하지 않았다.
- 원격 CI·설치본 6개·실기기 화면·실제 PR 정확도는 이번에 재실행하지 않았다. 이전 성공을 이번 검증 수치로 합산하지 않는다.

## 재현한 수정 사항

우선순위 P1은 잘못된 승인이나 편집 보존 경로의 막힘으로 다음 배포 전 수정, P2는 조건부 기능 오류로 바로 뒤에 수정한다. 데이터 유출이나 원격 코드 실행을 재현한 항목은 없다.

### R1 — P1: 한글 파일명이 정책 검사에서 누락될 수 있다

**위치:** `drift_gate/adapters/git/client.py:89–126`, 특히 `--name-status` 출력의 줄·탭 분리.

Git의 파일명 인용 처리를 해제하거나 해독하지 않은 채 경로로 사용한다. 임시 저장소에서 `src/routes/결제.py`를 변경하고 `src/routes/**` 변경에는 명세 수정이 필요하다는 blocker 규칙을 두었다. `core.quotePath=true`이면 경로가 따옴표와 이스케이프를 포함한 문자열로 들어오고 patch는 0바이트다. 결과는 **pass**다. 같은 변경에서 `core.quotePath=false`인 통제 실행은 **fail**이다. 규칙의 문제가 아니라 입력 경로를 다르게 읽는 문제다.

수정: `git diff --name-status -z`의 바이트 스트림을 상태에 따른 NUL 필드 수로 파싱한다. rename의 이전·새 경로를 보존하고, 경로 양끝 공백을 `.strip()`으로 제거하지 않는다. 패치 조회는 검증된 commit과 literal pathspec을 사용한다. `core.quotePath=false`만 넣으면 탭·개행·특수 경로가 여전히 남으므로 충분하지 않다. Git이 `-z`를 이 목적으로 제공함을 [공식 문서](https://git-scm.com/docs/git-diff)에서 확인했다.

완료 조건: 한글·공백·탭·개행·따옴표·rename 경로에 대해 수집 경로가 원본과 같고, 동일 변경의 판정이 quotePath 설정에 의존하지 않는다. 유효하지 않은 파일명 바이트의 처리 방침도 명시한다.

### R2 — P1: Git 수집 실패가 변경 없음·통과로 바뀐다

**위치:** `drift_gate/adapters/git/client.py:72–81`, `drift_gate/adapters/cli/runner.py:1516`.

명시한 base 조회가 실패하면 `HEAD~1`을 시도하고, 이것도 실패하면 빈 목록을 반환한다. 커밋 1개인 저장소에서 실제 변경 1개를 만들고 없는 ref를 지정하자 `no-changes`, `pass`, CLI exit **0**이 나왔다. 유효한 `HEAD`를 지정한 통제 실행은 동일 정책에서 exit **1**이다. 커밋이 더 있는 저장소에서는 지정하지 않은 `HEAD~1` 기준으로 조용히 평가할 수도 있다.

데스크톱의 `scan_repository`는 base를 사전 검증하므로 이 잘못된 ref 재현을 그대로 데스크톱에 일반화하지 않는다. GitAdapter를 직접 사용하는 CLI 등의 경로가 대상이다.

수정: 수집 결과를 `성공한 빈 diff`와 `수집 실패`로 구분한다. 명시한 base를 다른 ref로 대체하지 않는다. CLI는 입력/실행 오류를 별도 종료 코드로 알리고, MCP는 도구 오류를 반환하며, 화면에는 재시도를 안내한다. 실패를 정책 위반으로 꾸미는 대신 **평가가 완료되지 않았음**을 표현한다.

완료 조건: 잘못된 ref, Git 실패, 저장소 아님, timeout에서 절대 성공 exit/완료된 pass를 내지 않는다. 정상 빈 diff만 no-changes가 된다. unborn 저장소를 지원한다면 별도의 명시된 입력 모드로 검증한다.

### R3 — P1: 직접 추가로 121개가 되면 편집을 정상 보관할 수 없다

**위치:** `desktop-ui/src/features/project-progress/progressState.ts:246–251`, `requirement.ts:34`, `ProjectProgress.tsx:130` 부근.

추출·충돌 합치기에는 120개 제한이 있지만 직접 추가에는 제한이 없다. 실제 React 컴포넌트에 120개 기준을 주고 직접 추가→저장을 누르니 **121개 payload가 전송**됐다. 동일 구조의 121개 payload는 Python 저장·자동 보관·초안 내보내기에서 모두 거부됐다. 일반 편집 상태에는 항목 삭제·실행취소가 없고, 초안 내보내기는 충돌 상한 안내 안에만 있다.

이미 저장된 기준이나 정상 캐시가 지워지는 것은 아니다. 문제는 마지막 정상 보관 이후 편집을 이 상태에서 저장할 수 없고, 앱을 닫으면 그 편집을 잃을 수 있다는 것이다.

수정: 버튼과 reducer 모두 120개에서 추가를 거부하고 이유를 표시한다. 이미 초과한 메모리 상태의 회복을 위해 마지막 추가 취소 또는 명시적 항목 정리 경로를 둔다. 백업은 확정 기준의 제약과 분리된 구조 검증을 적용해 미완성 편집도 내보낼 수 있도록 설계한다. 기존 항목을 자동 절단하는 처리는 금지한다.

완료 조건: 119→120 성공, 120→121은 상태 불변, 빠른 두 번 클릭도 제한 준수. 예전 버전에서 온 초과 초안은 보존한 채 정리하거나 내보낼 수 있다. 집계 제외는 항목 수 감소로 취급하지 않는다.

### R4 — P2: 재클론 후 같은 폴더에서 내보낸 백업을 불러오지 못한다

**위치:** `progress_service.py:438–451`, `progress_drafts.py:266–288`.

기준 저장은 remote 정체성을 공유하지만 초안은 절대 checkout 경로로 분리한다. 기존 checkout A에서 저장한 기준을 같은 remote의 B에서 읽으면 내부 `repository`는 여전히 A다. B에서 내보내면 바깥 envelope는 B, draft 안쪽은 A가 된다. **그 파일을 B에 바로 불러와도** “초안과 원래 편집 기준의 프로젝트가 일치하지 않습니다”로 거부된다.

다른 PC로 백업을 옮기는 미지원 기능과 다르다. 지원 중인 기준 재사용 경로에서 앱 자체의 내보내기→불러오기 왕복이 깨진다.

수정: 프로젝트 정체성과 checkout 위치를 분리한다. 검증된 공유 기준을 B에서 편집할 때는 초안과 edit_base의 checkout 표현을 B로 정규화하되 원 작성 위치는 별도 출처로 보존한다. 임의 외부 파일의 경로를 무조건 치환하면 다른 프로젝트 차단이 약해지므로, 내부 정규화와 외부 이관 절차를 구분한다.

완료 조건: 같은 remote의 A→B 기준 재사용 후 B에서 생성한 백업이 B에서 복구된다. A/B 초안은 겹쳐 쓰지 않고 다른 프로젝트 파일은 계속 거부한다. edit_base와 현재 draft를 함께 검사한다.

### R5 — P2: 잘못된 테스트 결과를 읽으면 작업이 끝나도 UI가 완료를 받지 못한다

**위치:** `verification_records.py:78`, `web_app.py:71–85`.

`{"testResults":[{"name":"test","assertionResults":1}]}`을 읽으면 iterable 검사 없이 순회하다 `TypeError`가 발생한다. `ProgressTask.run`의 예외 목록에는 없으므로 **실제 Qt worker가 끝난 뒤에도 terminal event가 0개**였다. stderr에는 예외가 기록된다. 화면은 해당 요청이 끝났다는 사실을 알 수 없어 “읽는 중”을 해제할 응답이 없다. Qt 창 자체가 종료되는 것은 재현하지 않았고 그런 주장도 하지 않는다.

수정: 외부 JSON을 내부 모델로 바꾸는 지점에서 전체 구조를 검사하고 예상 오류로 변환한다. 작업 실행의 최외곽에서는 예상 밖 `Exception`도 기록하고 상관관계가 있는 terminal 실패 응답을 보낸다. 이미 저장한 작업의 후처리 실패를 저장 실패로 뒤집지 않도록 commit receipt를 별도 취급한다. `BaseException`을 통째로 삼키거나 모든 예외를 성공으로 바꾸지 않는다.

완료 조건: 잘못된 내부 타입·깊은 JSON·디코딩 오류·파일 소실·예상 밖 예외에서 요청마다 terminal 응답 1개. 오류 뒤 정상 파일을 다시 선택해 성공할 수 있다. 응답 직렬화 실패도 같은 계약에 포함한다.

### R6 — P2: 저장 응답과 뒤따르는 검사·이력이 서로 다른 기준을 가리킬 수 있다

**위치:** `web_app.py:161–175`, `progressState.ts:132–140`.

저장 잠금이 풀린 뒤 `inspect_progress`가 디스크 기준을 다시 읽는다. 그 사이 다른 앱이 저장하면 첫 작업은 v1 저장 응답에 v2 검사·이력을 붙일 수 있다. 두 함수 사이에 다른 저장을 배치한 통제 실험에서 **saved=1, report=2, history=2**가 나왔다. 이는 별도 프로세스의 무작위 경합 실험이 아니라 가능한 실행 순서를 결정적으로 삽입한 실험이다.

이전 수정 덕분에 reducer는 v2 report를 버려 잘못된 통계 표시를 막는다. 그러나 history는 받아들이며, `progressSaved`는 별도 재검사도 예약하지 않는다. 따라서 v1 편집기에서 v2 이력만 나타나고 report가 비어 있을 수 있다. 같은 토큰이라는 사실이 같은 데이터 버전을 보장하지 않는다.

수정: 저장이 반환한 불변 baseline으로 검사한다. report·history·test links·document links 모두 baseline identity/version과 inspection identity를 가진다. 불일치가 오면 관련 결과 묶음을 모두 거부하고 명시적인 refresh를 예약한다. 저장 잠금을 모든 분석이 끝날 때까지 길게 잡는 해결은 피한다.

완료 조건: 두 앱이 save/inspect/record 사이에 끼어드는 모든 순서에서 한 결과 묶음의 기준이 동일하다. 다른 기준이면 stale로 표시하거나 재검사한다. 사용자 편집을 자동으로 최신 기준으로 덮어쓰지 않는다.

## 기존 제약·추가 보완 후보

아래는 R1–R6과 동일한 우선순위의 새 결함으로 부풀리지 않는다.

| 항목 | 확인 | 판단·개선 |
|---|---|---|
| 내보내기와 불러오기 크기 차이 | 2MB 넘는 note가 있는 기준 저장·백업 생성 성공, 재불러오기 거부 재현 | 이전 문서에 명시된 제약이지만 백업 복구 계약에는 미달. 형식별 상한·편집 허용량·복구 경로를 함께 설계 |
| Python/TS 초안 검증 불일치 | edit_base.repository가 빠진 파일을 Python은 수입, TS는 recovery=null로 격리 | 원본/기준 유실 없음. 외부 형식의 중복 검증을 공통 fixture로 일치시킬 필요 |
| 즉시 초안 삭제 | 화면 버튼에서 바로 삭제 함수 호출, 확인/실행취소 없음 | 사용자의 명시 삭제이므로 무단 삭제 결함은 아님. 사본 식별 정보와 선택 개수 확인 또는 복원 가능한 삭제 도입 후보 |
| core 시간 의존 | ignore 만료 계산이 `date.today()` 호출 | 같은 입력이라도 날짜에 따라 결과 변경. evaluation context에 기준일을 포함해 재현 가능하게 만들기 |
| 사용하지 않는 public parameter | `core.engine.run(policy_path=...)` 인자가 남고 문서는 로드를 약속하지만 실제 미사용 | 현재 공식 adapter들은 policy를 전달함. API 사용자 혼동 방지를 위해 경고 후 제거하거나 명시 오류 |
| JSON 저장 내구성 | 같은 폴더 임시 파일+replace 사용, fsync 없음 | 원자적 교체와 전원 장애 내구성은 다른 보장. 전원 장애 유실은 이번에 재현하지 않음 |
| MCP schema | 도구 목록의 properties가 비어 있고 additionalProperties=true | 코딩 에이전트가 인자 계약을 discover하기 어려움. 실제 함수 인자·설명·제한을 schema로 제공 |
| 타입 검사 | TS 통과, Python CI mypy는 `|| true` | Python 전체 타입화보다 새 DTO·순수 로직부터 실패를 차단하는 검사로 전환 |
| 의존성·배포 | Actions SHA 고정, 파서 pin 확인. Python 일부 의존성 범위 설치 | 공급망 검증은 개선됨. 설치 버전 manifest, 플랫폼별 제약 파일, SBOM·서명은 별도 배포 과제 |

## 코드 구성 평가

### 유지할 부분

- `core`의 규칙 판단과 adapter의 수집을 분리한 골격. LLM의 의견이 규칙 gate를 덮어쓰지 않는 점.
- 범위 판정을 `progress_scope.py`/`status.ts`로 모으고, 재추출·충돌 합치기를 순수 함수로 두는 점.
- `ProgressRequests`와 `EditorSessions`로 방문 수명과 편집 수명을 구분한 점.
- 파일 쓰기를 원자 교체로 공통화하고, baseline 저장과 초안 삭제의 성공을 분리한 점.
- 저장소별 gate와 실행별 lease의 목적을 구분하고 persistent gate를 함부로 삭제하지 않는 점.
- frozen 앱에서 네트워크 없이 문법 분석이 가능한지를 CI에서 실제 실행하는 구조.

### 추상화가 필요한 부분

1. **전송·저장 계약:** `dict`와 `passthrough`로 동적 데이터가 여러 계층을 통과한다. 모든 곳에 같은 커다란 모델을 쓰기보다 Baseline, EditableDraft, RecoveryEnvelope, InspectionBundle의 검증 책임을 분리한다.
2. **작업 조정:** `DesktopBridge`가 파일 선택, 세션 사전, 저장·삭제·분석·이력, 이벤트 구성까지 맡는다. `ProgressApplicationService`로 사용 사례를 이동하고 Qt는 dialog/dispatch/emit만 맡긴다.
3. **파생 결과:** report에는 버전이 있지만 tests/links/history의 수락 기준은 일관되지 않다. 공통 InspectionContext를 사용한다.
4. **입력 실패:** Git 수집 오류·정책 위반·파서 성능 저하·초안 보관 실패가 서로 다른 의미임을 결과 타입으로 고정한다.
5. **제약의 중복:** 120/10/2MB를 UI, reducer, parser, import/export가 각각 해석한다. 하나의 제한 정의와 교차 언어 경계 fixture가 필요하다.

단순히 960줄짜리 service를 줄 수 기준으로 자르거나 모든 함수를 클래스·interface로 감싸지는 않는다. 여러 진입점이 공유하거나 실패 경계가 다른 기능만 분리한다. 분산 서비스·새 이벤트 버스·즉시 DB 전환은 이번 규모에서 필요성이 입증되지 않았다.
