# Drift Gate 보고서를 다시 검증한 결과

검증일: 2026-10-06. 대상 소스: `f43cada2ea177b63cb0ac4a79be37071113a5191`.

**보고서는 실제 실행 결과와 일치한다. 그러나 Drift Gate의 pass는 코드 전체가 올바르거나 계약 문서 내용이 정확하다는 인증이 아니다.** 실제 Git 변경을 사용하는 격리된 복사본에서 재실행과 반례 18조건을 확인했다. 정상 거부 조건 9개는 기대대로 작동했고, 검사 범위·정책 신뢰와 관련된 한계 5개가 드러났다. 나머지 4개는 실제 보고서의 재현·표시 일치 검사다. 이 개수는 정확도 벤치마크가 아니다.

## 무엇을 대조했는가

1. 원격 push CI와 PR CI의 `drift-gate-self-check` 산출물을 **다시 다운로드**했다. 두 실행의 `headSha`가 대상 커밋이고 실행이 성공했는지 확인했다.
2. 로컬 수정·사용자 문서 삭제·이번 재검증 문서가 들어가지 않은 임시 Git 복사본에서 대상 커밋을 체크아웃했다. 같은 기준 커밋과 같은 정책으로 검사를 재실행했다.
3. 원격 JSON 전체와 재실행 JSON을 대조했다. 실행 시간인 `runtime_seconds`만 제외했고 나머지는 모두 같았다.
4. 제품 수집기를 사용하지 않고 별도로 `git diff --name-only -z`를 실행했다. 그 파일 집합과 보고서의 matched·unmatched·ignored 합집합이 같았다.
5. 기존 HTML에 내장된 JSON과 당시 CLI JSON, 당시 소스를 이용한 재실행 JSON이 같았다. 화면의 WARN·스캔 파일 수 103도 일치했다.
6. 최신 커밋과 자체 정책으로 새 HTML을 만들었다. 내장 JSON과 화면의 PASS·스캔 파일 수가 최신 원격 push 평가와 일치했다.

## 재현한 한계와 개선 순서

### 1. 자체 검사 정책을 없애면 자체 검사도 통과한다

core에 실행 가능한 상수를 추가하고 `.drift-gate.self.yml`을 `rules: []`로 바꿨다. 계약 문서는 변경하지 않았다. 결과는 PASS, 평가 규칙 수 0, 검사 파일 수 2다. `scripts/check_self.py`가 검토 대상 작업 트리의 정책을 그대로 읽고, 빈 규칙 집합도 유효한 정책으로 받기 때문이다.

**자체 검사의 신뢰 경계 문제다.** 변경자가 규칙을 약화하면 그 규칙으로 자신의 변경을 검증한다. 다만 이는 권한 상승이나 외부 공격 성공을 재현한 것이 아니다. CI 자체도 같은 PR에서 수정할 수 있으므로 로컬 로더 하나로 완전한 보안 경계를 만들 수 없다.

우선 자체 검사에서 빈 규칙을 거부하고 필수 자체 규칙이 유지되는지 검사한다. 다음으로 변경 전 신뢰 기준의 정책과 변경 후 정책을 각각 평가하고 정책 변경을 별도 표시한다. 워크플로·정책 변경에는 저장소의 보호 규칙과 사람의 승인이 필요하다. 일반 사용자가 의도적으로 빈 정책을 쓰는 계약까지 전역으로 금지하는 변경은 별도로 판단해야 한다.

근거: `verified-run/policy-removes-all-its-own-rules.json`.

### 2. 운영 경로가 정책 밖이면 아무 문서 없이 통과한다

`drift_gate/desktop/resources.py`에 실행 가능한 상수를 추가했다. 결과는 PASS이며 그 파일이 unmatched로 보고된다. 해당 경로는 현재 자체 정책의 어느 when에도 포함되지 않는다.

이 실험은 리소스 함수 자체의 버그를 재현한 것이 아니다. 운영 코드가 바뀌어도 자체 정책의 계약 검사가 작동하지 않는 경로가 있다는 증거다. 전체 desktop·adapters·scripts 운영 경로를 목록화하고 의도한 제외를 따로 선언한다. 운영 코드 중 미분류 경로는 CI에서 실패시키거나 명확한 별도 상태로 표시하는 것이 좋다. 리뷰·평가 산출물처럼 의도적으로 unmatched인 자료까지 일괄 실패시키면 안 된다.

근거: `verified-run/uncovered-production-source.json`.

### 3. 지정 경로의 문서를 내용 없는 문장으로 바꿔도 통과한다

실제 변경분에서 필요한 계약 문서 3개를 모두 `# Reviewed`와 `All changes look good.` 두 줄로 교체했다. 결과는 PASS다. 기존 자체 정책은 이 문서에 대해 의미 검증 조건을 정의하지 않았고, 지정 경로에 변경이 생긴 것으로 요구를 충족한다.

이것은 기존 보고서의 위조나 현재 계약 문서 내용이 틀렸다는 증거가 아니다. **pass만으로 계약 문서 내용의 정확성을 입증할 수 없다는 반례다.** 코드의 계약을 독립적인 행동 테스트로 고정하고, 문서의 구체적인 상태·필드·에러 조건을 사람이 확인해야 한다. 단순 단어 수나 정해진 문구 존재 검사로 의미 정확도를 보장한다고 주장하면 안 된다.

근거: `verified-run/content-free-contract-substitution.json`.

### 4. Git에 등록하지 않은 새 파일은 검사 대상에서 빠진다

새 core 파일을 만들기만 한 경우 PASS, 스캔 0파일이다. 같은 파일을 `git add`한 뒤에는 문서 누락으로 FAIL이다. 현재 GitAdapter의 `git diff`는 Git에 등록되지 않은 파일을 수집하지 않는다.

원격 CI에서는 커밋된 파일을 검사하므로 이번 push·PR 결과가 이 이유로 누락된 것은 아니다. 로컬에서 “새로 만든 모든 파일까지 검사했다”고 표현할 경우 문제가 된다. 로컬 검사에 미등록 파일 경고를 추가하거나 검사 대상 계약을 tracked·staged 파일로 명확히 표시해야 한다. 파일 등록은 사용자에게 알리지 않고 원본 인덱스를 변경하는 방식으로 해결하지 않는다.

근거: `verified-run/untracked-new-source.json`, `verified-run/staged-new-source.json`.

### 5. 유효하지만 잘못 고른 기준 커밋은 오류로 탐지할 수 없다

깨끗한 복사본에서 `--base HEAD`를 사용하면 PASS, 스캔 0파일이다. 이것은 빈 diff에 대한 제품의 정상 동작이다. 이번 실제 CI는 push의 이전 SHA와 PR의 base SHA를 사용했고, 재실행으로 그 입력을 확인했으므로 이 실수가 있었다는 뜻은 아니다.

입력 의도를 알 수 없으므로 모든 빈 diff를 결함이나 실패로 취급하면 안 된다. 보고서에 해석된 base·head, 정책 해시, 검사 파일 수, 작업 트리 상태를 기록하고, 사용자가 기대한 변화가 있는데 0파일이라면 확인 대상으로 표시하는 것이 좋다.

근거: `verified-run/wrong-valid-base-head.json`.

## 결론과 남은 검증 범위

수정·설치본 검증 보고의 원격 결과는 재현되며 HTML 표시도 실제 JSON과 일치한다. 현재 자체 정책이 요구하는 문서 누락은 제대로 막는다. 그러나 정책의 자체 약화, 운영 경로의 미분류, 계약 문서의 의미 정확도는 PASS로 보장되지 않는다. 우선순위는 **정책 신뢰 경계 → 운영 경로 누락 → 입력·범위 표시**이며, 계약 내용의 정확성은 독립 행동 검증과 별도 리뷰가 계속 필요하다.

이번 반례는 코드 읽기와 실제 변경분에 맞춘 표적 실험이다. 독립적인 무작위 holdout이나 실제 PR 정확도 측정이 아니다. 파서 설치본 6건과 전체 Python·React 테스트를 이번에 다시 빌드·전수 실행하지는 않았다. 이 문서는 그것들의 성공을 새로 측정한 것처럼 주장하지 않는다.

이번에는 운영 코드 수정·커밋·푸시를 하지 않았으며, 재검증 프로그램·원격 원본·결과·이 문서만 새로 작성했다. 사용자의 기존 문서 삭제 2건도 건드리지 않았다.
