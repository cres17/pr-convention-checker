# E05 오류 수정 설계: 라우트 오탐·HEAD 미탐·Markdown 표

기준: [`v1`–`ver2` 통제 비교](v1-ver2-controlled-comparison-2026-09-23.md)의 12개 합성 사례. 이 문서는 **수정 설계서**다. 작성 시점에는 제품 코드 수정과 수정 후 검증을 수행하지 않았으므로 P06·P10·B01은 모두 **미해결**이다. 기존 판정과 수치는 [재점검 원본](assessment/v1-ver2-controlled-2026-09-23/post-discovery-recheck/result.json)을 따른다.

## 먼저 고칠 판정 흐름

`main.py check`가 변경 파일을 수집하면 [의미 신호 추출](../drift_gate/adapters/ast/analyzer.py)이 신호를 붙이고, [변경 강도 분류](../drift_gate/core/classification/intensity.py)가 정책의 `min_change_intensity`를 검사한다. 이 문턱을 넘은 파일만 [평가기](../drift_gate/core/evaluation/evaluator.py)의 문서 요구 조건으로 넘어간다. API 요구 조건은 [계약 검사](../drift_gate/core/evaluation/contracts.py)의 `route_delta()`로 코드의 추가·삭제 라우트를, `_routes(..., docs=True)`로 문서의 추가·삭제 라우트를 추출해 비교한다.

따라서 **분류와 내용 검사가 같은 변경을 같은 방식으로 라우트로 인식해야 한다.** 한쪽만 수정하면 P06처럼 잘못 발동하거나 P10처럼 검사 단계까지 도달하지 못할 수 있다.

| 사례 | 현재 실제/기대 | 직접 원인 | 수정할 위치 |
|---|---|---|---|
| P06 문자열 속 `@app.get('/sample')` | `fail` / `pass` | 문자열을 라우트 등록으로 해석 | `intensity.py`의 `ROUTE_PATTERNS`, `contracts.py`의 `_routes()`·`ROUTE`, Python 의미 신호 어댑터 |
| P10 `@app.head('/health')` | `pass` / `fail` | 분류 패턴과 Python 의미 신호에 `head`가 없음. 계약 검사의 `METHODS`에는 이미 있음 | `intensity.py`의 `ROUTE_PATTERNS`, `python_adapter.py`의 메서드 목록 |
| B01 `| GET | /members |` | `fail` / `pass` | 문서 파서는 `GET /members`처럼 한 줄에서 연속된 두 토큰만 인식 | `contracts.py`의 `_routes(..., docs=True)` |

## 권장 수정 순서와 방법

### 1. P06: 문자열과 실제 라우트 등록을 분리

1. `contracts.py`의 코드 라우트 추출을 **줄 중간 어디서든 찾는 정규식**에서, 지원하는 등록 문법으로 시작하는 코드 줄만 받는 함수로 분리한다. 우선 Python 데코레이터 `@app.get('/x')`·`@router.get('/x')`는 줄 앞 공백 뒤의 `@`부터, JS/TS `app.get('/x', …)`·`router.get('/x', …)`는 줄 앞 공백 뒤의 호출부터 검사한다. `message = "@app.get('/x')"`, `const example = "app.get('/x')"`, 주석은 추출하지 않는다. 추가 줄과 삭제 줄에 **동일한 파서**를 적용한다. 기존 `ROUTE`는 임의의 객체 이름도 허용하므로, `api.get(...)` 같은 실제 등록 사용처가 있다면 이를 누락하지 않도록 별도 회귀 사례로 고정한 뒤 지원 이름 범위를 정한다.
2. `intensity.py`도 그 판정 기준을 사용하도록 공통 추출 함수를 호출한다. 정규식 한 곳만 좁히고 다른 곳을 그대로 두면 강도 판정과 `route_delta()`가 다시 어긋난다. Python 어댑터의 `_has_route_decorator()`에도 같은 시작 위치·메서드 기준을 적용한다. `analyzer.py`에 있는 `PY_ROUTE`·`TS_ROUTE` 상수는 현재 참조되지 않으므로 공통 함수로 대체하거나 제거할지 함께 결정한다. 현재 Tree-sitter Python 어댑터는 S-expression에 노드가 있어도 마지막에 상위 어댑터의 정규식을 호출하므로, 이름만으로 AST 기반 문자열 필터가 된다고 보아서는 안 된다.
3. 이 변경은 **P06에 나온 단일 줄 문자열의 범위를 해결하는 최소 수정**이다. 여러 줄 문자열, 별칭을 통한 등록, 동적 경로, 복잡한 JS 표현식까지 정규식만으로 완전하게 판별할 수 없다. 지원 문법을 확장할 때는 파일의 실제 구문 트리에서 호출·데코레이터 노드를 추출하고, 파싱에 필요한 전체 파일 내용 또는 충분한 문맥을 입력으로 제공해야 한다. 분석 불가를 정상 변경으로 단정하지 않도록 별도 상태를 유지한다.

### 2. P10: 라우트 메서드 집합을 한 곳에서 관리

1. `contracts.py`의 `METHODS`는 이미 `get|post|put|patch|delete|head|options`를 포함한다. 이를 공통 상수 또는 추출 함수로 옮겨 `intensity.py`, `python_adapter.py`, JS/TS 어댑터가 같은 목록을 쓰도록 한다. 최소 패치만 선택한다면 사용 중인 패턴들에 빠진 `head|options`를 각각 추가하되, 중복 목록이 다시 달라질 위험을 테스트로 막는다. `analyzer.py`의 미사용 `PY_ROUTE`·`TS_ROUTE` 상수도 함께 정리한다.
2. `@app.head('/health')`의 추가 줄이 `route-contract-change`로 분류되고, `route_delta()`에 `('HEAD', '/health')`가 들어가는지 확인한다. 문서에 `HEAD /health`가 없으면 차단, 추가·삭제 내용이 일치하면 허용해야 한다. `OPTIONS`도 같은 경로로 확인한다.
3. 변경 강도만 올리는 것으로 끝내지 않는다. 문서 요구 조건까지 실제로 발동했는지 CLI 결과의 규칙 상태와 필수 경로를 확인한다.

### 3. B01: Markdown 표의 메서드·경로 셀 읽기

1. `contracts.py`의 문서 파서에 `GET /members` 평문 형식을 유지하면서, `| GET | /members |`처럼 **같은 행의 인접한 두 셀**에 메서드와 경로가 있는 표 형식을 추가한다. 헤더·구분 행은 무시하고, 셀 앞뒤 공백과 메서드 대소문자를 정규화한다. 표 행 전체에서 임의의 단어 둘을 찾는 방식은 잘못된 조합을 만들 수 있으므로 열 위치를 확인한다.
2. 기존 비교 의미를 보존한다. 코드에서 `GET /users`를 삭제하고 `GET /members`를 추가했다면, 문서 diff의 삭제 쪽에서 이전 경로를, 추가 쪽에서 새 경로를 각각 읽어야 통과한다. 새 표에 `GET /members`만 있고 이전 경로 삭제 기록이 없다면 차단해야 한다.
3. 표 셀 순서가 다른 경우나 코드 블록 속 예시는 별도 사례로 명시한다. 이번 최소 수정 범위는 **메서드 열 다음에 경로 열이 오는 두 열 표**다. 임의 열 순서, 이스케이프된 `|`, 복잡한 Markdown은 필요 범위를 정한 뒤 파서를 확장한다.

## 검증 기준

수정 전 [12개 입력과 기대값](assessment/v1-ver2-controlled-2026-09-23/cases.json)을 **변경하지 않고** 다음을 확인한다. P06=`pass`, P10=`fail`, B01=`pass`가 되어야 하며, 기존에 일치했던 9개 일반 사례도 모두 유지되어야 한다. 이는 동일 사례에 대한 회귀 확인일 뿐, 새로운 데이터에서의 일반화 성능 증거는 아니다.

| 층위 | 추가할 검사 | 실패를 막는 이유 |
|---|---|---|
| 단위 | Python/JS 문자열·주석 속 가짜 호출은 강도 `route-contract-change`와 `route_delta()` 모두에서 제외. 실제 데코레이터·호출은 유지 | P06 한 패턴만 특례 처리하는 과적합 방지 |
| 단위 | `HEAD`, `OPTIONS`의 추가·삭제를 분류와 계약 추출 양쪽에서 인식 | P10처럼 앞단에서 누락되는 문제 방지 |
| 단위 | 평문과 두 열 표의 추가·삭제 경로 추출. 헤더·구분 행·무관한 셀·코드 예시는 추출하지 않음 | B01 해결 과정에서 문서 오인식 방지 |
| 엔진 | 문서 없음·다른 경로·틀린 HTTP 메서드는 `fail`, 정확한 추가·삭제 문서는 `pass` | 추출 결과가 실제 정책 판정으로 이어지는지 확인 |
| CLI | 12개 동일 Git 변경을 수정된 제품 코드로 실행하고 JSON 판정과 종료 코드를 저장 | 단위 테스트와 실제 실행 경로 차이 확인 |
| 추가 표본 | 사례 작성 후 제품 코드를 모르는 별도 사람이 고른 문자열·HEAD/OPTIONS·표 변형과 정상/위반 쌍 | 이미 알고 있는 3개 사례에만 맞춘 수정을 구분 |

[`scripts/compare_v1_ver2.py`](../scripts/compare_v1_ver2.py)는 **기준 커밋 `b9c2bd4`의 제품 파일과 현재 파일이 동일해야만 실행**한다. 제품 코드를 고친 뒤 이 도구를 그대로 돌리거나 고정 검사를 제거해 과거 실험 결과를 덮어쓰면 안 된다. 수정 후 비교는 별도 실행 도구 또는 별도 옵션으로 **기준 ver2 커밋과 수정 커밋을 모두 기록**하고, 입력·정책·환경을 동일하게 유지해 새 결과 디렉터리에 저장한다. 기존 `run-3`, `run-4`, `post-discovery-recheck` 원본은 보존한다.

완료 기록에는 수정 커밋 SHA, 변경한 함수, 단위·엔진·CLI 결과, 12개 사례의 전후 판정, 추가 표본 결과와 남은 지원 범위를 넣는다. 그 근거가 확보되기 전까지 [비교 문서](v1-ver2-controlled-comparison-2026-09-23.md)의 **미해결** 표기와 9/11·0/1 수치는 바꾸지 않는다.
