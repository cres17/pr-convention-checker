## 1. 결정: 기능 폭보다 판정 한 건의 완결성을 높인다

Drift Gate의 중심을 다음 문장으로 고정한다.

> 코드 변경으로 생긴 문서 갱신 의무를 명시적 정책으로 검사하고, 확인한 누락과 확인하지 못한 범위를 근거와 함께 보여 준다.

우선 완성할 사용자 흐름은 두 가지다.

1. 새 환경 변수 키를 사용했는데 배포용 샘플에 빠진 경우를 찾는다.
2. API 경로를 추가·제거했는데 연결된 API 문서에 반영되지 않은 경우를 찾는다.

둘 다 사람이 PR에서 반복 확인하는 일을 집합 비교로 설명할 수 있다. 판정 근거는 키, HTTP 메서드·경로, 정책, 원본 위치다.
일반적인 코드 정확성이나 자유로운 자연어 주장의 참·거짓까지 자동 판정하는 제품으로 범위를 넓히지 않는다.

핵심 성공 기준은 **“확인된 누락을 정확히 지적하고, 수정 후 같은 입력 조건에서 해결됐음을 다시 확인할 수 있는가”**다.
기능 수, 지원 언어 수, 테스트 수를 성공 기준으로 삼지 않는다.

## 3. 범위를 줄이는 방법

기존 기능을 삭제하거나 저장 형식을 초기화하지 않는다. **기본 사용 흐름과 신규 개발의 우선순위**를 줄인다.

| 영역 | 이번 계획에서의 위치 | 다음 확장 조건 |
|---|---|---|
| 정적 환경 변수 키 ↔ 샘플 파일 | 첫 번째 주력 검사 | 실제 사용자가 추가 문법을 필요로 하고 재현 사례가 있을 때 |
| 정적 API 경로 ↔ 구조화된 API 문서 | 두 번째 주력 검사 | 지원 프로파일의 오탐·미탐과 범위를 먼저 확인한 뒤 |
| 파일 동반 수정 정책 | 유지, 별도 약한 보장으로 표시 | 내용 검증을 한 것으로 승격하지 않음 |
| 스키마 호환성 | 알려진 오류부터 수정, 고급 선택 기능으로 유지 | 독립 의미 검증과 반례 시험을 통과한 범위만 보장 |
| Express 및 다른 언어 분석 | 기존 기능·회귀 유지 | 주력 두 흐름의 실제 수요로 확장 순서 결정 |
| 증거 저장·재실행·신뢰 엔진 | 기존 기반 재사용 | 새로운 저장 시스템이나 증명 언어를 만들지 않음 |
| 프로젝트 현황·초안·조직 저장소·영구 캐시 | 유지보수, 새 기능 보류 | 주력 검사 사용 중 구체적인 필요가 확인될 때 |
| 선택형 LLM 설명 | 판정 후 설명 보조 | 꺼져 있거나 실패해도 핵심 판정이 동일해야 함 |
| AI 주장 검증 | 개발·리뷰 절차로 제공 | 범용 자동 실행 플랫폼은 만들지 않음 |

첫 프로파일은 이미 있는 `python-env-literals@1`, `python-fastapi-routes@1`을 재사용한다.
후자는 지원하는 정적 등록·같은 모듈의 라우터 구성을 뜻하며 FastAPI 전체 기능 지원을 뜻하지 않는다.
새 추상 계층이나 플러그인 프레임워크를 추가하기 전에 현재 프로파일의 전제·허용 문법·거부 사유를 한 표로 고정한다.

### 무엇을 검사한다고 말할 것인가

- 환경 변수 검사는 **정적으로 확인된 새 키의 이름이 선택한 샘플에 있는가**다. 값의 정확성, 비밀값의 안전성, 운영 배포 성공은 별개다.
- API 경로 검사는 **선택한 서비스·모듈 범위의 메서드와 경로 변경이 지정 문서에 반영됐는가**다. 인증·응답 내용·실제 서버 가동을 보장하지 않는다.
- 삭제된 경로가 문서에서 없어야 한다는 의무는 그 문서와 경로의 소유 범위가 명확할 때만 확정한다. 다른 모듈·서비스가 같은 경로를 유지할 수 있으면 보류한다.
- 변경된 파일만 분석한 결과를 서비스 전체의 변경 없음으로 확대하지 않는다. 기존 범위 분석이 닫힘을 확인하지 못하면 그 이유를 남긴다.
- 처음에는 OpenAPI JSON/YAML의 경로 목록을 주력 문서 형식으로 삼는다. Markdown 경로 표기는 명시적인 토큰 포함 검사로 유지하며 문장 의미를 이해했다고 설명하지 않는다.

## 4. 판정 논리를 작게 고정한다

### 4.1 판정 전에 고정할 입력

하나의 평가에는 다음이 묶여 있어야 한다.

- base/head commit OID, 비교 방식, 대상 저장소·서비스·모듈 범위
- 정책 원문 해시·버전, 프로파일 버전, 엔진 식별자
- before/after 원문, 문서 원문, 원문 해시와 근거 위치
- 자원 예산, 면제 판단에 사용하는 평가 시각 등 결과에 영향을 주는 context

같은 입력·정책·프로파일·엔진·평가 context의 **의미 판정**은 같아야 한다. 실행 ID·소요 시간·게시 시각까지 같을 필요는 없다.
수집 오류, 잘못된 정책, 예산 초과, 증거 검증 실패는 정상적인 `pass`가 아니다. 완성된 gate를 발급하지 않고 실행 실패와 진단을 남긴다.

### 4.2 사실 → 의무 → 판정

기존 `ExactFacts / BoundedFacts / UnknownFacts`, planner, proof 검증기를 재사용한다.

1. **사실:** 이 범위에서 확실히 추가된 키·경로와 아직 확정할 수 없는 후보를 구분한다.
2. **의무:** 해당 변경에 어떤 문서 조건이 필요한지 정책으로 정한다.
3. **판정:** 조건 충족을 증명하거나, 위반 증거를 제시하거나, 판단을 보류한다.
4. **조치:** 차단·검토·허용은 기존 정책의 심각도·면제·미검증 처리 규칙으로 별도 계산한다.

새 키의 집합을 `A`, 문서의 키 집합을 `D`라고 하면 기본 의무는 `A ⊆ D`다.
완전한 집합을 얻었을 때는 다음처럼 끝난다.

```text
추가 키 = after 키 − before 키
누락 키 = 추가 키 − 문서 키

의무가 적용되고 누락 키가 있음 → 위반, 누락 키를 증거로 제시
의무가 적용되고 누락 키가 없음 → 충족
추가 키가 없음을 닫힌 범위에서 확인 → 해당 의무 없음
```

불완전한 분석에서는 하한·상한을 이용한다. `A− ⊆ A ⊆ A+`, `D− ⊆ D ⊆ D+`라 할 때:

| 판정 | 충분조건 | 의미 |
|---|---|---|
| 충족 T | `A+ ⊆ D−`를 증명 | 추가될 수 있는 항목 모두 문서에 확실히 있음 |
| 위반 F | `A− − D+`가 비어 있지 않음 | 확실한 추가 중 문서에 들어 있을 가능성도 없는 항목이 있음 |
| 보류 U | 위 조건을 증명하지 못함 | 정보가 더 필요함 |

열린 상한은 전체 가능성을 뜻하며 빈 집합이 아니다. 문서를 읽지 못한 경우와, 지정 경로에 문서가 없음을 확인한 경우도 구분한다.
문서가 없음을 확정했다면 `D=∅`이지만, 읽기 실패라면 `D`를 모른다.

경로 제거 의무는 `R ∩ D = ∅`다. `R+ ∩ D+ = ∅`를 증명하면 T, `R− ∩ D−`에 원소가 있으면 F, 그 외 U다.
이 식은 문서와 경로의 소유 범위가 일치한다는 전제 아래 적용한다.

### 4.3 의무의 적용 여부를 빼먹지 않는다

| 의무 발생 A | 문서 조건 C | 결과 |
|---|---|---|
| 확실히 발생 | T | 충족 |
| 확실히 발생 | F | 위반 |
| 확실히 발생 | U | 보류 |
| 발생하지 않음을 증명 | 어떤 값이든 | 해당 없음 |
| 발생 여부 불명 | 어떤 값이든 | 적용 여부 보류 |

마지막 행은 보수적인 제품 계약이다. 논리적 함의 `A ⇒ C`를 더 적극적으로 단순화할 수 있는 경우에도,
범위를 확인한 것처럼 보이지 않도록 적용 여부의 불확실성을 별도로 남긴다.

`all` 조건은 하나의 확실한 F가 있으면 F, 전부 T면 T, 나머지는 U다.
`any` 조건은 하나의 확실한 T가 있으면 T, 전부 F면 F, 나머지는 U다.
관련 없는 미지원 항목 하나 때문에 이미 확인한 위반을 숨기지 않는다. 반대로 오류 때문에 읽지 못한 범위를 T로 채우지 않는다.
여러 문서의 부분 정보를 합칠 수 있는지도 정책이 정해야 한다. 한 완전한 문서를 요구하는 `any`를 여러 불완전한 문서의 합집합으로 통과시키지 않는다.

### 4.4 사용자 결과는 쉽게, 내부 구분은 정확하게

사용자에게는 의무별로 **충족 / 위반 / 보류 / 해당 없음**과 이유를 먼저 보여 준다.
면제·검사 생략·실행 실패는 이 네 값의 성공 변형으로 숨기지 않고 별도로 표시한다.
보장 범위, 증거 수준, gate 결과, 조직의 조치는 상세 정보로 남긴다.

권장 엄격 정책에서는 미해결 항목을 `review`로 보내고 승인 없는 자동 병합 근거로 쓰지 않는다.
기존 정책이 경고·생략·면제를 허용하는 의미를 조용히 바꾸지는 않는다. 허용 조치와 “내용을 검증했다”는 표현은 항상 구분한다.

부분 수용은 복합 주장을 작은 주장으로 나눈 뒤 사람이 정하는 요약이다.
전체가 참이어야 하는 주장은 하위 주장 하나의 반례만으로 전체 수용을 거부할 수 있다. 이를 단순히 “통과한 테스트 비율만큼 참”으로 계산하지 않는다.

## 5. 현재 코드에서 먼저 바꿀 부분

아래 P1~P4는 [2026-10-13 코드 검토](../review/drift-gate-portfolio-senior-review-2026-10-13.md)와
[재현 자료](../assessment/portfolio-review-2026-10-13/README.md)를 기준으로 한다. 이전 버전에서 이미 고친 결함과 구분한다.

| 작업 | 실제 수정 지점 | 완료 조건 |
|---|---|---|
| P1: 숫자 의미 통일 | `core/evaluation/compatibility.py`의 enum 동등성·정수 분류·분기 겹침 | 1과 1.0의 동등성, true와 1의 구분, 소수·음수·큰 수·비유한 입력을 일관되게 처리. 재현한 잘못된 T 두 건 제거 |
| P2: 근거 없는 무한성 추론 제거 | 같은 모듈의 `subset`·object/array 처리 | 빈 객체만 허용하는 동등 schema를 F로 판정하지 않음. 증명 불가 범위는 U |
| P3: 평가 분모 고정 | `adapters/holdout.py`의 case 검증·`_units` | 정책 규칙 전체가 평가 단위에 존재. 정답이 없더라도 단위를 없애지 않고 미라벨로 남김 |
| P4: 지표 행렬 고정 | `core/evaluation_stats.py` | 모든 엔진 결정×정답 조합의 분자·분모가 명시된 표와 일치. 정답 `not-applicable`을 잘못 확정한 경우도 집계 |
| 결과 표현 통일 | `models/result.py`, `content_result.py`, `gating/enforcement.py`, 각 출력 어댑터 | 동일 결과가 CLI·JSON·HTML·Desktop에서 충족/보류로 다르게 해석되지 않음 |

스키마 수정에서 숫자를 JSON 문자열로 비교하지 않는다. Python의 `bool`이 `int`처럼 취급되는 것도 차단한다.
숫자 디코딩에서 정밀도를 잃은 값을 정확한 비교라고 인증하지 않도록 허용 입력·디코더 계약을 먼저 정한다.
분기 간 겹침을 증명하지 못한 `oneOf`를 서로소 합집합으로 단순화하지 않는다.

F에는 실제로 확인 가능한 반례 값이나, 정의된 프로파일 안에서 검증 가능한 위반 근거가 필요하다.
T는 지원 문법의 논리 규칙으로 도출한다. 유한 샘플에서 반례를 못 찾았다는 이유만으로 T를 내지 않는다.
독립 validator는 반례·회귀 대조에 사용하며 모든 schema의 포함 관계를 증명하는 장치로 설명하지 않는다.

P1/P2는 주력 기능을 좁혀도 먼저 고친다. 고급 선택 기능에 남은 잘못된 확정을 방치하는 것은 범위 축소가 아니다.

## 6. 구조 변경은 기존 흐름 안에서 한다

목표 흐름은 이미 존재하는 계층을 정돈하는 것이다.

```text
Git 원본·정책·문서 수집
  → InspectionSnapshot + EvaluationContext
  → 프로파일별 사실 추출
  → 의무 계획 + 순수 판정
  → 결과·증거 검증
  → 정책 조치 계산
  → CLI / JSON / HTML / Desktop 출력
                └ 기존 증거 묶음·재실행 경로
```

| 책임 | 재사용할 곳 | 제한된 변경 |
|---|---|---|
| 입력 수집·고정 | `adapters/git/immutable.py`, `snapshot.py`, `inspection.py` | 선택 범위·읽지 못한 입력을 결과까지 전달 |
| 프로파일과 사실 | `core/contracts/profiles.py`, `core/models/facts.py` | 지원 계약 명시, 같은 의미의 새 사실 타입을 중복 생성하지 않음 |
| 의무와 증거 | `core/contracts/planner.py`, `evaluation/proof_gate.py`, `result_guard.py` | 주력 두 흐름의 연결·증거 충분성 확인 |
| 의미 판정 | `evaluation/environment.py`, `routes.py`, `compatibility.py` | 집합 연산·JSON 값 의미를 순수 함수로 유지 |
| 공개 상태 변환 | `models/result.py`, `content_result.py`, `gating/enforcement.py` | 상태 생성·변환의 소유자를 명확히 하고 공통 계약 시험으로 고정 |
| 실행 조정 | `adapters/cli/runner.py` | 인자 등록, 검사 실행, holdout/bundle/org 명령을 책임별로 분리 |
| 사용자 안내 | 기존 reporter와 Desktop | 확인한 항목·미해결 사유·다음 행동을 같은 결과에서 표시 |

CLI 분리는 판정 오류 수정과 별도 커밋으로 진행한다. 명령·종료 코드·JSON·오류 계약을 먼저 고정하고 함수 이동 뒤 대조한다.
줄 수 감소를 목표로 삼지 않고, 한 의미를 고칠 때 여러 출력 채널의 판정 코드를 함께 고쳐야 하는 상태를 줄인다.
핵심 모델·새로 분리한 순수 모듈부터 타입 검사를 CI 필수 항목으로 만든다. 전체 저장소의 일괄 타입 재작성은 보류한다.

## 7. 사용자가 실제로 얻는 결과

다음은 **목표 출력 예시이며 현재 실행 결과가 아니다.**

```text
검사: 새 환경 변수 키의 샘플 반영
판정: 위반
대상: src/config.py → .env.example
누락: BILLING_TOKEN
근거: 고정한 head 원문에서 새 정적 키 확인 / 샘플 원문에 해당 키 없음
조치: 샘플에 키 이름과 필요한 설명을 추가한 뒤 다시 검사
확인 범위: 선택한 Python 모듈의 정적 키 접근
```

불확실한 경우는 다음 행동도 달라야 한다.

```text
판정: 보류
이유: 런타임에 조합하는 환경 변수 이름이라 새 키 집합을 확정할 수 없음
확인된 부분: 정적 키 BILLING_TOKEN의 샘플 반영은 확인
다음 행동: 동적 키 목록을 사람이 확인하거나 지원되는 명시적 설정으로 변경
```

핵심 데모는 각 주력 기능마다 세 장면으로 고정한다.

1. 코드만 변경: 정확한 누락 증거가 나온다.
2. 올바른 문서를 반영: 같은 정책·프로파일에서 충족으로 바뀐다.
3. 미지원 문법·불완전한 범위: 성공으로 위장하지 않고 보류 사유가 나온다.

이미 문서에 내용이 있는 경우도 따로 시험한다. **파일 동반 변경 정책**과 **내용 충족 정책**은 다른 의무다.
내용이 이미 맞으면 파일을 형식적으로 건드릴 필요가 없도록 하는 새 권장 설정은 별도로 제안하되,
기존 `any_changed/all_changed`의 동반 변경 의미를 몰래 바꾸지 않는다. 기존 proof 전환 기능과 비교해 명시적으로 이동한다.

## 8. 자기소개서 경험을 재현 가능한 작업 방식으로 남긴다

새 범용 테스트 실행기를 만드는 대신 기존 회귀 테스트·재현 스크립트·증거 묶음을 연결하는 짧은 기록 양식을 둔다.

| 필드 | 기록할 내용 |
|---|---|
| 주장 | 원문, 당시 작성자·출처를 확인할 수 있는 범위 |
| 범위·명제 | 어떤 버전·입력·환경에서 어떤 결과를 보장한다는 주장인지 |
| 기대 | AI의 결과를 보기 전에 정한 기준과 그 근거 |
| 재현 | 검토한 스크립트, fixture, 실행 명령, 의존성·환경 |
| 관찰 | 종료 코드, 원본 결과, 입력/결과 해시, 근거 위치 |
| 판단 | 수용·부분 수용·불수용·판단 보류와 그 이유, 판단자 |
| 후속 | 반례 ID, 수정 커밋, 회귀 결과, 여전히 확인하지 못한 것 |

정책 검사의 정적 판정과 앱의 실제 실행 관찰을 다른 근거 종류로 기록한다.
실행은 관찰 사례를 늘리지만 일반적인 정확성 증명은 아니다. 반대로 순수한 집합 관계는 입력 사실이 올바르다는 전제 아래 논리적으로 판정할 수 있다.
임의 PR의 명령을 자동 실행하거나 제출자의 테스트 기대값을 그대로 독립 정답으로 채택하지 않는다.

대표 사례는 기존 C12(의미 있는 코드 변경을 주석으로 오인), C05(비교 기준), C09(비유한 숫자)다.
당시 결과는 보존하고 최신 버전의 재실행 결과를 별도 파일에 남긴다. 최신 P1의 스키마 숫자 반례는 C09의 전송 직렬화 문제와 다른 결함으로 기록한다.

## 9. 논리가 맞는지와 쓸모가 있는지를 따로 검증한다

### A. 논리·회귀 검사

| 축 | 필수 사례 | 확인할 불변식 |
|---|---|---|
| 수집 | base 이동, rename, 삭제, 원문 누락, 예산 초과 | 입력 변경·수집 실패가 정상 통과로 숨지 않음 |
| 키 | 실제 접근, 주석·문자열, 이름 재바인딩, 동적 키, 모듈 간 이동 | 지원 범위에서만 정확한 추가 집합을 생성 |
| 경로 | 추가·삭제, prefix, 중복 identity, 다른 서비스, 열린 import | 범위 밖 경로를 근거 없이 합치거나 제거하지 않음 |
| 문서 | 내용 반영, 미반영, 기존에 존재, 참조/파싱 실패, 빈 선택 | 부재와 읽기 실패, 동반 변경과 내용 충족을 구분 |
| 합성 | 위반+보류, 충족+보류, any/all, 면제 | 앞의 진리표와 조치 계약을 유지 |
| 숫자·schema | 1/1.0, bool/number, 빈 객체·배열, oneOf 겹침 | 잘못된 T/F 반례 제거, 미지원은 U |
| 출력·재실행 | 동일 snapshot, 각 출력 채널, 묶음 손상 | 의미 판정 일치, 손상 시 정상 결과 인증 거부 |

변형 시험은 횟수보다 변형의 의미를 정한다. 프로파일이 무시한다고 선언한 주석·공백 변경은 판정을 유지해야 한다.
닫힌 내용 검사에서 누락 키를 문서에 추가하면 그 누락 위반이 해결돼야 한다.
불확실성이 늘었다는 이유만으로 해당 증거와 무관한 확정 위반이 없어지면 안 된다.
표본을 늘려도 생성 문법 밖의 결함은 찾지 못하므로 생성기 범위 자체를 검토한다.

### B. 평가 지표의 계약

기본 평가 단위는 **PR 사례 × 정책 규칙**으로 고정한다. 세부 의무 지표를 추가할 경우 별도 분모와 안정된 ID를 쓴다.
정책 전체 규칙을 단위로 생성하고, 미라벨·보류·생략·오류를 조용히 제거하지 않는다.
일부 규칙만 평가하려면 동결 전에 선택 규칙·이유·제외 수를 명시하고 전체 성능과 구분한다.

확정 오판율은 확정 판정 중 독립적으로 판단 가능한 정답과 불일치한 비율이다.
정답 `not-applicable`인데 엔진이 충족 또는 위반이라고 확정한 경우도 불일치다.
정답 `undecidable`은 자동 정답·오답 처리하지 않고 평가 불가 수와 해당 확정 출력 수를 별도로 낸다.
이 규칙은 현재 P4 수정 때 전체 교차표로 고정한다.

함께 보고할 지표는 다음과 같다.

- 확정 위반의 정밀도와 재현율: 검토해야 할 지적이 얼마나 맞으며 실제 위반을 얼마나 찾았는가.
- 확정 오판율과 판정 가능 비율: 전부 보류해서 오판을 숨기지 않았는가.
- PR 단위 오차단·누락 차단·실행 오류: 실제 사용 흐름에서 어떤 부담이 생겼는가.
- 보류 사유별 건수와 미지원 입력 비중: 다음 지원 범위를 어디에 투자해야 하는가.
- 정답 출처, 전체·라벨된·제외된 수, 분자/분모, 구간 추정의 전제: 수치를 해석할 수 있는가.

규칙 결과는 같은 PR 안에서 상관될 수 있다. 단순 비율의 구간만으로 독립 표본이라고 주장하지 않는다.
초기에는 PR·저장소별 결과와 원시 분모를 함께 내고 작은 표본의 일반화 한계를 적는다.

### C. 작은 실제 PR 파일럿

1. 여러 외부 저장소에서 두 주력 검사와 관련된 실제 PR을 모은다. 예를 들어 20~30개는 시작 규모 제안일 뿐 통계적 보장 기준이 아니다.
2. 규칙과 문서 연결의 근거를 코드 작성자 관행·문서에서 정하고, 기대 결과에 맞춰 정책을 뒤늦게 고르지 않는다.
3. 저장소·변경 계열 단위로 개발/평가를 분리하고 입력·정책·정답 자료를 해시로 고정한다. 기존 개발용 반례는 평가셋에서 제외한다.
4. 엔진 결과를 가린 상태에서 사람이 판정한다. LLM 대리 평가는 `llm-proxy`로 분리하고 사람 독립 정답으로 부르지 않는다.
5. 같은 입력에서 기존 방식, 파일 동반 수정만 보는 기준선, 개선본을 비교한다. 항상 통과/항상 보류하는 기준선도 지표의 허점을 확인하는 용도로 둔다.
6. 확인한 누락, 불필요한 경고, 보류를 해결하는 추가 확인 시간, 실행 시간을 측정한다. 수동 검토와 비교할 때 같은 사례를 먼저 본 학습 효과를 통제하거나 한계로 밝힌다.
7. 평가 후 코드를 수정했다면 해당 사례는 회귀 자료가 된다. 다음 성능 주장은 새로 동결한 평가셋에서 한다.

실제 문서 누락이 너무 적으면 검출 성능을 추정할 수 없다. 그 사실을 보고하고, 의도적으로 만든 결함은 별도 통제 실험으로 분리한다.
외부 저장소에 없는 문서 의무를 우리가 새로 정한 경우에는 “실제 팀 정책의 위반 탐지”가 아니라 “정의한 정책에서의 재평가”다.

## 10. 구현 순서와 종료 조건

아래는 새 작업 묶음 이름이다. 이전 설계의 S1/S2/W 번호를 구현 완료로 다시 해석하거나 덮어쓰지 않는다.

| 순서 | 묶음 | 산출물 | 다음 단계로 넘어가는 조건 |
|---:|---|---|---|
| 1 | 확정 판정 오류 수정 | P1/P2 수정·반례 회귀·독립 validator 대조 | 알려진 잘못된 T/F 제거, 지원 문법의 정상 T/F 유지. 모두 U로 바꿔 끝내지 않음 |
| 2 | 측정 계약 수정 | P3/P4 수정·분모 검사·전체 지표 행렬 | 일부 정답을 빼도 평가 단위가 사라지지 않고 모든 조합의 집계가 표와 일치 |
| 3 | 두 주력 흐름 정리 | 지원 계약 표·권장 정책·누락/수정/보류 데모 | 원본 수집부터 출력까지 실제 제품 경로로 작동, 정확한 근거와 행동 안내 제공 |
| 4 | 책임·표현 통일 | CLI 책임 분리·공통 결과 계약·핵심 타입 검사 | 기존 CLI/API/저장 형식 회귀 통과, 채널별 판정 불일치 없음 |
| 5 | 외부 파일럿 | 동결 자료·출처별 평가·검토 부담 기록 | 측정 결과로 유지/축소/확장을 결정할 수 있음. 좋은 점수 자체를 종료 조건으로 두지 않음 |
| 6 | 배포·포트폴리오 정리 | 현재 보장 한 장·대표 재현·검증한 설치 파일 안내 | 소스·원격 CI·다운로드 파일의 commit/해시 연결, 핵심 사용 흐름 설치본에서 재현 |

3번의 권장 정책 전환은 기존 `auto`·기존 JSON 의미를 유지한 채 명시적인 설정으로 제공한다.
기존 proof/typed-trigger 비교 경로를 이용해 같은 snapshot의 결과 차이를 설명하고, 차이를 검토한 뒤에만 기본값 변경을 별도 버전으로 다룬다.
의도된 의미 변경은 schema/policy 버전과 이동 안내에 기록하고 과거 증거 묶음 재생을 계속 지원한다.

각 제품 변경 뒤에는 관련 회귀를 먼저 실행하고, 묶음 완료 시 전체 Python·React·타입·린트 검사를 수행한다.
원격 CI·세 플랫폼 설치본 검증은 해당 구현 커밋의 결과로 기록한다. 계획 작성 시점에 이전 CI 성공을 새 구현 검증처럼 인용하지 않는다.

**완성도를 판단할 최종 질문은 세 가지다.**

- 처음 보는 개발자가 잘못된 판정 한 건의 입력·근거·반례·수정 결과를 따라갈 수 있는가?
- 문서 누락을 찾거나 불필요한 수동 확인을 줄인 실제 사례가 있는가?
- 지원하지 않는 부분을 숨기지 않으면서도, 지원하는 두 흐름에서는 안정적으로 결론을 내리는가?

이 세 가지를 충족하기 전에는 조직 기능·언어·새 분석 계층을 추가하지 않는다.
이미 제출한 자기소개서의 경험은 당시 사실로 유지하고, 이 계획으로 새로 얻은 결과는 날짜·버전·근거를 붙여 후속 개발로 설명한다.
