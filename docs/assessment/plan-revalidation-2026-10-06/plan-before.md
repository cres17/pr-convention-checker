## 3. P1: 입력과 작업 경로

### 재현 사실

같은 Git 변경에 대해 일반 CLI를 저장소 루트에서 실행하면 5개 규칙으로 FAIL이다. `src/`에서 실행하면 정책을 못 찾아 0개 규칙으로 PASS다. 명시한 `--policy nope.yml`도 PASS·종료 0이다. `review`는 루트에서 종료 0, 하위 폴더에서는 `src/a.py`를 읽지 못해 종료 2다.

**`scripts/check_self.py`의 정책 없음은 종료 2다.** 일반 CLI까지 이 동작이라고 일반화하면 안 된다. Git 입력 오류는 이미 종료 2로 처리하지만 정책·체크리스트 입력 오류는 같은 계약을 공유하지 않는다.

관련 코드: `adapters/cli/runner.py:_run_check`, `_run_review`, `_run_self_audit`, `adapters/policy_loader.py`, `adapters/git/client.py`.

### 수정안과 완료 기준

먼저 `git rev-parse --show-toplevel`로 검사 저장소를 확정하고, Git이 반환한 경로는 그 루트에 상대적으로 읽는다. 명시적 `--policy`의 상대 경로는 호출 위치 기준으로 해석할지 저장소 기준으로 해석할지 명시하고 한 번만 확정한다. 기본 정책 탐색만 저장소 루트에서 수행하면 일반적인 CLI 경로 관례도 보존할 수 있다.

- 루트·하위 폴더에서 같은 대상/정책의 결과가 같아야 한다.
- 명시적 정책 오타·없는 파일·잘못된 인코딩·스키마 오류는 `input_error`, 종료 2, 신선한 JSON으로 끝나야 한다.
- 정책 없는 프로젝트를 허용하려면 명시적인 탐색 모드와 `not-configured` 결과를 사용한다. 일반 PASS와 구별한다.
- 체크리스트 누락도 같은 입력 오류 계약으로 처리한다.
- 원격 PR 검사와 로컬 검사에서 소스·문서 리더가 같은 루트를 사용해야 한다.

원격 문서의 “D5는 새 회귀”는 사용자 관점에서는 맞지만, 코드상 이전 버전도 잘못된 상대 경로를 사용했다. 과거 `review_files`가 읽기 예외를 삼켜 성공한 것이다. 예외를 다시 삼켜 종료 0으로 만드는 것은 수정이 아니다.

## 4. P1: 의미 있는 코드 변경이 코멘트로 분류됨

`intensity._is_comment_or_blank`와 `analyzer._comment_line`은 `*`·`#` 등의 줄 시작만으로 코멘트를 판단한다. Python AST로 문법이 맞는지 확인한 `*extra`·`**options` 추가도 자체 정책에서 PASS다. 같은 함수에 `c=2`를 추가하면 FAIL이다. 원격의 `#define` 반례도 Mac에서 재현됐다.

이 경우는 언어 미지원 경고가 아니라 **실제 코드 변경을 분석 전에 지워 규칙을 적용하지 않는 문제**다. 두 개의 코멘트 판별 함수를 각각 고치면 서로 다시 어긋날 수 있다.

수정은 언어별 렉서·토큰 문맥을 공유하는 작은 순수 모듈로 한다. Python은 `tokenize`, C 계열은 블록 코멘트 상태와 문자열 문맥을 구별한다. 언어를 모르는 경우 분석에서 제외하지 않는 보수적 처리가 필요하다. 단순히 확장자별 허용 prefix만 바꾸면 여러 줄 문자열·블록 코멘트·generator·포인터가 남는다.

완료 기준: 유효 varargs/kwargs·기본 인자·전처리 지시·포인터/생성기 변경은 해당 규칙을 적용하고, 실제 코멘트·문자열 속 코드 예시는 코드 변경으로 승격하지 않는다. 기존 지원·경계 사례와 원래 문서 동기화 정상 사례가 유지돼야 한다. 통과해야 할 반례를 테스트 이름만 추가해서 해결했다고 판단하지 않는다.

## 5. P1: 이름 변경이 검사 범위를 벗어남 — H1

같은 파일을 100% 내용 동일한 Git rename으로 이동했다.

| 이동 | 판정 |
|---|---|
| `drift_gate/core/audit_subject.py → elsewhere/audit_subject.py` | FAIL: 이전 경로가 규칙에 걸림 |
| 위 파일 → `drift_gate/tests/audit_subject.py` | PASS: 새 경로 ignore로 먼저 제거 |
| 위 파일 → `docs/audit_subject.py` | PASS: docs-only로 전체 평가 생략 |
| 위 파일 → `tests/audit_subject.py` | PASS: test-only로 전체 평가 생략 |
| 원래 파일 삭제만 수행 | FAIL |

원인은 `classifier`의 전체 변경 종류 판정과 `evaluator`의 ignore 처리에서 새 경로만 보는 것이다. 실제 trigger 판정은 이전 경로도 보지만, 그 전에 평가가 생략되거나 파일이 빠진다. `check_self.py`의 coverage도 새 경로만 보므로 첫 사례는 FAIL인데 matched 목록은 비어 있다.

수정 기준: rename의 이전·새 경로를 같은 변경 객체로 보존하고, 어느 쪽이라도 보호된 운영 경로이면 doc/test 전용 생략이나 목적지 ignore로 지우지 않는다. ignore 경계 양쪽의 의도를 명시한다. evaluator·coverage·전체 변경 분류가 하나의 경로 집합 계산을 공유해야 한다. 위 네 이동과 반대 방향, 평범한 테스트 간 이동, 실제 삭제를 함께 회귀 검사한다.

## 6. P1: 자체 검사의 신뢰 경계 — H2

core 변경과 문서 누락을 유지한 채 아래 정책 변형을 각각 적용했다. 정책 변경 자체에 필요한 운영 문서는 수정해 다른 규칙의 실패가 원인을 가리지 않게 했다.

| 변경 | 실제 결과 |
|---|---|
| 규칙 전체 삭제 | PASS |
| core 규칙만 삭제 | PASS |
| 심각도를 nit로 내림 | 위반은 존재하지만 PASS |
| major 실패 개수를 999로 올림 | WARN·종료 0 |
| core를 ignore에 추가 | PASS |
| 계약 문서 그룹을 optional로 바꿈 | PASS |
| 트리거를 맞지 않는 경로로 축소 | PASS |
| impl-only 기준을 signature-change로 올림 | PASS |

빈 규칙만 금지해도 나머지가 남는다. 더 근본적으로 현재 CI는 검토 대상 브랜치의 `scripts/check_self.py`와 설치된 엔진을 실행한다. 신뢰 정책을 읽는 코드도 검토 대상이므로 같은 실행기 안에서만 하는 보호는 완전한 보안 경계가 아니다.

권고: 기본 브랜치나 별도 고정된 신뢰 버전의 실행기·정책으로 기존 의무를 검사하고, 후보 정책의 새 동작을 별도 작업으로 검사한다. 정책 약화·의도적 마이그레이션은 명시적으로 승인한다. 범용 `ignore reason`이나 문서 문장만으로 자체 검사 완화를 승인하지 않는다. 검토 대상 코드는 제한된 권한으로 실행하고, `pull_request_target`에서 후보 코드를 비밀과 함께 실행하는 방식은 피한다.

읽기 전용 GitHub branch API에서 `ver2`와 `main`의 `protected`는 모두 false로 응답했다. 이는 해당 응답에 대한 확인이며 조직 차원의 모든 통제 부재까지 증명하지 않는다. 로컬 저장소에는 CODEOWNERS 파일이 발견되지 않았다. 보호 설정 적용은 이 문서 작성에서 수행하지 않았다.

완료 기준: 위 8개 변형 중 승인되지 않은 약화는 후보 검사 결과가 PASS라도 필수 검사를 통과하지 못해야 한다. 정당한 새 규칙 추가와 승인된 정책 마이그레이션은 가능해야 한다. 실행기만 `exit(0)`으로 바꾸는 후보도 신뢰된 검사를 무력화하지 못해야 한다.

## 7. P1/P2: 운영 경로 목록의 누락 — D12·H3

현재 목록은 Python 운영 파일(`__init__` 포함), UI TS/TSX/CSS, packaging, workflows, 명시한 빌드 설정을 대상으로 한다. Python 테스트·일반 평가 스크립트는 목록에서 제외했고 UI 테스트 11개는 ignore로 남겼다. **194 = 일치 157 + 제외 11 + 미분류 26**이다. 원격의 “PR 변경분 중 문서 제외 36개”와 분모가 다르며 두 수치가 충돌하는 것은 아니다.

중요한 미분류: `grammar_resources.py`, `parser_hashes.json`, `policy_loader.py`, `desktop/service.py`, `desktop/package_check.py`, `desktop/resources.py`, `action.yml`, UI package/lock/vite 설정. 이름만 있는 `__init__.py`까지 모두 같은 위험이라고 보지는 않는다. 현재 파서 무결성 검사가 깨졌다는 뜻도 아니다. 그 파일들의 변경에 계약 갱신 요구가 연결되지 않는다는 의미다.

수정안: 전체 경로를 무조건 한 규칙에 넣지 말고 파서·입출력·설치·화면·이력·정책 로딩 책임별 문서에 연결한다. 신규 운영 파일은 `covered` 또는 사유가 있는 `explicitly-exempt`여야 한다. 미분류 운영 파일은 CI에서 별도로 거부한다. 리뷰 산출물·문서·테스트까지 일괄 거부하면 불필요한 문서 갱신이 늘어난다.

완료 기준: 명시한 운영 목록의 모든 파일이 담당 규칙이나 검토된 제외 사유를 가지며, 새 운영 파일 하나를 임의 위치에 추가해도 정책 등록 없이 통과하지 않는다. rename의 이전 경로도 목록에 반영한다.

## 8. P2: 입력 스키마와 결과 파일의 신뢰성 — D4·H4

빈 정책 파일·YAML `null`·루트 `[]`는 규칙 0개 PASS다. `rules: null`, rule id 누락, null rule, boolean severity, 문자열 실패 임계값은 KeyError/TypeError/AttributeError 등으로 종료 1이 된다. 이 다섯 경우에는 **미리 있던 PASS 결과 파일이 그대로 남았다.**

중요한 구분: 프로세스는 실패했다. CI가 성공했다는 실험이 아니다. 오래된 JSON만 읽거나 `always` 업로드 결과를 최신 결과로 오인하는 위험을 재현한 것이다. 정상 YAML 문법 오류와 없는 정책은 `input_error` JSON으로 덮어써 종료 2가 된다.

수정안: YAML 파싱 후 객체 생성 전에 루트·규칙·그룹·경로 배열·문자열·boolean·임계값의 형식을 검증한다. `safe_load(...) or {}`로 잘못된 빈 타입을 같은 값으로 뭉개지 않는다. 필드 경로가 포함된 PolicyLoadError로 정규화한다. 임의 Exception을 모두 삼키는 방식은 프로그래밍 오류를 숨긴다.

결과는 실행마다 새 run ID와 출처를 가진 파일에 원자적으로 기록한다. 실패해도 그 실행의 error artifact가 남아야 하며, 이전 PASS는 과거 실행임을 식별할 수 있어야 한다. 저장 자체가 실패한 경우 JSON이 남았다고 주장하지 않는다.

완료 기준: 이번 10개 스키마 입력이 의도한 명확한 계약으로 처리되고, 오류 실행이 이전 PASS 파일을 최신 결과로 재사용하지 않는다. 정상 빈 정책을 범용 라이브러리에서 허용하더라도 필수 자체 검사에서는 `not-configured`나 오류로 구별한다.

## 9. P2: 비교 기준을 항상 merge-base로 바꾸면 안 됨 — D3

기능 브랜치를 만든 뒤 main에 API 파일이 추가된 사례에서 `--base main`은 그 파일을 내 삭제로 보아 FAIL이다. merge-base 기준은 PASS였다. 로컬 “내 브랜치 변경” 사용 목적에 대해 원격 지적이 맞다.

다만 현재 `git diff <commit>`는 **지정 커밋의 트리와 현재 상태 비교**로서 정상적인 의미가 있다. push 이전 SHA 비교·특정 릴리스 비교까지 자동으로 merge-base로 바꾸면 계약이 달라진다. `comparison_mode=commit`과 `comparison_mode=merge-base`를 구분하고, README의 브랜치 안내를 후자로 명확히 해야 한다. PR CI의 기본 merge checkout은 로컬 기능 브랜치와 입력 상태가 다르다.

완료 기준: main 전진·divergence·merge commit·detached HEAD·dirty worktree·상관없는 history에 대해 기대 변경 목록을 독립 Git 명령과 대조한다. 요청 base·해석 base·HEAD·비교 모드를 보고서에 보존한다.

## 10. P2: self-audit와 계약 문서의 의미 — D6·H5

Mac 재실행에서도 거부한 C05·C09·C12가 모두 supported였다. C10은 명시한 한 파일과 달리 31개 근거가 붙었다. 숫자가 원격의 30과 다른 것은 문서 커밋까지 입력에 포함됐기 때문이다. 경로 조각 매칭의 실패 방향은 같다. C14는 변경 파일 이름 단서가 없어 unsupported였다. 이번에는 테스트 수 주장을 전수 재실행하지 않았으므로 “이번에 사실을 새로 입증했다”고 하지 않는다.

정확한 파일명 매칭만 도입해도 주장 내용의 진실성이 검증되지는 않는다. `supported`를 `related-evidence-found` 수준의 상태로 바꾸고, `behavior-verified`는 별도 실행 근거(커밋, 입력, assertion, 결과, 도구 버전)가 있을 때만 사용해야 한다. 근거가 없다는 것은 거짓이라는 뜻이 아니다. 체크리스트에 적힌 임의 shell 명령을 자동 실행하는 방식으로 해결해서는 안 된다.

계약 문서에서는 공백 추가·HTML 코멘트·무관 문장·전체 내용 비우기도 PASS였다. 소스와 문서를 함께 삭제하면 FAIL이지만 계약 문서만 삭제하면 docs-only 생략으로 PASS다. 최소한 중요 문서 존재·비어 있지 않음·필수 계약 항목 유지 검사는 별도 정적 무결성 검사로 둘 수 있다. 일반적인 자연어 의미 일치를 완전히 자동 판정한다는 약속은 하지 않는다.

완료 기준: 거짓 주장에 관련 파일만 추가해도 행동 검증으로 승격되지 않고, 올바른 외부 테스트 근거는 파일명 단서가 없어도 별도 근거로 기록할 수 있어야 한다. 중요 문서 삭제·빈 문서·무관 문장 반례는 의미 검증 완료 상태를 얻지 못해야 한다.

## 11. P2: MCP 계약과 경로 권한 — D8·D9

Mac에서도 JSON-RPC 결과의 `content.text` 안에 `NaN`이 남았고 레거시 경로는 같은 입력을 거부했다. **바깥 JSON은 유효하다.** 문자열 안에 들어 있는 JSON 표현을 strict JSON으로 다시 읽을 때 문제가 되며, 이를 전체 전송 JSON 파손이라고 표현하면 과장이다. 도구 결과를 직렬화하는 내부 단계에도 동일한 유한 숫자 규칙을 적용해야 한다.

id 없는 tools/list 요청에 응답 1개가 왔고, 파싱 실패는 레거시 `{ok:false}` 형식으로 왔다. JSON-RPC 2.0은 알림에 응답하지 않고 파싱 오류 응답에 규격 envelope를 요구한다. 지원 프로토콜/레거시 모드를 명확히 하고 두 계약을 각각 검사한다. [JSON-RPC 2.0](https://www.jsonrpc.org/specification), [JSON 숫자 규칙](https://www.rfc-editor.org/rfc/rfc8259#section-6).

외부 경로 읽기는 임시 JSONL의 합성 표식만으로 재현했다. 실제 사용자 파일을 읽지 않았다. API에 `path`·`repo_root`가 있으므로 허용된 다중 저장소 기능인지, 저장소 안으로 제한된 기능인지 계약을 먼저 정해야 한다. 이 결과만으로 프롬프트 주입에 의한 탈취나 권한 상승이 입증되지는 않는다.

제한 모드에서는 서버 시작 때 정한 허용 루트를 사용하고 요청마다 이를 확장하지 못하게 한다. `..`, 절대 경로, symlink, Windows 대소문자·UNC, 파일 크기 및 레코드 수를 포함해 검사한다. 문자열 startswith로 경계 검사를 구현하면 안 된다. 이 교차 플랫폼 경로 행렬은 아직 실행하지 않았으며 후속 통과 기준이다.

## 12. P2: 지원 언어와 분석 입력 — D7·D11

Python env 사례는 문서를 갱신하면 PASS, Go·Java·Ruby·Vite 사례는 같은 정책에서 WARN이었다. “항상 WARN”으로 일반화하지 않는다. 샘플의 major 실패 임계값이 2라 WARN인 것이며 임계값 1이면 FAIL이 될 수 있다. 파서 언어 지원과 env-key 의미 분석 지원은 별개다.

지원 능력 표를 규칙 종류 × 언어로 작성하고, 구현하지 않은 정적 키 검사는 `unsupported/indeterminate` 근거를 명확히 남긴다. 별칭·동적 키를 임의로 추정해 문서 충족으로 인정하지 않는다. 추가 언어 지원 시 해당 언어의 문자열·주석·동적 호출 대조 사례를 함께 고정한다.

기존 파일의 diff 조각이 문법적으로 불완전해 휴리스틱으로 처리되는 현상은 설계상 확인된다. 원격의 36%·7%는 그 입력 범위의 수치이며 현재 전체 품질 비율로 재사용하지 않는다. 이번 구문 오류+문서 변경 사례도 PASS였지만, Drift Gate는 컴파일러가 아니므로 이것만으로 결함이라고 단정하지 않는다. 분석 상태와 Python/TS 검사를 함께 읽어야 한다.

전체 파일 AST로 개선한다면 기준 버전은 `git show`, 현재 버전은 실제 비교 모드와 같은 snapshot에서 읽고, diff의 수정 노드에만 의미 신호를 귀속한다. 전체 파일에 있는 기존 API를 모두 새 변경으로 처리하면 오탐이 늘어난다. 파일 크기·인코딩·삭제·rename·unavailable·수집 후 변경도 고려한다. 기존 고정 입력과 별도 새 사례에서 개선·악화를 함께 측정한 뒤 채택한다.

## 13. P2/P3: 보고서가 무엇을 검사했는지 설명해야 함 — D10·D13·H6

미등록 파일 제외는 이미 운영 문서에 명시돼 있다. 로컬 preflight에는 `untracked_skipped` 수와 경로를 표시하는 보완이 적절하다. 사용자 인덱스를 몰래 변경하거나 비밀 파일까지 새 파일 검사에 넣으면 안 된다.

빈 diff와 docs-only는 정상 PASS다. 다만 `EvaluationResult`가 가진 `skip`·`skip_reason`·`no_policy`가 JSON 직렬화에서 빠진다. `evaluated_rules`도 실제 실행 규칙 수가 아니라 정책 규칙 수다. 검사 미수행과 실제 6규칙 충족을 구분할 필드가 필요하다.

필수 보고 필드: schema/version, run ID, timestamp, requested/resolved base, head, comparison mode, dirty 상태, policy digest·출처, source snapshot digest, collected·ignored·unmatched·untracked, triggered·evaluated·skipped, analysis method, warnings, gate, execution status. `result=pass`는 정책 판정이고 `execution_status`는 입력·실행 성공 여부다.

0으로 된 40자리 base는 실제로 입력 오류·종료 2였다. 이는 위험한 성공을 막는 현재 동작이며 자동 fallback으로 없애면 안 된다. 최초 push를 지원하려면 저장소 정책에 따라 trusted default branch 또는 empty tree를 **명시적으로** 선택한다. 현재 GitAdapter는 empty tree를 commit으로 허용하지 않으므로 구현 경로도 따로 필요하다. 실제 최초 push 이벤트는 생성하지 않았다.

## 14. 구현 워크플로와 중단 기준

| 단계 | 구현 묶음 | 다음 단계로 넘어가기 위한 근거 |
|---|---|---|
| 1 | CLI 루트·정책 탐색·스키마 오류·신선한 오류 산출물 | D2/D4/D5 및 stale 5조건 해결, 정상 입력 유지 |
| 2 | 언어 문맥 코멘트 판별·rename 경계·coverage 공유 | 유효 `*` 인자 2개, 일반 인자, 실제 코멘트, rename 4조건 모두 올바름 |
| 3 | 자체 검사 신뢰 기준·필수 경로 목록·보호 설정 | 8약화 변형 거부, 신규 운영 파일 누락 거부, 승인된 마이그레이션 허용 |
| 4 | 비교 모드·보고서 출처·skip와 범위 표시 | branch/commit 기준의 독립 diff 대조, 과거 산출물 혼동 방지 |
| 5 | self-audit 상태·MCP·언어별 capability | 거짓 supported 과장 제거, 프로토콜 및 경로 회귀 행렬 |
| 6 | 의미 분석 확대·전체 AST 실험 | 고정 baseline과 독립 사례에서 악화 없이 효과 확인 |

각 단계는 재현 실패 테스트 → 최소 운영 수정 → 정상·반례 대조 → 해당 문서 갱신 → Drift Gate 자체 검사 → 적절한 전체 회귀 → 커밋 순서다. 자체 Gate만을 승인 근거로 삼지 않는다. 운영 코드가 바뀐 최종 커밋은 원격 CI와 세 플랫폼 설치본의 오프라인 결과 파일을 다시 확인한다. 실패하면 실패한 커밋·입력·산출물을 보존한다.

**이번 산출물은 검증과 구현 계획이다. D1~D13 및 H1~H6의 운영 수정이 끝난 것으로 표시하지 않는다.** 현재 운영 코드 수정·새 커밋·푸시는 수행하지 않았다. 원격 문서 반영과 로컬 근거·통합 문서 작성만 수행했다.
