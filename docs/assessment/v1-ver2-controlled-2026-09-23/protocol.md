# v1 태그와 ver2의 통제 비교 프로토콜

작성·사례 고정: 2026-09-23T00:33:28.298859+00:00  
사례 파일 SHA-256: `9c8202b9b73b5573ab6281adfd8a23f501f57cdd9879da7b89376606d50c391b`

## 비교 대상

- `v1` / `v1.0.0` 태그가 가리키는 실제 커밋 `13a5ded9ca03f67cf07d134421d5a1e1cd82b19e`: Claude API가 PR 규칙 문서와 diff를 해석하는 GitHub Action.
- `ver2`의 현재 커밋 `b9c2bd4b2afaca0fcf932f9e3fc1f1428e038cbd`: YAML 정책으로 문서 변경을 평가하는 Python CLI.
- 기존 `main`의 `bffc655`은 `v1` 태그와 다른 버전이다. 이전 main→ver2 성능 수치는 이 실험의 v1 결과로 사용하지 않는다.

## 실험 질문

1. 동일한 합성 Git 변경에서 `ver2`의 실제 판정은 사전 기대값과 몇 건 일치하는가? 오탐과 미탐은 어디서 생기는가?
2. `v1`의 Action이 같은 diff와 규칙 문서를 모델에 전달하는가? 모델의 응답만 바꿨을 때 Action의 CI 결과도 바뀌는가?
3. 공통 입력이더라도 두 제품의 판정 메커니즘이 다른 점 때문에 어떤 성능 비교가 가능한가?

## 통제 변수와 실행 순서

1. `cases.json`의 기준 파일, 12개 변경, 기대 판정을 실행 전에 확정한다. `support` 11개와 문서 형식 경계 `boundary` 1개는 별도로 센다. `fail`은 문서 누락을 차단해야 하는 사례이며 `pass`는 허용해야 하는 사례다.
2. 사례별로 새 임시 Git 저장소를 만든다. 동일한 기준 커밋과 변경 커밋을 `v1`과 `ver2`에 입력한다. 규칙은 `CLAUDE.md`와 `.drift-gate.yml`에 각각 같은 문서 동기화 요구를 표현하되 문법은 각 제품에 맞춘다.
3. `v1`은 태그의 `github-action/entrypoint.sh`를 그대로 실행한다. Git diff 폴백을 사용하고 `curl`만 로컬 가짜 응답기로 교체한다. 실제 Claude/GitHub API 호출, 토큰, 비용은 없다. 모든 사례에 같은 정상 응답 두 개(위반 없음 / `[BLOCKER]`)를 각각 돌려 입력 전달·결과의 응답 의존성을 확인한다. 두 응답은 모델의 실제 판단을 대체하지 않는다.
4. `ver2`는 같은 저장소의 기준 커밋을 `--base`로 지정한 `main.py check --json`을 실행한다. 결과 파일에는 실제 pass/fail, 종료 코드, 판정 근거의 식별 정보만 남긴다. 동일 입력을 한 번 더 실행해 결정성을 확인한다.
5. 두 제품 코드는 수정하지 않는다. 입력 파일, 실행 스크립트, 제품 파일 해시, 도구 버전과 각 사례의 관측 결과를 기록한다. 실패 사례도 삭제하거나 수정하지 않는다.

## 판정 기준

- `ver2`는 `pass`/`fail`을 기대값과 비교한다. 정상 변경의 차단은 FP, 문서 누락의 허용은 FN이다. 오류·skip은 별도 기록하며 정확 집계에서 빼지 않고 실패로 표시한다.
- `v1`의 결과는 가짜 모델 응답에 의해 강제로 정해진다. **v1 정확도, v1-v2 정확도 차이, 모델 품질로 해석하지 않는다.** 평가 가능한 것은 입력 전처리, API 호출 경로, 응답에 따른 게이트 결과뿐이다.
- 개발자가 두 버전의 코드를 이미 본 상태에서 만든 합성 사례다. 독립·블라인드 검증이 아니며 실제 PR 성능이나 리뷰 시간 절감 효과는 측정하지 않는다.
- 비교 범위의 차이는 결과 문서에서 버전 기능 차이와 측정 한계로 분리한다. `support`는 이 실험의 사용 시나리오이지 제품이 공식 지원을 보장한다는 뜻이 아니다.

## 재현 조건

Python 3.11, Git, Bash, jq와 ver2 의존성이 필요하다. 실험 스크립트는 이미 존재하는 결과 디렉터리에 쓰지 않는다. 재실행할 때는 다른 출력 경로를 지정하고 사례·스크립트 SHA-256을 비교한다.

## 실행 도구 보정 기록

첫 2회 실행 후, 결과 문서 커밋 뒤에도 재실행할 수 있도록 스크립트의 `HEAD == ver2 커밋` 조건을 **제품 Python 파일이 고정 커밋과 바이트 단위로 동일한지** 확인하는 조건으로 바꿨다. `main.py`도 검사 대상에 추가했다. 사례·기대 판정·제품 코드·실행 명령은 바뀌지 않았다. 보정 전 결과는 `run-1`·`run-2`에 보존하며, 보정한 도구로 다시 실행한 `run-3`·`run-4`를 최종 비교의 기준으로 삼는다. 이 보정은 첫 실행 후 이뤄졌으므로 최초 도구가 완전히 사전 고정됐다고 주장하지 않는다.
