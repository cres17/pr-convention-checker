# Cross Agent — 문서 기준 구현 현황 기능 계획

작성일: 2026-09-29 · 상태: **첫 단계 구현 진행 중**

> **현재 구현 범위 (2026-09-29):** 데스크톱 앱에 ‘프로젝트 현황’ 화면을 추가했다. 저장소의 Markdown 선택, 체크 항목·완료 조건 표·제목을 기능 후보로 추출, 이름·완료 조건·포함 범위 수정, 코드 경로·줄과 판단 이유 기록, 수동 검증 기록, 로컬 저장·재시작 후 복원, 상태별 요약·필터가 동작한다. 문서·코드가 바뀌면 이전 확인을 집계에서 제외한다. 실제 macOS 앱의 합성 저장소에서 문서 선택→후보 추출→기준 저장→현황 표시를 확인했다. **코드 의미의 자동 판정, 자동 테스트 실행, CI 증거 연결, 기준 변경 전후 비교는 아직 구현하지 않았다.** 아래 4~8절은 최종 목표와 구현 기준을 유지한다.

> **후속 구현 (2026-10-01):** 문서 종류를 현재 목표·향후 계획·과거 결과·참고로 저장하고 현재 목표만 집계한다. 종류 변경 시 기존 근거를 보존하며, 현재 목표 출처가 하나라도 남아 있는 중복 항목은 유지한다. 리뷰의 경고는 ‘주의’, 현황은 ‘근거 없음·재확인 필요’로 구분한다. 근거가 모두 비어 있으면 첫 코드 근거 입력으로 안내하고, 요약 카드는 해당 상태 목록에 연결한다. [구현과 검증 기록](docs/review/document-kinds-v5-v7-2026-10-01.md)을 참고한다. 자동 의미 판정·자동 테스트 실행·기록 삭제·분석 취소까지 완료한 것은 아니다.

## 1. 만들고자 하는 기능

**사용자가 Markdown에 적어 둔 목표를 기준으로, 무엇이 만들어졌고 무엇이 남았는지, 만들어진 기능은 문서대로 동작하는지 한 화면에서 보여준다.**

사용자는 저장소와 기준 문서를 선택한다. 앱은 문서에서 기능과 완료 조건을 정리하고, 실제 코드·연결 구조·검증 기록을 대조한다. 결과는 기능별 현황과 근거, 다음에 할 일로 제공한다.

사용자가 얻어야 할 답은 다음 세 가지다.

1. **어디까지 만들었나?** — 계획한 기능별 구현 상태
2. **제대로 만들었나?** — 문서의 조건과 실제 구현·검증 결과의 일치 여부
3. **이제 무엇을 해야 하나?** — 누락된 구현, 연결되지 않은 화면, 실패한 검증, 확인이 필요한 조건

예를 들어 “로그인 화면은 있지만 로그인 요청 연결이 없다”, “보고서 저장은 구현됐고 파일 생성까지 확인했다”, “Windows 빌드는 성공했지만 실제 PC에서 실행했는지는 확인하지 못했다”처럼 설명한다. 파일 수나 코드 줄 수로 완성도를 대신하지 않는다.

## 2. 현재 앱과 추가할 기능의 관계

현재 앱은 Git 변경 내용을 수집해 `.drift-gate.yml`의 규칙을 평가한다. 지원하는 API·환경변수 항목에는 문서 내용 대조도 적용하지만, **임의의 MD에 적힌 프로젝트 목표 전체를 이해하고 완성도를 평가하는 기능은 아직 없다.**

| 구분 | 현재 제공하는 기능 | 이번에 추가할 기능 |
|---|---|---|
| 질문 | 이번 변경이 설정된 문서·계약 규칙을 충족하는가? | 계획한 기능 중 어디까지 구현했고, 완료 조건을 충족하는가? |
| 기준 | 정책 파일, 변경 전후 코드, 관련 문서 | 사용자가 선택·확정한 MD 요구사항과 완료 조건 |
| 분석 범위 | 비교 기준 이후의 Git 변경 | 선택한 저장소의 현재 전체 구현과 검증 증거 |
| 결과 | 통과·경고·실패, 규칙별 이유, diff | 구현 현황, 검증 상태, 출처, 남은 작업 |
| AI 역할 | 선택적인 추가 검토 | 요구사항 추출·코드 대응 후보 제안·불확실성 설명 |

현재 구조에서 재사용할 수 있는 부분:

- [검사 서비스](drift_gate/desktop/service.py): 저장소 확인과 기존 규칙 검사. 전체 구현 분석은 별도 서비스로 추가한다.
- [데스크톱 연결](drift_gate/desktop/web_app.py): 화면과 Python 연결, 비동기 작업, 이벤트 전달.
- [React 화면](desktop-ui/src/App.tsx): 사이드바, 결과 카드, 필터, 근거 표시.
- [구독 LLM 검토](drift_gate/desktop/subscription_review.py): 공식 CLI 연결과 전송 확인 흐름. 현재 변경 검토용 입력·출력 형식은 새 분석에 맞게 확장해야 한다.
- [기존 UI 구성](docs/design/tool-ui-integration-2026-09-29.md): tool-ui의 요약 카드·작업 단계·전송 확인·diff 표시.

기존 규칙의 `pass`를 프로젝트의 ‘완성’으로 변환하지 않는다. 프로젝트 현황에서는 기존 검사 결과를 해당 변경에 대한 증거로 연결한다. 새 현황 분석은 정책 파일이 없는 저장소에서도 사용할 수 있도록 설계한다.

## 3. 사용자 흐름

```text
저장소 선택
  → 기준 MD 선택
  → 추출된 기능·완료 조건 확인
  → 구현 현황 분석
  → 전체 현황 / 기능별 근거 / 남은 작업 확인
  → 필요하면 검증 실행
  → 수정 후 다시 분석하고 이전 결과와 비교
```

### 처음 사용하는 경우

1. README, 요구사항, 계획 문서 등을 후보로 보여준다. 사용자가 분석 기준에 포함할 문서를 선택한다.
2. 문서를 ‘현재 목표’, ‘향후 계획’, ‘과거 결과’, ‘참고 자료’로 구분한다. 파일명이나 작성일만으로 우선순위를 확정하지 않는다.
3. 앱이 기능 목록과 완료 조건을 제안한다. 사용자는 항목을 수정·병합·제외하고 이번 버전의 범위를 확정한다.
4. 확정한 항목을 기준으로 코드와 증거를 대조한다. AI 없이도 항목을 직접 입력하고 코드·증거를 연결할 수 있게 한다.
5. ‘프로젝트 현황’에서 전체 상태를 보고, 항목을 눌러 근거와 남은 조건을 확인한다.

서로 모순되는 문서, “사용하기 편해야 한다”처럼 판단 기준이 모호한 문장은 ‘기준 확인 필요’로 남긴다. 분석할 수 없는 문장도 목록에서 조용히 버리지 않는다. 외부 문서 링크는 자동으로 따라가지 않고 별도 입력으로 취급한다.

### 다시 사용하는 경우

기존에 확정한 요구사항과 이전 분석을 불러온다. 기준 문서가 바뀌면 추가·변경·삭제 후보를 먼저 보여주고, 사용자가 반영하면 새 기준 버전을 만든다. 코드만 바뀌면 영향을 받는 항목을 다시 분석한다. 분석 도중 파일이 변경되면 결과를 최신 상태로 표시하지 않고 재분석을 안내한다.

## 4. 판정 기준: 구현과 검증을 분리한다

### 구현 상태

| 상태 | 의미 | 판정에 필요한 근거 |
|---|---|---|
| 구현 확인 | 정의된 구현 조건에 대응하는 코드와 연결 경로를 확인 | 관련 코드 위치, 호출·화면 연결, 조건별 대응. 실제 동작 보장은 별도 검증 |
| 부분 구현 | 일부 조건만 구현돼 있거나 연결이 빠짐 | 충족한 조건과 남은 조건을 각각 제시 |
| 미구현 확인 | 범위가 명확한 조건에서 구현 부재를 확인 | 명시적 stub, 빠진 필수 연결, 검토자가 확인한 부재 등 구체적 근거 |
| 확인 필요 | 자료 부족, 지원하지 않는 구조, 문서 충돌로 판단 불가 | 확인하지 못한 범위와 추가로 필요한 정보 |

검색에서 코드가 안 나왔다는 이유만으로 ‘미구현 확인’으로 처리하지 않는다. 범위에서 제외한 요구사항은 별도로 표시하고 집계에서 제외한다.

### 검증 상태

| 상태 | 의미 |
|---|---|
| 조건 충족 확인 | 해당 요구사항의 검증 조건을 현재 분석 대상에서 확인 |
| 일부 조건 확인 | 단위 테스트 등 일부 근거는 있으나 필요한 통합·사용 흐름 확인이 남음 |
| 조건 불충족 | 해당 조건의 테스트 실패나 실제 불일치가 확인됨 |
| 미검증 | 유효한 실행·검토 기록이 없거나 현재 코드와 연결할 수 없음 |

**‘완료 확인’은 구현 확인과 조건 충족 확인을 모두 만족한 항목에만 표시한다.** AI의 판정만으로 완료 처리하지 않는다. 테스트 파일이 있다는 사실과 테스트를 실행해 통과했다는 사실을 구분한다. 수동 확인은 확인자·시점·대상·설명을 남겨 자동 검증과 구분한다.

### 완료율 계산

- 분모는 사용자가 범위를 확정한 **집계 대상 기능 수**다. 상위 기능과 하위 조건을 중복 집계하지 않는다.
- 구현 확인 비율 = 구현 확인 기능 수 ÷ 집계 대상 기능 수.
- 완료 확인 비율 = 구현 확인이면서 모든 검증 조건을 충족한 기능 수 ÷ 집계 대상 기능 수.
- 부분 구현을 임의로 50%로 환산하지 않는다. ‘확인 필요’도 분모에 남겨 불확실성을 숨기지 않는다.
- 기준이 확정되지 않았거나 집계 대상이 0개면 퍼센트 대신 ‘기준 확정 필요’ 또는 ‘대상 없음’을 표시한다.
- 퍼센트 옆에 항상 `완료 확인 4 / 10개`처럼 분자·분모를 표시한다.
- 이 값은 **합의한 기능 목록의 항목 비율**이다. 작업 시간, 난이도, 서비스 품질, 출시 준비율을 의미하지 않는다.
- 범위가 바뀌면 기준 변경량을 함께 표시한다. 기능을 삭제해 비율이 오른 경우를 개발 성과로 표현하지 않는다.

## 5. 화면 설계

사이드바에 **프로젝트 현황**을 추가하고 기존 리뷰 화면과 연결한다. 현황 화면에서는 먼저 상태를 요약하고, 근거는 항목을 선택했을 때 펼친다.

아래 수치는 화면 설명용 가상 예시다. 현재 저장소를 평가한 결과가 아니다.

```text
프로젝트 현황                         [기준 문서] [다시 분석]
기준: 계획.md 외 1개 · 요구사항 v1 · 분석 시점 / 코드 기준

┌────────────────┬────────────────┬────────────────┐
│ 완료 확인 4/10 │ 구현 확인 6/10 │ 확인 필요 1개  │
│ 조건 충족 40%  │ 구현 비율 60%  │ 근거 추가 필요 │
└────────────────┴────────────────┴────────────────┘
구현 상태: 구현 확인 6 · 부분 구현 2 · 미구현 확인 1 · 확인 필요 1

[전체] [남은 작업] [조건 불충족] [확인 필요]       [기능 검색]

기능             구현 상태       검증 상태             다음 할 일
보고서 저장      구현 확인       조건 충족 확인        —
구독 계정 검토   구현 확인       일부 조건 확인        취소 동작 검증
검사 기록 보관   부분 구현       일부 조건 확인        재실행 후 복원
자동 업데이트   미구현 확인     미검증                업데이트 설계

선택한 기능: 검사 기록 보관
  목표 문장 / 출처 문서와 줄
  확인된 코드와 충족한 조건
  남은 조건: 앱을 종료한 뒤에도 이전 기록을 열 수 있어야 함
  검증 기록과 한계
  [문서 보기] [코드 근거] [관련 변경 검사] [검증 방법 확인]
```

### 시각 표현과 상호작용

- 첫 화면은 요약 카드, 상태별 분할 막대, 기능 목록으로 구성한다. 영역별 기능이 많으면 영역별 가로 막대를 제공한다.
- 요약 카드 클릭 시 해당 상태로 목록을 필터링한다. 차트의 각 구간에도 항목 수와 텍스트 범례를 제공한다.
- ‘확인 필요’를 회색 빈 공간처럼 숨기지 않는다. 색상과 상태명·아이콘을 함께 사용한다.
- ‘분석 진행률’과 ‘프로젝트 완료율’은 다른 위치와 이름으로 표시한다. 분석 중에는 실제 단계와 처리 파일 수를 보여주고 예상 퍼센트를 꾸미지 않는다.
- 넓은 창은 목록과 근거 패널을 나란히, 좁은 창은 목록 다음에 상세 화면을 표시한다. 상세에서 돌아오면 필터·선택·스크롤을 유지한다.
- 키보드로 필터·행·상세를 이동할 수 있게 하고 포커스를 표시한다. 오류는 해당 영역에서 이유와 재시도 방법을 알려준다.
- 기존 크림색 배경·짙은 사이드바·녹색 강조와 공통 스타일 토큰을 유지한다. 본문 대비 4.5:1 이상을 확인한다.
- 데이터가 없으면 ‘0%’가 아니라 기준 문서 선택 안내를 보여준다. 분석 실패 시 이전 결과에는 ‘이전 분석’ 표시를 붙인다.

`StatsDisplay`는 요약 카드, `ProgressTracker`는 분석 작업 단계, `ApprovalCard`는 AI 전송 확인에 재사용한다. 요구사항 표·상태별 막대·근거 패널은 새로 만든다. `CodeDiff`는 변경 증거에 사용하고, 전체 구현 근거는 파일의 해당 줄을 읽는 별도 보기로 제공한다.

## 6. 분석 구조와 데이터

```text
선택한 Markdown → 요구사항 후보 → 사용자 확정 → 기준 버전
                                              ↓
저장소 스냅샷 → 코드 색인 → 근거 후보 → 조건별 판정 → 현황 화면
                                              ↑
                         테스트·CI·수동 확인 기록
```

### 분석 단위

| 데이터 | 저장할 내용 |
|---|---|
| 요구사항 | 고유 ID, 기능명, 영역, 목표 버전, 포함 여부, 구현 조건, 검증 조건 |
| 문서 출처 | 상대 경로, 제목, 줄 범위, 원문 발췌, 파일 해시 |
| 구현 근거 | 코드 경로·줄·해시, 연결 관계, 충족 조건, 분석 방법, 한계 |
| 검증 근거 | 대상 요구사항, 실행 방식, 코드 기준, 시간, 결과, 로그 위치, 자동·수동 구분 |
| 분석 결과 | 구현 상태, 검증 상태, 이유, 남은 조건, 확인 필요 사유 |
| 스냅샷 | 요구사항 기준 버전, HEAD, 작업 트리 파일 해시, 분석 범위·제외 목록, 도구·판정 버전 |

요구사항 ID는 재분석해도 유지한다. 문구 수정·병합·분할은 이전 ID와의 관계를 기록한다. 사용자가 상태를 수정하면 자동 판정을 지우지 않고 수정 이유와 함께 보존한다.

### 구현 원칙

1. 전체 구현 분석은 Git diff와 분리한다. 기본 대상은 추적 파일의 현재 작업 트리이며 미추적 파일은 사용자가 포함할 수 있게 한다. 포함 여부를 결과에 기록한다.
2. `.git`, 의존성 폴더, 빌드 결과, 바이너리, 비밀 설정은 제외한다. 저장소 밖 심볼릭 링크를 따라가지 않는다. 파일·총량 제한으로 생략된 범위는 공개한다.
3. 먼저 경로·심볼·설정·연결 관계로 근거 후보를 수집한다. AI가 반환한 파일·줄·인용은 실제 스냅샷과 대조한다. 존재하지 않는 근거는 판정에 사용하지 않는다.
4. AI는 요구사항 추출과 의미 대응을 돕는다. 연결된 코드가 모든 조건을 만족하는지 불명확하면 ‘확인 필요’로 둔다. 정적 분석만으로 모든 실행 경로를 증명한다고 주장하지 않는다.
5. 기존 구독 CLI 연결을 활용하되 새 분석 전용 입력·응답 스키마를 만든다. 선택된 문서·코드 발췌와 전송 범위를 사용자가 확인한 뒤 요청한다. 기존 변경 검토용 한도를 그대로 전체 저장소 분석에 적용하지 않는다.
6. 문서와 코드 안의 명령문은 분석 자료다. 요구사항 추출을 이유로 셸 명령·외부 접속·파일 수정을 실행하지 않는다.
7. 검증 명령은 자동 발견하더라도 실행 전 사용자가 명령·작업 위치·영향을 확인한다. 취소·시간 제한·프로세스 종료를 제공한다. 첫 버전은 자동 테스트 실행 대신 기존 기록 연결과 검증 방법 안내부터 제공한다.
8. 분석 기록은 OS별 앱 데이터 디렉터리에 원자적으로 저장한다. 저장소에는 임의로 파일을 추가하지 않는다. 기록 삭제·JSON/HTML 내보내기를 제공하고 로그의 민감정보를 점검한다.
9. 코드 변경으로 유효성을 잃은 근거는 ‘재검증 필요’로 표시한다. CI 성공도 대상 커밋·실행한 검사·요구사항 대응을 확인한 경우에만 연결한다.

## 7. 구현 순서와 완료 조건

아래는 전체 로드맵이다. 위의 현재 구현 범위와 구분해 읽는다.

| 단계 | 구현 범위 | 완료 조건 |
|---|---|---|
| 1. 기준 확정 | MD 선택, 기능·조건 추출, 출처 표시, 수정·병합·제외, 기준 저장 | 모든 집계 항목이 출처와 완료 조건을 가지며 앱 재시작 후 복원됨. 충돌·모호한 항목이 누락되지 않음 |
| 2. 구현 대조 | 저장소 색인, 코드 근거 연결, 구현 상태, 스냅샷 저장 | 각 상태의 근거를 열 수 있고 없는 근거로 구현 확인을 만들지 않음. 지원 밖은 확인 필요로 표시 |
| 3. 현황 화면 | 요약·상태 막대·필터·상세·남은 작업·기존 리뷰 연결 | 합계와 필터 결과가 일치하고 범위 변경·오류·취소·빈 상태를 구분. 근거 없는 완료 표시 없음 |
| 4. 검증 강화 | 테스트 기록 연결, 선택적 검증 실행, 조건별 결과 | 현재 코드와 연결된 증거만 완료에 사용. 단위 테스트만으로 통합 조건을 충족 처리하지 않음 |
| 5. 변화 비교 | 이전 스냅샷 비교, 기준 변경 분리, 보고서 | 구현 진전·회귀·요구사항 변경을 나누어 설명하고 재시작 후 같은 기록을 열 수 있음 |

**첫 사용 가능 버전은 1~3단계다.** 기준 문서를 읽어 기능별 구현 상태와 남은 일을 보여주는 데 집중한다. 실행 증거가 없는 항목에는 ‘미검증’을 명확히 표시한다. AI 연결이 없어도 수동 기준 입력·근거 연결·현황 조회를 사용할 수 있게 한다.

예상 코드 배치는 다음과 같다. 모두 신규 제안 경로다.

- `drift_gate/core/progress/`: 요구사항·근거·상태 모델과 집계 규칙
- `drift_gate/adapters/progress/`: MD 읽기, 저장소 색인, 기록 저장, 검증 증거 입력
- `drift_gate/desktop/progress_service.py`: 분석 작업과 취소·스냅샷 관리
- `desktop-ui/src/features/project-progress/`: 기준 확정, 현황, 근거, 이전 결과 비교 화면

기존 `web_app.py`와 `bridge.ts`에는 별도 현황 이벤트를 추가한다. 변경 규칙 평가 결과와 프로젝트 현황 결과는 서로 다른 자료형으로 유지한다.

## 8. 통제된 검증 설계

구현 전에 아래 사례의 기대 상태와 근거를 고정한다. 개발용 사례와 최종 확인용 사례를 분리하고, 최종 확인 결과를 보고 수정했다면 그 사례는 회귀 테스트로 전환한다. 다른 문구·폴더·언어 구조의 추가 사례로 다시 확인한다.

| 사례 | 기대 결과 |
|---|---|
| 문서 체크박스만 완료이고 코드는 없음 | 체크 표시를 구현 근거로 인정하지 않음 |
| 함수는 있지만 빈 본문·고정 응답만 있음 | 완료 조건을 충족하지 않으면 구현 확인으로 처리하지 않음 |
| 로그인 화면만 있고 요청 연결이 없음 | 부분 구현, 빠진 연결 표시 |
| 코드와 단위 테스트는 있지만 실행 기록이 없음 | 검증은 미검증 |
| 단위 테스트는 통과했지만 사용자 흐름 테스트 실패 | 해당 통합 조건 불충족, 완료 확인 제외 |
| 같은 목표가 README와 계획서에 중복됨 | 병합 후보 제공, 확정 후 한 번만 집계 |
| 과거 문서와 새 계획이 충돌함 | 기준 확인 필요, 자동으로 한쪽을 선택하지 않음 |
| 동적 연결 등 지원 밖 구조에 구현이 존재함 | 찾지 못했다고 미구현 단정하지 않음 |
| 예전 커밋 테스트 통과 후 관련 코드가 바뀜 | 재검증 필요, 현재 완료 근거에서 제외 |
| 제외한 기능·미래 버전 기능이 있음 | 현재 분모에서 제외하고 제외 목록에 표시 |
| AI가 없는 파일·줄 또는 잘못된 JSON을 반환함 | 검증 실패로 처리, 이전 결과 보존, 완료 집계에 사용하지 않음 |
| 분석 도중 파일 변경·요청 취소·일부 파일 생략 | 불완전·오래된 결과를 최신 분석으로 표시하지 않음 |
| 요구사항 0개 또는 전부 제외 | 0으로 나누지 않고 대상 없음 표시 |
| MD에 명령 실행·비밀 전송 지시가 포함됨 | 지시를 실행하지 않고 자료로만 취급 |

결과 보고서에는 사례별 기대값·실제값·근거와 함께 다음을 싣는다.

- **잘못된 완료 판정:** 실제 미완료인데 완료 확인으로 표시한 수 / 실제 미완료 사례 수
- **완료 누락:** 실제 완료인데 완료 확인으로 표시하지 못한 수 / 실제 완료 사례 수
- **판단 보류:** 확인 필요 수 / 전체 사례 수. 모두 보류해 오류가 낮아 보이는 상황도 공개
- **근거 오류:** 존재하지 않거나 다른 조건을 가리키는 인용 수 / 검토한 인용 수
- **화면 검증:** 상태 합계·분모·필터·기준 변경·키보드 조작·작은 창·재시작 복원 결과

각 비율에는 원시 건수를 함께 적고 분모가 0이면 해당 없음으로 표시한다. 고정된 인수 사례에서 허위 완료 0건, 집계 오류 0건을 출시 조건으로 삼되 일반 저장소 정확도라고 표현하지 않는다. 실제 Windows·macOS 앱 사용 흐름도 별도로 확인한다.

## 9. 이번 문서의 범위와 적용 기록

이 문서는 추가 기능의 설계와 구현 현황을 함께 기록한다. 현재 프로젝트 완성도를 실제로 측정한 보고서는 아니다. 현재 앱이 표시하는 수치는 **사용자가 확정한 기능과 근거·수동 검증 기록**에 대한 것이다. 자동 의미 판정이나 실제 사용자 프로젝트의 전체 완성도 측정으로 해석하지 않는다.

UI 계획에는 `ui-ux-pro-max` 스킬을 사용했다. `project progress desktop dashboard --design-system` 결과의 랜딩 페이지 구성은 앱 현황 화면에 맞지 않아 채택하지 않았다. `status dashboard --domain product` 재검색도 프로젝트 요구사항 관리와 정확히 일치하지 않아 기존 앱 구조를 유지했다. `status color text labels --domain ux`에서 확인한 색상 외 텍스트·아이콘 병기, 대비, 명시적 레이블 원칙을 적용했다.

후속 구현은 **MD 기준을 확정하는 과정과 근거를 확인할 수 있는 상태 판정부터** 시작한다. 그 위에 시각적 현황과 변화 비교를 얹어, 사용자가 숫자의 이유를 직접 확인할 수 있게 한다.
