## 1. 개선 목표

현재 강점은 코드 변경과 문서 변경을 연결하는 정책, 불필요한 경고를 줄이는 변경 분석, 판정과 AI 설명의 분리다. 다음 목표는 **분석 실패나 형식적인 문서 수정 때문에 중요한 변경이 통과하는 상황을 줄이고, 같은 입력에서 개선 효과를 증명하는 것**이다.

개인 프로젝트에서 Claude를 활용했다는 사실과 별개로, 문제 발견 → 대안 선택 → 구현 검증 → 결과 비교를 본인의 경험으로 남기는 데 초점을 둔다. 아래 문제 발견과 기준값은 이번 점검에서 확인한 결과다. 이전 개발 당시 본인이 이미 발견·해결했던 일로 표현하지 않는다.

| pytest 통과율 | **99.79%** | 테스트 개수 비율이며 제품 정확도가 아님 |

실패 테스트는 `test_tree_sitter_grammar_is_available`이다. 문법 로딩 후 `parse_sexp()`가 문자열을 `parser.parse()`에 전달해 `TypeError: source must be a bytestring or a callable, not str`가 발생했다. 따라서 현재 환경에서 AST 분석이 정상 동작한다고 주장할 수 없다. 일부 어댑터가 예외를 잡고 휴리스틱으로 대체하므로, 최종 검사 결과가 정상이어도 파서 자체의 동작을 증명하지는 못한다.

### 3.2 기존 합성 사례 22개 비교

중첩 디렉터리까지 포함한 동일한 22개 JSON 사례로 측정했다. 평가 단위는 규칙 위반이며, 사례 성공은 최종 판정이 기대값과 같고 추가·누락된 규칙 위반이 없는 경우다.

| 방식 | 사례 통과 | FP: 잘못 경고한 규칙 수 | FN: 놓친 규칙 수 | Precision | Recall | F1 |
|---|---:|---:|---:|---:|---:|---:|
| 경로 기반 `path-only` | 19/22 | 3 | 0 | 0.823529 | 1.000000 | 0.903226 |
| 변경 내용 기반 `patch-aware` | 22/22 | 0 | 0 | 1.000000 | 1.000000 | 1.000000 |
| 의미 신호 추가 `semantic-aware` | 22/22 | 0 | 0 | 1.000000 | 1.000000 | 1.000000 |

현재 입증된 차이는 **경로 기반 방식 대비 이 22개 사례에서 오탐 3건 감소**다. 제거된 오탐은 주석·내부 구현 변경 사례다. 다음 개선은 현재 `patch-aware`/`semantic-aware`를 기준으로 비교한다. 과거 경로 기반 방식과의 차이를 새로운 개선 성과로 다시 계산하지 않는다.

이 데이터에서는 patch-aware와 semantic-aware의 추가 정확도 차이가 없다. 파서 오류도 있으므로 Tree-sitter 덕분에 F1이 향상됐다고 해석하지 않는다. `llm-enriched` 평가 분기는 실제 LLM을 호출하지 않으므로 AI 효과 비교에서 제외했다.

### 3.3 별도 개선 목표 사례 8개

기존 평가가 이미 만점이므로, 실제로 드러난 한계를 별도 고정 사례로 만들었다. **버그 재현과 앞으로 지원할 동작의 인수 기준이 함께 들어 있다.** 기존 명세에 대한 테스트 실패율이나 실서비스 정확도로 표현하지 않는다.

| ID | 입력 상황 | 기대 판정 | 현재 판정 | 기대 충족 |
|---|---|---|---|---|
| C01 | API 경로 변경, 문서 없음 | fail | fail | 충족 |
| C02 | API 경로 변경, 무관한 결제 문서의 오타만 수정 | fail | pass | 미충족 |
| C03 | API 경로와 해당 문서의 엔드포인트를 함께 수정 | pass | pass | 충족 |
| C04 | API 파일 삭제, 문서 없음 | fail | pass | 미충족 |
| C05 | API 파일 변경, patch 정보 없음 | fail | pass | 미충족 |
| C06 | 승인 필수 정책에서 임의의 `approved-by` 문자열만 기재 | fail | pass | 미충족 |
| C07 | 주석만 수정 | pass | pass | 충족 |
| C08 | 내부 지역변수 이름만 수정 | pass | pass | 충족 |

**현재 기대 충족률: 4/8 = 50.0%. 목표: 8/8 = 100%.** 이는 목표이며 달성 결과가 아니다.

- 차단해야 하는 5개 사례 중 실제 차단: **1/5 = 20.0%**. 목표는 5/5다.
- 정상 통과해야 하는 3개 사례 중 잘못 차단: **0/3 = 0%**. 이 값은 유지해야 한다.
- C05는 분석 불가 시 차단하는 보수적인 blocker 정책을 선택한 사례다. 모든 제품 사용 환경에서 무조건 차단하라는 의미는 아니다. 경고를 허용하는 별도 정책은 별도 사례로 검증한다.
- 승인 검증을 추가할 때 C06만 통과시키려고 모든 예외를 금지하면 안 된다. 실제 승인·만료·승인 철회 등 양쪽 조건의 사례를 추가해야 한다.

## 4. 우선순위별 개발 과제

### P0-A. 파서가 실제로 동작하도록 복구하고 대체 경로를 드러내기

**현재 근거:** 전체 테스트 1개 실패, 직접 파싱 0/3. `tree_sitter_support.py`의 호출이 설치된 API와 맞지 않는다.

할 일:

1. 파서 입력 형식, 반환 트리·노드 접근 방식을 실제 설치 버전에 맞춘다. 첫 오류만 고치고 완료 처리하지 않는다.
2. 분석 결과에 사용한 방식과 대체 사유를 기록한다. 예: grammar / heuristic / unavailable.
3. Python·TS·Go의 정상 파싱, 잘못된 코드, 문법 로딩 실패를 각각 확인한다.
4. 로컬 설치와 GitHub Action의 의존성을 맞춘다. 현재 `action.yml`은 PyYAML만 설치하므로 깨끗한 실행 환경에서 파서 의존성이 보장되지 않는다.
5. 재현 가능한 버전 정책과 지원 환경 검증을 마련한다. 무조건 최신 버전 허용 또는 무조건 오래된 버전 고정 중 하나만으로 해결됐다고 보지 않는다.

완료 기준:

- 기준 시점의 실패 테스트를 해소하고 전체 테스트가 통과한다. 기존 테스트를 삭제하거나 skip해 수치를 맞추지 않는다.
- 고정 파서 smoke 0/3 → **3/3**.
- 파서 로딩 실패 시 보고서에서 휴리스틱 대체 사실을 확인할 수 있다.
- 기존 22개 사례의 FP 0, FN 0을 유지한다.

주요 위치: `drift_gate/adapters/ast/tree_sitter_support.py`, 언어별 어댑터, `action.yml`, `pyproject.toml`.

### P0-B. 삭제·분석 불가 상태에서 중요한 변경이 통과하지 않도록 하기

**현재 근거:** C04·C05가 pass. 삭제·patch 부재가 `signature-change`로 분류되면 더 높은 `route-contract-change` 기준에서 제외된다. 의미 신호 추출도 추가된 줄 위주다.

할 일:

1. 추가·삭제·수정·이동을 구분하고 삭제된 코드의 API 계약도 분석한다.
2. 변경 전후 전체 파일 또는 신뢰할 수 있는 diff를 기반으로 비교한다.
3. patch 누락, 너무 큰 파일로 인한 생략, 파싱 실패를 명시적인 분석 불가 상태로 표현한다.
4. 분석 불가 때 pass/warn/fail을 정책에서 정하되, C05의 blocker 정책은 보수적으로 차단한다.
5. 파일 이동만으로 계약 변경을 단정하지 않도록 정상 이동 사례도 검증한다.

완료 기준:

- C04·C05 **0/2 → 2/2 기대 충족**.
- C07·C08의 정상 통과 유지.
- 불완전한 분석 결과를 정상 검사 완료로 표시하지 않는다.

주요 위치: `core/classification/intensity.py`, `adapters/ast/analyzer.py`, Git/GitHub 입력 어댑터.

### P0-C. 문자열로 기재한 승인과 실제 승인 증거를 구분하기

**현재 근거:** C06에서 임의의 승인자 문자열만으로 예외가 수락된다. 현재 검사는 승인자의 존재 여부만 확인한다.

2. GitHub 어댑터에서 실제 리뷰 상태와 담당자 자격을 확인한다. 현재 변경에 유효한 승인인지 정책을 명시한다.

- 신뢰 가능한 정상 승인 사례는 여전히 예외 처리 가능.

주요 위치: `adapters/github/client.py`, `core/evaluation/evaluator.py`, `core/models/result.py`.

### P1-A. 문서 동반 수정에서 실제 내용 반영 확인으로 확장하기

**가장 추천하는 차별화 과제다.** 현재는 문서 경로가 수정 목록에 있으면 조건이 충족된다. C02처럼 관계없는 문서 수정으로 통과할 수 있다.

첫 구현 범위는 **환경변수 키와 `.env.example`**으로 좁히는 것을 권한다.

1. 변경 전후 코드에서 요구하는 환경변수 키 이름을 추출한다. 값은 수집·출력하지 않는다.
2. `.env.example`의 변경 여부뿐 아니라 변경 후 내용에 필요한 키가 존재하는지 비교한다.
3. 다른 키 추가·주석 수정만으로는 충족 처리하지 않는다.
4. 이미 필요한 키가 샘플에 있다면 불필요한 문서 변경을 요구하지 않는다.
5. 동적 키처럼 확정할 수 없는 경우는 분석 불가로 명시한다.
6. 누락 키, 사용 위치, 확인한 샘플 문서를 근거로 제공한다.

그다음 범위를 API 메서드·경로와 OpenAPI 또는 정해진 문서 형식의 대응으로 넓힌다. 자유 형식 문서 전체의 의미를 이해한다고 주장하지 않는다. 이 단계에서 C02를 해결하고 C03을 유지한다.

완료 기준:

- 환경변수용 평가셋을 구현 전에 확정하고 **현재 버전의 결과부터 별도로 저장**한다. 현재 환경변수 내용 정합성 수치는 미측정이다.
- 신규 키 누락·무관한 수정은 탐지하고, 이미 반영된 키·올바른 수정은 통과시킨다.
- API 대응까지 구현한 뒤 C02 **0/1 → 1/1**, C03 정상 통과 유지.
- 리포트에 어떤 계약 항목과 어떤 문서 항목을 비교했는지 표시한다.

주요 위치: 문서 검증 어댑터 신설, `core/evaluation/evaluator.py`, `ChangedFile` 또는 별도 분석 결과 모델. 전체 파일 읽기는 I/O 어댑터에 둔다.

### P1-B. 실제 PR을 활용한 별도 평가로 일반화 가능성 확인하기

현재 22개 사례와 추가 8개 사례는 모두 합성 데이터다. 사례 이름의 `oss` 또는 `real-oss-style`은 원본 PR 검증을 대신하지 않는다.

할 일:

1. 본인 프로젝트 또는 공개 저장소에서 초기 목표 **30~50개 PR**을 수집한다. 이는 제안하는 규모이며 현재 확보한 실적이 아니다.
2. 저장소·PR URL·base/head SHA·정책 버전·기대 판정·판정 이유를 보존한다.
3. 문서가 빠진 PR뿐 아니라 올바르게 반영한 PR, 내부 구현 수정, 문서만 수정한 PR도 포함한다.
4. 정책 조정용과 최종 평가용을 분리한다. 최종 평가 PR마다 정책을 바꿔 정답에 맞추지 않는다.
5. 가능하면 다른 개발자가 정답 일부를 검토하도록 하고 의견 불일치도 남긴다. 혼자 판정했다면 그 한계를 기록한다.
6. 비교할 이전 버전과 개선 버전을 동일한 데이터·정책으로 실행한다.

측정값: 규칙 단위 Precision/Recall/F1, PR 단위 불필요한 차단 비율, 놓친 계약 변경 수, 분석 불가 비율. 단위와 분모를 함께 기록한다.

완료 기준: 원본을 추적할 수 있는 고정 평가셋과 이전·이후 원본 보고서 확보. 작은 평가셋에서 일반적인 성능을 단정하지 않는다. 기존 합성 데이터 점수와 실제 PR 점수는 별도 표로 유지한다.

### P2. 반복 예외와 실제 사용 효과를 신뢰할 수 있게 측정하기

현재 반복 예외 경고 함수와 로컬 이력 저장은 있지만, GitHub Action은 실행 임시 디렉터리에 이력을 기록하며 누적 이력 복원과 temporal gate 적용이 연결돼 있지 않다. 조직 단위 추적이 완성됐다고 보기 어렵다.

할 일:

- 저장소·PR·규칙·대상 커밋을 기준으로 중복 실행을 구분한다. 동일 PR 재실행 3회를 서로 다른 예외 3건으로 세지 않는다.
- 지속 저장 및 복원 방식을 정하고 CLI와 Action의 반복 예외 정책을 맞춘다.
- 같은 PR에서 위반 발견 후 실제 해소된 시점만 해결 시간으로 계산한다.
- 우선 경고만 표시하는 방식으로 사용해 유용한 경고·불필요한 경고·수정 여부를 기록한다.

측정값: 고유 PR 기준 반복 예외 수, 유용한 경고 비율, 해결까지 걸린 시간의 중앙값, 정책별 무시 비율. **현재 실사용 수치는 미측정**이다. 위반 수 감소만으로 품질 개선을 주장하지 않는다. 검사 대상 PR 수나 변경 유형이 달라졌을 수 있다.

## 6. 개선 후 재측정하는 방법

다음 명령은 저장소 루트에서 실행한다. 아래는 macOS/Linux 예시다. 기준값과 환경을 맞추려면 Python 3.11.15 및 고정 의존성을 사용한다. Python 패치 버전이 다르면 보고서에 환경 차이가 표시된다.

### 6.1 측정 환경 준비

```bash
python3.11 -m venv /tmp/drift-gate-eval
```

```bash
/tmp/drift-gate-eval/bin/python -m pip install -r docs/assessment/baseline-requirements.txt
```

처음 실행할 때 Tree-sitter가 문법 파일을 내려받을 수 있어 네트워크와 사용자 캐시 쓰기 권한이 필요하다. 캐시 제한으로 인한 초기화 실패와 코드의 파서 호출 오류를 구분해 확인한다.

### 6.2 개선 버전 기록 및 자동 비교

```bash
/tmp/drift-gate-eval/bin/python scripts/measure_development.py --out docs/assessment/after-v2 --compare docs/assessment/baseline-2026-09-22/summary.json
```

결과:

- `after-v2/summary.json`: 개선 후 수치와 환경·입력 해시.
- `after-v2/benchmark-full.json`: 사례별 원본 결과.
- `after-v2/pytest.txt`, `pytest.xml`: 전체 테스트 결과.
- `after-v2/comparison.md`: 기준값 → 개선 후 → 차이와 사례별 판정표.

`after-v1`에는 1차 개선 결과가 이미 있다. 다음 측정에서는 `after-v2` 등 새 디렉터리를 사용한다. 제품 테스트가 실패해도 측정 자료는 저장되며 기록 도구 자체는 정상 종료할 수 있다. **측정 명령의 종료 코드 0을 제품 테스트 통과로 해석하지 말고** `summary.json`의 `pytest.exit_code`와 개별 사례 결과를 확인한다.

### 6.3 비교의 공정성

- 기존 fixture, challenge-v1, 측정 스크립트의 해시가 바뀌면 자동 비교표의 수치 차이 출력을 보류한다.
- 새 기능으로 입력 형식·측정 도구가 바뀌어야 한다면 동일한 새 도구·평가셋으로 이전 제품 코드와 개선 제품 코드를 모두 다시 측정한다. 제품 소스에 맞춘 호환 어댑터의 차이도 공개한다.
- 새 사례는 `challenge-v2`처럼 별도로 관리한다. 8개 중 4개 통과와 20개 중 19개 통과를 같은 집합의 개선률로 계산하지 않는다.
- 테스트를 추가해 전체 통과 수가 늘어난 것은 탐지 정확도 향상과 다르다. 원래 실패가 해소됐는지와 새 테스트를 분리해서 본다.
- 의존성·운영체제·Python이 바뀌면 환경 차이가 표시된다. 의존성 변경 자체가 수정 사항이라면 의도한 차이를 명시하고 나머지 조건을 고정한다.
- 기존 평가 도구의 속도 측정은 의미 분석 전처리를 제외한다. 원본 파일에는 그 값이 남지만 요약 비교 지표에서는 제외했다. 성능 목표가 필요하면 수집/파싱/판정/보고 전체 시간을 별도로 측정한다.
- 고정 사례를 통과하도록 구현한 결과는 회귀·인수 검증이다. 성능 일반화는 별도의 미사용 PR 집합에서 확인한다.

## 7. 최종 전후 비교표

1차 개선의 실측값을 반영했다. 미측정인 실 PR·실사용 지표는 목표값으로 대체하지 않는다.

| 지표 | 현재 저장값 | 목표 | 개선 후 실측 | 해석 |
|---|---:|---:|---|---|
| 기존 pytest | 470/471 | 기존 실패 0 | 524/524 | 신규 53개; 기존 파서 실패 해소 |
| 고정 파서 검증 | 0/3 | 3/3 | 3/3 | 각 언어의 파서 호출 동작 |
| 기존 22개 사례 FP/FN | 0/0 | 0/0 유지 | 0/0 | 기존 기능 회귀 방지 |
| 추가 8개 사례 충족 | 4/8, 50.0% | 8/8, 100% | 8/8, 100% | +50%p; 동일 합성 사례 |
| 차단 대상 탐지 | 1/5, 20.0% | 5/5, 100% | 5/5, 100% | 중요한 변경·우회 탐지 |
| 정상 사례 오차단 | 0/3, 0% | 0/3 유지 | 0/3, 0% | 정상 변경 보존 |
| 환경변수 내용 대응 | 별도 재측정 5/8 | 8/8 | 8/8 | 원래 커밋을 복원하여 같은 새 평가셋으로 비교 |
| 실제 PR Precision/Recall/F1 | 미측정 | 실제 사례 확보 후 결정 | 미측정 | 합성 사례 점수와 분리 |
| 사용자 작업 시간·경고 유용성 | 미측정 | 사용 관찰 후 결정 | 미측정 | 시간 절감 수치 창작 금지 |

예를 들어 실제로 8/8을 달성했다면 **“고정한 8개 개선 목표 사례의 충족률이 50%에서 100%로 50%p 상승했고, 기존 22개 사례의 오탐·미탐 0건을 유지했다”**라고 쓸 수 있다. “제품 정확도가 100%가 됐다”는 표현은 사용할 수 없다. 1차 개선에서 해당 8/8 결과를 실제로 확인했다. 실서비스 전체 정확도로 확대해서 표현하지 않는다.

## 8. 자기소개서용 개발 기록 양식
